# CLI Analytics Storage

OTel telemetry from coding agents, sent by CodeMie CLI (formerly the sdlc-analytics plugin): Claude Code OTLP plus hook events, is stored in PostgreSQL, the only storage engine, behind the ports of `codemie.repository.cli_analytics`. The dashboards are served under `/v1/analytics/cli-analytics/*`.

OTel stays a data source, decoded inside the API: the OTLP endpoints of the API ingest directly, and a background job refreshes the rollups. There is no Collector and no second database; the analytics tables live in the application's PostgreSQL by default (see PostgreSQL Settings). Local stack: `docker compose up -d codemie postgres`.

Analytics sessions run with `jit=off`: plans over every weekly partition cost past `jit_above_cost`, and JIT compilation added ~500 ms to a 3 ms query.

The analytics role needs DDL on its schema, DML on its tables and `TEMPORARY` on the database (PUBLIC has it by default; the refresher stages its keys in a temporary table). A DBA may create the schema for it; the role then needs no `CREATE` on the database.

The connection must be direct or session-pooled (PgBouncer `pool_mode = session`), never transaction-pooled. The session settings above are sent as startup parameters, the background jobs hold session-level advisory locks across transactions, and asyncpg caches prepared statements per connection. This applies to the application database too when `CLI_ANALYTICS_PG_URL` is empty.

## Window Semantics

On the PostgreSQL reader a session is in a date window if `session_dims.started_at` is in `[start_dt, end_dt]` (inclusive, bounds truncated to ms) AND the session has ever produced at least one `turns_daily`, `tool_facts_daily`, `cost_daily`, `session_usage` or `lines_daily` row (`_has_any_activity`, no day bound), OR it has activity inside the window (`_active_in_window`): one of those same five rows on a UTC day wholly inside `[start_dt, end_dt]`, or one on a day the window covers only in part together with a raw activity record stamped inside `[start_dt, end_dt]`. The predicate lives once, in `_sessions_cte` (`sel`); every windowed fact query scopes or inner-joins to `sel` and carries no day, timestamp or hour predicate of its own, so an in-window session contributes all its data whatever the fact's own day, and a session that is out of the window on both halves of the predicate contributes nothing. Sessions without `started_at` are excluded. Session-detail and skill-name lookups keyed by `session_id` are not windowed.

This is a hybrid, not a pure activity check: a session whose `started_at` falls inside `[start_dt, end_dt]` keeps the exact sub-day window-boundary precision earlier design decisions depend on, as long as it has produced at least one real signal, ever — `_has_any_activity` gates that arm so a session that only ever got `session.start`/`session.env` hooks is excluded from `sel` entirely, not merely flagged. The second half (`_active_in_window`) only *additionally* rescues a session whose `started_at` is outside the window but has fresh activity in it — an old session resumed with no new activity in the window stays excluded, one resumed with fresh activity is included. A day row has no time of day, so it decides alone only for a UTC day wholly inside the window (from `_FIRST_WHOLE_DAY_UTC` to `_LAST_WHOLE_DAY_UTC`). For a day the window covers only in part (every day of a Last hour, Last 6 hours or Last 24 hours window, today in Last 7 days, both ends of a custom range) the session also needs a raw activity record stamped inside the window (`_raw_activity_in_window`): an `agent.prompt.submit`, `agent.tool.start`, `agent.tool.end`, `agent.subagent.start`, `agent.subagent.usage` or `agent.skill.dispatch` hook, any `usage_requests` row, an OTel log record or span of a known kind, or a lines-of-code metric point. Lifecycle hooks (`session.start`, `session.env`, `session.end`, `git.snapshot`, summary) are not activity, so a same-day `--resume` with nothing typed is not listed for a window that holds only those hooks, and a session that started after a sub-day window is not listed for it. The raw check is an AND on top of the day row, so it can only narrow the day-row rule. Raw rows are kept for `CLI_ANALYTICS_RAW_RETENTION_DAYS` only: whole days keep the day-row rule for that reason, and a partial first day older than the raw retention admits nobody through this arm. The raw checks use the `(session_id, ts)` index of each raw table. A finer check would mean reading these raw tables for every admission decision instead of the day-partitioned rollups, which exist specifically to avoid that scan cost, so it is left as-is unless a future ticket asks for it explicitly.

**Out of scope:** Copilot subagent fragments appearing as separate sessions (ticket gap (c)) are explicitly deferred to EPMCDME-16572 by the ticket's own Comment 1 ("Subagent fragments are not shown as sessions. They belong to the parent session (fix in EPMCDME-16572...)"), and are not reproducible against this repo's current schema/ingest code anyway (no cross-session linkage found; `subagent_invocations`' primary key is session-scoped, and every `agent_id` usage in `fork_attribution.py`/`reader.py` is joined against its own session, never another session's). No code changes for it here; see EPMCDME-16572 if it is ever substantiated against this repo.

Six indexes serve the window, all from revision `a1c1a0000011` (which adds the columns they cover first): `session_dims_started_at` (`started_at`) and the partial `session_dims_started_shared` (`started_at` where the session is not owner-private, the scope of the shared list), which the readers that do not filter by activity use (the framework counts); and, over the stored activity facts below, `session_dims_active_started` (`started_at` where `has_activity`, the page of any scope), the covering `session_dims_active_shared_cov` (the shared predicate and `has_activity`, `INCLUDE (session_id)`: the unfiltered shared list's page, count and ids-only statements are index-only scans), `session_dims_resumed_last` (`last_activity_day` where `resumed`) and `session_dims_activity_pending` (`started_at` where `has_activity IS NULL`, empty once every session is derived). See *Index and activity-facts runbook* in Operations.

**Stored activity facts (EPMCDME-16427).** The rule above asks five rollup tables for each session; for ~10^6 sessions that is a scan of the window (a 30-day default page timed out). `session_dims` therefore stores `has_activity` (a row exists in any of the five tables), `last_activity_day` (the latest such day) and `resumed` (a row exists on a UTC day other than the session's start day), written by `session_activity.derive_session_activity` for every session of each rollup batch, in the batch's transaction, after the last rollup statement. `_admitted_arms` builds `sel` as five `UNION ALL` selects, each on its own index: (1) started in the window and `has_activity`; (2) started in the window, facts not derived (NULL), asking `_has_any_activity` as before; (3) started outside the window, facts NULL, asking `_active_in_window` as before; (4) started outside the window, `resumed`, with `last_activity_day` on or after the window's first UTC day, decided by the unchanged `_active_in_window` with per-row probes; (5) started outside the window, not `resumed` (all rows on the start day), with that start on the window's first day before it or on its last day after it, decided by `_active_in_window` with the raw records tested first. The unfiltered `start_time` page and count read arm (1) (`sel_main`) and arms (2) to (5) (`sel_rest`) separately: the page is the first rows of the ordered walk of arm (1) merged with the few rows of the rest, and the count is one index-only count of arm (1) plus a count of the rest; every other reader reads `sel`, the union. A candidate filter can only narrow what the exact predicate sees, never widen it, and every session the predicate can admit is a candidate (a session with a day row in the window and a start outside it either has a row off its start day, so it is `resumed` with a last day in or after the window, or all its rows sit on its start day, which then lies on the window's first or last day). The fast-path callers of `sel` that read only ids (`ids_only`: the `ctx_per_call` sort, the framework filter, the cost-model list) use the same five arms. They read the window alone before this change, so a session with no activity was counted by them and not by the list; they now agree. The facts depend on the day rows of the five tables and on `session_dims.started_at`, and both are written only by the rollup refresher, which derives the facts of every session of the batch in the same transaction; the session binding (ingest) writes neither, so the facts cannot go stale behind a writer (`test_session_activity.py` guards the binding). NULL facts are "not derived yet" (a session that existed before the revision, or one written outside the refresher): the lists are exact at every point of the roll-out, and only slower for those sessions. The facts are kept at refresh time, so a session whose rollup rows all pass retention stays `has_activity` (**an accepted divergence from `_SESSION_ADMITTED_IN_WINDOW`, requester 2026-11-06:** for a window older than `CLI_ANALYTICS_ROLLUP_RETENTION_DAYS`, 365 days by default, a session that started in it stays admitted, with no data, where the rule would exclude it; the API caps the length of a window, not its age) (the session itself is purged by `CLI_ANALYTICS_SESSION_RETENTION_DAYS` when set); `resumed` follows the start day the refresh saw, and a start moved by a later refresh is re-derived with it.

The window decides membership only. The start, end and duration a session reports are its activity range (see Notes for a reader), which can begin before `started_at`: a session whose first OTel event precedes its first hook is still in the window of its `started_at`.

Overview's `total_sessions` (`get_cost_kpis`), per-developer `session_count`/`session_ids` (`get_users`) and per-developer-per-day activity (`get_users_daily_activity`) all count every session of `sel`, priced or not — the same costless-inclusive universe the Sessions list already uses via `get_session_cost_facts(..., include_costless=True)`. This replaces the earlier "D1 rule" that restricted all three to the `cost_daily`-only (priced) universe. `get_users_daily_activity`'s day bucket comes from a `UNION` across all five activity tables (not just `cost_daily`), so a costless session's day comes from whichever table it actually has a row in. `get_class_lists(f, "all")` (the subscription-type/project-origin breakdown merged into Overview's and Cost's KPIs) likewise covers every session of `sel`, not only ones with a `cost_daily` row.

`get_cost_kpis`'s `spend_sessions`/`total_cost_usd` and `get_users`'s `cost_usd` still require an actual `cost_daily` row on top of the personal-billed exclusion (`_spend(alias)`): `_spend` only encodes the billing-class check, so every caller must evaluate it against an alias that is NULL for a costless row (the `c` side of the `sel`/`cost_daily` join), never against `sel`'s own row, or a costless company-billed session is wrongly counted as a spend session. This is not optional even when the caller also checks `_spend` against the right alias: `x NOT IN (<subquery>)` is unconditionally TRUE in Postgres whenever the subquery returns zero rows — the common case when no session in the window is personal-billed — regardless of whether `x` itself is NULL, so `spend_sessions`'s `count(DISTINCT s.session_id)` additionally filters on `c.session_id IS NOT NULL` before `_spend("c")` runs. A `sum(...)` filtered the same way needs no such guard: the summed column (`cost_usd`) is itself NULL for a costless row, so `sum` ignores it regardless of what the FILTER clause evaluates to.

Every query that names a developer (`get_users`, `get_cost_by_user`, `get_users_daily_activity`, `get_session_cost_facts`, `get_users_last_active`) resolves it through the single `_DEVELOPER` constant: the session's own email, else its smallest non-empty `cost_daily` email, else its smallest non-empty `lines_daily` email, else `'unknown'`. The expression is self-contained (its own correlated subqueries against `s.session_id`), not borrowed from whatever `c`/`d` alias happens to be in scope, specifically so every one of those callers agrees on a costless session's developer the same way instead of silently diverging per query. `get_users`' leaderboard `ORDER BY cost_usd DESC NULLS LAST` matches `_TOP_MODEL`'s own `DESC NULLS LAST` pattern a few lines above it: Postgres defaults `DESC` to `NULLS FIRST`, which would otherwise sort every costless developer (`cost_usd` NULL after the `RIGHT JOIN sel s` widening) above every priced one.

A session admitted to `sel` only through activity (no cost row at all) needs at least one row in one of the five `_ACTIVITY_TABLES` to be admitted at all (see `_has_any_activity` above) — a live-Postgres test fixture that seeds only `session_dims` (no rollup row of any kind) represents a true zero-activity session per gap (b), not a costless-but-active one, and is now excluded from every list/aggregate, including a session's own owner's private view.

**Scan cost of the admission rule:** the `OR` of the rule (`_STARTED_IN_WINDOW` vs. `_active_in_window`) made Postgres run up to ten correlated EXISTS per `session_dims` row, five with no day bound, and no index could prune rows before them; on the dev data (1.9M sessions, ~949K started in 30 days) the default sort and the count timed out after the rule landed on `main`. The stored activity facts above replace the five unbounded probes with one indexed column and confine the day probes to a candidate set that is small whenever sessions mostly end on their start day (a continued session is the rare case). The candidate filter is not a pre-filter on the rule's meaning: the rule is still evaluated, unchanged, on every candidate. Measured 2026-11-06 on the dev database (1.9M sessions, ~947K started in the 30-day window, every session derived, `VACUUM (ANALYZE)` run), through the running API on a loaded host (load average 15-24): `GET /sessions?per_page=20&sort_by=start_time` answered 200 in 0.16 s for 7 days and 0.46 s for 30 days (0.79 s on the second default-window call, 3.3 s on a cold first one); before the facts, the same request timed out at the 30 s statement timeout. In the plan the started arm's page is an ordered walk of `session_dims_active_shared_cov` (about 0.2 ms for 20 rows) and its count an index-only scan; what remains is the exact check of the sessions that started earlier on the window's first day (about 10,600 here, per-row probes). The dev data has few continued sessions (10 `resumed`), so the resumed arm is a lower bound. Single runs: use `scripts/cli_analytics_bench/run_sessions_bench.py` for a quiet-host figure. The section 6.6 latency budget (825 ms per endpoint) is met by the default sort when the window starts at 00:00 UTC (the presets); a window with a partial first day adds the exact check of that day's sessions (1.7 to 4 s here). The other sorts and the framework filter are above the statement timeout at 30 days: see *Final code, measured 2026-11-06* below.

**Known gap, out of scope by the plan — fact values are not period-clipped:** `_scope` (shared by Overview, Cost, Users, Sessions, Efficiency, the repositories view and the heatmap) carries no day bound at all — once a session is admitted to `sel` for a window, every fact query sums or reads that session's entire lifetime of rows, not just the rows inside the viewed window. The plan is explicit that this task changes session *membership* only, fact *values* stay all-time sums ("list row numbers are NOT period-clipped"), so this is a known, deliberate limitation carried over from the original design, not a gap this ticket's comments ask to close. This is not only an inflated-totals issue: `get_users_daily_activity`, `get_lines_daily` and `get_class_lists(f, "day")` read their day bucket the same unbounded, session-scoped way (`_scope`, no day filter), so a day-bucketed chart for a short window (e.g. "Last 7 days") can render a bucket for a day outside that range whenever an admitted session's unrelated activity happens to fall there — not just a wrong number on an otherwise-correct axis, but an out-of-range axis entry. Clipping fact values (or at minimum these day buckets) to the window touches the day bound of every query `_scope` feeds and was explicitly scoped out of this round; it needs its own task.

The section 6.6 latency budget (825 ms per endpoint) was measured for the Sessions list on the 1.9M-row dev database (about 950K sessions in a 30-day window; see *Known performance limits* and *Final code, measured 2026-11-06* there); the other whole-session scans were not re-measured.

### Project policy (per-project ingest gate)

Whether a project's analytics is stored is a flag in the main database, not in the analytics database: `applications.cli_analytics_enabled` (NOT NULL, default `false`). The migration therefore turns ingestion off for every existing project until a global administrator or maintainer enables the pilot projects; enable them only after their CLI versions send `X-CodeMie-Project`. The gate is `codemie.service.analytics.cli_analytics_project_gate.build_ingest_gate`: the router builds it per request and hands it to the ingestor as a callable, because the adapter may not import `codemie.service`. The ingestor decodes once, calls the gate with the explicit project values and the wire count the decoder collected, and on a discard returns before `_store`, so a discarded request writes no raw rows, resources, dedup entries or rollup work. The reasons, answers and counting rules are in [`cli-analytics-events.md`](cli-analytics-events.md#project-gate).

The setting is visible in the project API (`cli_analytics_enabled` on list, detail, create and PATCH) only to global administrators and maintainers and to the Project Admin of that project; for everyone else the key is absent. Only a global administrator or maintainer may write it: any request body that contains the field from someone else, even `null` or an unchanged value, is 403 before anything is applied. Personal projects stay `false`.

Gate discards are visible as one INFO log line per discarded request (`codemie.repository.cli_analytics.gate_discards`) with route (`otlp` / `hooks`), reason code, dropped record count, `session_count` (distinct non-empty session ids of the kept records), `session_ids` and, when `CLI_ANALYTICS_LOG_HMAC_KEY` is set, `user_hash` (first 16 hex characters of HMAC-SHA256 of the user id, computed only when a discard is recorded: the gate's `user_hash` property, part of the `IngestGate` protocol). A discard of a request with zero records is logged too (`dropped=0 session_count=0`, no `session_ids`). `session_ids` appears only when `session_count` is above 0 and is a sample: at most 3 ids, each with every whitespace or non-printable character replaced by `?` and cut to 64 characters, de-duplicated after sanitizing and sorted; `session_count` counts the raw ids, so two ids that sanitize alike count twice and show once. Limitations: the count undercounts records that carry no session id, metric point types the decoder does not keep and hook events dropped for `RecursionError`; an id is client-supplied text and may embed sensitive text, so treat the line like any application log; an id containing `,` or `=` still stays one bounded line, so grep the line and do not parse it. The HTTP answer is unchanged. The key defaults to empty: until it is set, no `user_hash` field appears in the discard log. Rollout: set `CLI_ANALYTICS_LOG_HMAC_KEY` per environment (a secret, different from `MCP_AUTH_HMAC_SECRET`); changing it changes every hash. The log never carries an email, a project name or a raw user id, and the hash is a log field only, never a metric label. `CLI_ANALYTICS_LOG_HMAC_KEY` is separate from `MCP_AUTH_HMAC_SECRET`.

### Deduplication by `event_id`

- With a non-empty `event_id` the record hash is over (type, session key, event_id) on both paths, so a re-send is recognised whatever the sender's email and two sessions sharing an `event_id` are both kept. The first stored version stays: a changed event, a new summary for one, must carry a new `event_id`. Without one, the old content hash applies.
- The ledger key is `(day, h)` and is kept `CLI_ANALYTICS_DEDUP_RETENTION_DAYS` (14) days: a repeat is dropped when it carries the same UTC day and arrives inside that window.
- On OTLP, a record with an `event_id`, and any `agent.usage.request`, takes `ts` from its `timestamp` attribute (record time when absent or unparseable), as `/event-hooks` does.

### Rollup families 16 and 32

`RollupFamily` gains `USAGE_FACTS = 16` and `SESSION = 32` (`rollup_dirty.kinds` is an integer: no migration).

| Record | New bits |
|---|---|
| `usage_requests` row | `USAGE_FACTS`, plus `LOG_FACTS`; `SESSION` when the session id is non-empty; never `DIMENSIONS` |
| OTel `api_request` | `USAGE_FACTS` on the key of its `LOG_FACTS` |
| OTel `user_prompt`, `api_request`, `api_error` | `SPAN_FACTS` (plus `SESSION` with a session id), on its own day and on the neighbouring day within 1 hour of midnight |
| `hook_events` row of type `agent.prompt.submit` | `SPAN_FACTS` on its own day and on both neighbouring days within 1 hour of midnight |
| `hook_events` row of type `agent.subagent.usage` | `USAGE_FACTS` |
| Any log, hook, span or metric record with a session id | `SESSION` |

- Midnight rule (marking): a `usage_requests` row at most 1 hour after 00:00:00 UTC also marks the previous day, and at most 1 hour before the next midnight the next day, with bits 1, 16 and 32 (`USAGE_REQUEST_REACH` in `dirty.py`, one constant shared with the recompute). An OTel `api_request` with a non-empty `request_id` marks the neighbouring day within the same 1 hour with the bits of its own day (1, 16 and 32 when the session id is non-empty); without a `request_id` it does so only within 5 seconds; this 5 s / 1 h reach is the usage rule. For turns, an OTel `user_prompt`, `api_request` or `api_error` marks `SPAN_FACTS` (plus `SESSION` with a session id) on the neighbouring day within 1 hour of midnight on either side, and an `agent.prompt.submit` hook marks `SPAN_FACTS` on both neighbouring days within 1 hour: a request or an auto-prompt hook that arrives later re-counts the turn of a span on the other side of midnight. A skill initiator hook event (`agent.skill.dispatch`, a Skill `agent.tool.start` / `agent.tool.end`) and a Skill `TOOL` span within the same 1 hour also mark the neighbouring day with bit 4: a fork may start on the next day. Both bounds are inclusive. An `agent.tool.end` / `agent.tool.error` of an `Agent` or `Skill` call of any client, and a `TOOL_EXECUTION` span, also mark the day before with bit 4, at any time of day: the evidence of a call, and a fork's initiator, may arrive up to 1 day later. A `TOOL_EXECUTION` span and an `Agent` or `Skill` `agent.tool.end` / `agent.tool.error` at most 1 hour before the next midnight also mark the next day with bit 4: the evidence of a call may lie up to 1 hour before it. An `agent.subagent.start` with a non-empty `agent_id` also marks with bit 4 the day of every later start of the same `agent_id` in the session: only the first start counts, so a first start that arrives late undoes a later one's count. Ingest runs this lookup, and the one of the own day of the fork or agent an `Agent` / `Skill` `agent.tool.end` names, after the batch's rows are inserted and under a transaction-scoped advisory lock per session of the batch (`pg_advisory_xact_lock`, keys sorted), so of two concurrent batches of one session the second waits for the first to commit and its lookups see the other's rows. An `agent.tool.end` carrying a numeric `lines_added` marks bit 8 on its own day; with a non-empty `tool_use_id` a lookup run the same way (after insert, under the same lock) also marks bit 8 on the day of every stored copy of the same `(session_id, tool_use_id)` carrying a numeric `lines_added` dated on another day: a call counts its lines once, by its earliest copy, so a copy dated earlier that arrives late moves the count off the later copy's day. When its session switches source with this batch (no such event of the session was stored before the batch; checked before the batch's rows are inserted), a lookup run the same way (after insert, under the same lock) also marks bit 8 on every day of the session that has `lines_daily` rows or lines metric points (`metric_points` of the lines metrics only; a day without them has no metric lines to replace), back to today minus `CLI_ANALYTICS_RAW_RETENTION_DAYS` (the cutoff the refresher drops keys by): the session's lines then come from its hook events on every day. A later batch of a session already on its hook events marks only its own day. A metric batch with a lines metric point takes the same per-session lock before it commits (other metric points take none), so a lines metric day committed after a hook batch's lookup is recomputed only once that hook batch has committed. An event dated on the first or the last day of the calendar (0001-01-01, 9999-12-31) marks its own day only.
- Request matching (recompute of day D): tier 1 pairs a transcript request with the OTel `api_request` of the same session and the same non-empty `request_id` (n-th with n-th in time order) when each record lies within 1 hour of the other one's UTC day, in both directions: on the same day anywhere, or across a midnight with both records within 1 hour of it. D therefore reads transcript requests whose latest line is in [D - 1 h, D + 1 day + 1 h) and OTel records in the same range. The matched row is written only on the transcript request's own day; the paired OTel record is not written on its own day as a service or OTel-only row, so a cost is never counted on two days. Tier 2 (fingerprint, no identifier) stays at 5 seconds: both records within the day widened by 5 s and at most 5 s apart. Tier 2 requires the input, output, cache-read and cache-write totals equal for every transcript request, a partial one included, so a partial request cannot take the exact match of a final one. Tier 3 handles the partial transcript requests (no `stop_reason` on a non-`is_api_error` request, positive output) and the OTel records that tiers 1 and 2 left unpaired: same session, the same UTC day (`a.t_day = b.o_day`), the OTel `model` equal to the transcript's raw model, both records within the day widened by 5 s, the OTel output at least the transcript output, at most 30 s apart (`_MATCH_PARTIAL`), and not both `request_id`s present. Input and cache totals are not required (Claude Desktop reports them differently). A main-thread transcript request (empty `agent_id`) is paired only with an OTel record whose `query_source` is empty, `repl_main_thread` or `sdk` (so never a `compact`, `generate_session_title` or `prompt_suggestion` side call, nor a subagent's record); a subagent request (non-empty `agent_id`) only with a record whose `query_source` is empty or starts with `agent:`. Tier 3 is resolved one to one like tier 2 and never takes a record paired by tier 1 or 2; each request takes the first free candidate by: input, cache-read and cache-write totals equal, then the transcript `agent_type` equal to the OTel `agent.name` or to the last `:` part of an `agent:` `query_source`, then the nearest gap (ties to the earlier OTel record). A final request, an `is_api_error` one and a partial one with a 0 or NULL output are never paired by tier 3. Known limits of tier 3: two subagents of one type running in parallel within 30 s can swap their OTel records (the session totals stay right, the per-agent attribution may shift); the main-vs-subagent filter does nothing when `query_source` is empty (Claude Desktop does not document it), where only the totals and the agent-name preference apply; a partial request and its OTel record on two sides of a midnight stay unpaired, so both days recompute to the same result. The lines of one transcript request are grouped across the same 1 hour reach, so a request straddling midnight is never counted on two days.
- Every family recomputes: bit 16 rebuilds `session_usage` and `session_usage_hourly`, bit 32 the new `session_dims` columns and `subagent_invocations`. The `SESSION` statements run for the session of every claimed key with bit 1, 4, 8 or 32, after the daily and hourly rollups and `DIMENSIONS`. A key holding only bit 32 for a session with no rollups runs without error.
- A day is recomputed only inside raw retention; older keys are dropped with a WARNING and their rollups are kept.

### Session tables

| Table | Key | Recomputed |
|---|---|---|
| `session_usage` | `session_id, day, model, speed, inference_geo, scope_kind, scope_name, agent_id` (`''` = unknown) | Per `(day, session)` by bit 16: delete the day's rows, insert from `usage_requests` and OTel `api_request` |
| `session_usage_hourly` | the same plus `hour` and `service_tier` | Same recompute, one row per hour of the request time; the hours of a day sum to its `session_usage` rows |
| `subagent_invocations` | `(session_id, agent_id)` | Bit 32, upserted; the latest `agent.subagent.usage` wins; `attribution` is `hook` or `heuristic` (only start/stop seen); a `duration_ms` computed from the two times is NULL when the end is before the start |
| `session_dims` (new columns) | `session_id` | Bit 32, merged into the stored row; `DIMENSIONS` (bit 2) keeps the columns of the initial schema |

- Subagent totals are read from the agent's latest `agent.subagent.usage` event that carries them (`usage` is an array with at least one object); a later event without them replaces nothing. They become `session_usage` rows only when the session has no `usage_requests` for that agent, no OTel `api_request` and no `session_usage` row of the session (any day, any `agent_id`) carrying `attrs.otel_requests`; otherwise they stay in `subagent_invocations.attrs`. They are never added to per-request rows and have no hourly rows. The last condition keeps the tokens from being counted twice once raw retention has purged the OTel records: a later recompute of the totals' day still sees the marker. The delete of stale totals rows uses the same predicate.
- `api_calls`, `web_search_requests` and `web_fetch_requests` of `session_usage` and `session_usage_hourly` are `int` columns. A sum that does not fit is stored as NULL, so the recompute of the key never fails on it.
- `attrs.otel_requests` on a `session_usage` row is the number of OTel `api_request` records that went into the row: matched rows, `service` rows and OTel-only rows. The key is present only when the number is above 0. It is not a `token_source` value: a matched row takes its tokens from the transcript and only its cost from OTel, except the output of a partial request (no `stop_reason` on a non-`is_api_error` request), which is `greatest(transcript, OTel)`. A partial request with a positive output that tiers 1 and 2 did not pair is paired with the OTel record of its model on the same UTC day within 30 s whatever the input and cache totals (tier 3, with the main-thread / subagent filter and the preference order described under request matching), so it is one request, not a transcript row plus a service row. A partial request with no such OTel record (including one across a midnight), or with a 0 or NULL output that tier 2 did not pair, keeps its transcript output as a lower bound.
- `session_dims` merge kinds (a NULL never overwrites a value):

| Kind | Rule |
|---|---|
| summary | Counters, lists, `title`, `ended_at`, `client_versions` and similar come from the latest `agent.session.summary`, written only when its `ts` is not older than the stored `summary_ts` |
| fallback | The same columns for a session with no summary, computed from raw rows; written only while `summary_ts` is NULL |
| priority | (`user_email`, `identity_source`) and (`story_id`, `story_source`) are replaced only by a higher rank, or the same rank and a later timestamp |
| latest value | Columns from `agent.session.env`, `agent.git.snapshot`, common fields and `session_attributes`: the latest non-empty value |
| latest session name | `session_title` is the latest non-empty `session_title` field of the session's events, trimmed of spaces, tabs, carriage returns, line feeds and no-break spaces (U+00A0) and cut to 200 characters; a blank value shadows nothing. It is a column of its own, never a key of `session_dims.attrs`, and is separate from the summary's AI-generated `title`, which is stored but not served |
| accumulating | `sources`, fallback `client_versions` and `attrs` are merged with the stored value; an `attrs` key is never removed |
| rollup-derived | `active_ms`, `source_cost_usd`, `delivery_framework` (classified from skill names and subagent types), `feature_id` are recomputed each time |

- `tool_calls`, `tool_errors` and `tools` follow a stricter summary rule, because a fallback value includes subagent calls and a harvester adds the subagents' counts to a summary's. When a summary wins, a present value replaces the stored one (0 included); when the summary omits the field (absent, NULL, malformed or out of range), the stored value is kept only if the row carries `attrs.tool_counters = 'summary_only'`, else it becomes NULL. Every summary win writes that marker, a first insert of a session that already has a summary included (an older summary that loses never does), so on a marked row each of the three is a summary value or NULL. The marker is the compatibility signal: a harvester must add subagent counts only to a marked row, and treat an unmarked row (or a backend that never writes the marker) as not safe. Limits: a row stored before this rule has no marker even when `counters_source` is `summary` (the flag can sit on fallback values), so its next summary win NULLs the fields that summary omits, and its current values are not repaired. Repair is a backfill that marks the retained raw sessions dirty and recomputes them from the retained summary events (an equal `ts` wins); where raw summaries have expired, the per-field origin cannot be rebuilt and nothing is repaired. Deploy this backend before enabling the harvester, then backfill only the sessions that matter.
- When the stored `activity_started_at` is earlier than the earliest raw record now present (raw rows were purged), fallback columns sourced from raw rows keep their stored value.
- A `session_dims` row created by a backfill rebuild (`--now`) keeps `delivery_framework` NULL until the next recompute by the refresher: the command passes no classifier.

### Counter fallback

A `(day, session)` pair is a fallback pair when it has no span of kind `TOOL`, `TOOL_EXECUTION` or `INTERACTION`; the test is by kind, never by name. Its `turns_daily`, `tool_facts_daily`, `invocations_hourly` and `session_files_daily` rows are counted from `hook_events` (`agent.prompt.submit`, `agent.tool.start`/`end`/`error`, `agent.skill.dispatch`, `agent.subagent.start`); a pair with spans uses spans. Tool calls, turns, files and agents have one source per pair, never both. Skills are read from spans and hooks on every pair, and each skill invocation counts once: an `agent.tool.start` of a call that has a `TOOL` span is left out, and so is a forked skill's `agent.subagent.start` joined to a counted initiator. An `agent.subagent.start` counts once per `agent_id`, by the first start of that `agent_id` in the session: SendMessage continues an agent or a fork under its `agent_id` with a new start, which is no new invocation; a start with an empty `agent_id` counts on its own. Skill and agent counts therefore also read the fork a Skill call's hook `agent.tool.end` names (its `fork_agent_id`, else the complete `agentId` in `tool_response`; never the typed `agent_id`, which on a call made inside a subagent is the caller's) and `agent.skill.dispatch` `prompt_id` (a slash command's fork, only when the dispatch is the one of its `prompt_id`: a start of its skill name, else a foreground one without a skill name that no `Agent` call names), on any day of the session, a day with spans included; these fork rules read Claude Code events only (`platform` `claude-code` or absent). `turns_daily` counts every `agent.prompt.submit` except a Claude Code hook's (`platform` `claude-code` or absent) prompt starting with `<task-notification>` or `<agent-message`; an empty `prompt_body` still counts. `success` is an `agent.tool.end` with the same `tool_use_id`, counted on the day of the start. The reader has no fallback query of its own: it reads these rollups for the sessions of the window.

### Session prompt (`prompt` of the sessions list and the session detail)

The served `prompt` is the session's name when `session_dims.session_title` is non-empty after trimming; otherwise it is the first prompt, cleaned again at read time (`strip_pasted_content`: the `<pasted_content ...>` and `</pasted_content>` tags removed, the pasted text kept, trimmed of spaces, tabs, carriage returns, line feeds and no-break spaces (U+00A0) at both ends; the tag's attributes are complete quoted `name="value"` pairs separated by ASCII whitespace (`[ \t\n\r\f\v]`, never the locale-dependent `\s`); a tag cut off at the very end of the text is removed too, while a stray `<pasted_content` followed by prose is left in the text). The read-time cleaning serves a `first_prompt` stored with the tags clean even when its raw rows are past retention and cannot be recomputed. When the cleaned first prompt is empty (an old-CLI prompt cut inside the open tag), the served `prompt` is the session's repository, else its branch, else an empty string; the fallback order is title, cleaned first prompt, repository, branch. Efficiency's `worst_session_prompt` uses the same label (truncated to the preview length; `null` when it is empty). The search term of the sessions list is matched in SQL against the stored `first_prompt` (not cleaned at read time), the stored `session_title`, the repository and the branch; a session whose title is empty is found by its first prompt, which is also what it is served as. The summary's `title` is stored in `session_dims`, not read, served or searched. `prompt_original` and `session_title` are not copied into `session_dims.attrs` (`session_title` has a column of its own); both stay in `hook_events.attrs` until raw retention (`otlp.py`, the event keys outside `HOOK_KNOWN_KEYS`), and search matches the stored first prompt, not the cleaned one (a pasted-content tag inside the stored prompt is searchable text).

### Slash commands (`get_invocations`, kind 4)

`slash_commands` of `/tools` has one source per session. Only the kind-4 branches of the PostgreSQL reader's `get_invocations` follow this rule.

| Session | Source |
|---|---|
| With a summary (`session_dims.summary_ts` is not NULL) | Every string element of `session_dims.commands`, each counting 1 (duplicates kept, names as stored, without a leading slash). Non-string and empty elements are skipped; an empty or NULL `commands` adds nothing. Its OTel `user_prompt` records (kind 4 of `invocations_hourly`) add nothing |
| Without a summary | `command_name` of its OTel `user_prompt` records, from `invocations_hourly`, as before |

The window is the shared one (see Window Semantics): a session whose `started_at` is in the window adds all its commands, whichever source they come from.

### Known limitations

| Case | Effect |
|---|---|
| A tool call starts before midnight and its `agent.tool.end` arrives after 01:00 in a later batch | `success` stays 0 on the start's day until that day is recomputed again; a full rebuild gives 1. The span path has the same gap. Hook and span marking are unchanged |
| Tier-1 request matching: a transcript request and its OTel `api_request` (same session, same `request_id`) are more than 1 hour apart around midnight, so one record is outside the 1 hour reach of the other's UTC day | The pair is not matched and a cost can be lost; it is never counted twice, because the matched OTel record is written only with its transcript request |
| A client version changes between batches and there is no summary | `client_versions` accumulates both incrementally and after a backfill over existing rows; a rebuild from an empty schema keeps only the latest |
| Hooks counted a tool call, then an `INTERACTION` span with no tool spans arrives | `tool_calls` keeps the hook value incrementally (a NULL never overwrites); a full rebuild gives NULL |
| A session known from hooks only | `get_session_detail_tools` shows no tools: it reads raw spans only |
| A summary, an identity or a story event dated in the future by a wrong client clock | It is the latest by its own time: later, correctly dated events of that session do not replace its values until real time passes that date. The recalculation never compares client times with the current time |

**Turn rule (`turns_daily`).** A turn is an interaction the user started that talks to the model: a typed
prompt, or a slash command that made a model request. Auto prompts are not turns. A `claude_code.interaction`
span counts unless one of three checks, applied in order, finds a row:

1. Auto prompt: a `user_prompt` log row (`event_kind = 2`) of the same session and `span_id` whose `prompt_id`
   is the `prompt_id` of a Claude Code `agent.prompt.submit` hook (`platform` `claude-code` or absent) whose
   `prompt_body` starts with `<task-notification>` or `<agent-message`
   (`vocabulary.CLAUDE_CODE_AUTO_PROMPT_PREFIXES`; leading space, tab, CR and LF are ignored; this turn rule keeps its own trim set, not the blank set above):
   the prompts Claude Code injects itself when a forked skill, background agent or background command finishes,
   and when a subagent hands its result back or a peer session sends a message. In OTel it looks like a typed
   prompt; only the hook tells them apart.
2. Command without a model request: a `user_prompt` row of the same session and `span_id` with a non-empty
   `command_name`, and no `api_request` (`event_kind = 1`) or `api_error` (`event_kind = 6`) row with the same
   `span_id`. The test applies to slash commands only: a typed prompt interrupted with Esc sends no request and
   is still a turn.
3. Injected message without a hook and a model request: on a Claude Code span (name starting `claude_code.`), a
   `user_prompt` row of the same session and `span_id` with a `prompt_id` and no `command_name`, no `api_request`
   or `api_error` row with the same `span_id`, no `agent.prompt.submit` hook with that `prompt_id`, while the
   session has an `agent.prompt.submit` hook carrying a `prompt_id` within 1 hour of the span's `ts` (the plugin
   is present). Claude Code injects a
   `<task-notification>` that fires no `UserPromptSubmit` hook and makes no model call, so the auto-prompt check
   cannot see it; a typed prompt fires its hook, so an Esc-interrupted one stays a turn. Another client's
   interaction span is not tested.

Every row is paired with the span within 1 hour of the span's `ts` on either side (`_CROSS_MIDNIGHT` in
`dirty.py`, the reach at which ingest marks a neighbouring day), and every lookup is bounded by `session_id`
and `ts`, so it reads the `(session_id, ts)` indexes of `log_events` and `hook_events`. The checks are
`NOT EXISTS`, so a duplicated `user_prompt` row cannot count a span twice. A fallback pair counts its
`agent.prompt.submit` hooks except Claude Code's `<task-notification>` and `<agent-message` ones: built-in slash commands fire no `UserPromptSubmit`
hook (checked on Claude Code 2.1.302 with `/model`, `/effort`, `/context`, `/cost`, `/help`, `/status`, `/mcp`,
`/clear`, `/compact` and `/exit`), so there is no command prompt to exclude there, while project and plugin skills
fire it and are turns. The texts Claude Code writes into the transcript itself — "This session is being continued
from a previous conversation…", "Caveat: The messages below were generated by the user while running local
commands", `<command-name>` and `<local-command-stdout>` wrappers — reach neither a `user_prompt` log nor the
prompt hook (checked after `/compact`, with `--continue` and with `--resume`), so they are never counted. Limits: a request more than 1 hour after its command is not seen, and the command is not
counted; without the plugin hooks an auto prompt or an injected message stays a turn; in a plugin session an
Esc-interrupted typed prompt whose hook is lost (or not yet delivered) is not a turn — a late hook re-counts its day.

**`ended_at`/`duration_ms` and a non-final summary.** `agent.session.summary` is sent on every Stop,
not only at `SessionEnd`, each one marked `is_final`. A **final** summary (`is_final: true`, or the
field absent — an older client never sent it, and absence keeps the pre-existing, final-wins
behavior) is authoritative outright: `ended_at`/`duration_ms` come from it alone, even if some
unrelated raw record lands later. A **provisional** summary (`is_final: false`, the shape every Stop
sends since codemie-code v0.15.9) is a lower bound, not the final word: `ended_at` is the *later* of
that summary's own `ended_at` and the session's latest raw record, so a `SessionEnd` cancelled after
the last Stop (a normal `/exit`) does not truncate the stored duration back to that Stop. Tolerance:
once a final summary or a real `SessionEnd` is recorded, the value is exact to the transcript; while
only provisional summaries have been seen, the duration can still undercount by up to the gap between
the true exit and the latest raw record this session has sent so far. That gap narrows with the next
raw event or summary, whichever lands first, and closes outright once the real `SessionEnd` arrives —
**but if neither ever does** (the session goes idle after its last Stop and sends no further
telemetry of any kind, the normal-`/exit`-with-cancelled-`SessionEnd` shape this fix exists for), there
is no later event to narrow or close it: the undercount is not bounded by this mechanism at all and
the duration stays at the last Stop's timestamp indefinitely, the same as before this fix.

This stored `ended_at` is not the whole of the reported duration, and the two layers do not make each
other redundant. The reader derives what a dashboard shows from the activity range
(`greatest(last_event_at, ended_at, latest log_events, latest spans)`, see Window Semantics), so a
tail that lands in `log_events` or `spans` is recovered there even when the stored `ended_at` is cut
at a Stop. The reverse does not hold: those probes read those two tables only, and `last_event_at`
moves for the 13 dimension hook types alone, so a tail that is a non-dimension hook
(`agent.git.snapshot`, which is sent *at the end of the session*), a `usage_requests` row or a
`metric_points` row is invisible to the reader. The fallback range behind `ended_at` spans all five
raw tables, so correcting it here is the only way those tails reach the reported duration — and
`ended_at` is itself one of the inputs to that `greatest(...)`.

**Notes for a reader.**

- Two pairs of times. `started_at` and `last_event_at` are hook times and decide the dashboard windows. `activity_started_at` and `ended_at` are the first and the last transcript line (the raw range in the fallback).
- The reported session range (EPMCDME-15506). The client stamps a hook after its own setup work, so an OTel `api_request` or tool span can precede the first hook or follow the last one. The reader reports start = `least(started_at, activity_started_at, earliest log_events / spans row)`, end = `greatest(last_event_at, ended_at, latest log_events / spans row)`, and `duration_ms` = end − start: wall clock, idle time included. Every path looks for OTel rows only within one day of the column bounds, which prunes the other weekly partitions at run time, so the Sessions list and Session Detail always agree; a session without a `session_dims` row (Session Detail only) has no column bounds and every row of it counts. The Sessions list, Session Detail, `get_session_durations` (Users Avg Session Duration, the Overview `duration_ms`) and the activity heatmap all report this range. `session_dims.duration_ms` is not read by them.
- `session_dims` counters describe the main thread. Tools, skills and commands of a subagent are in `subagent_invocations`.
- In `session_usage`, `agent_id = ''` is the main thread and `agent_id <> ''` a subagent. `scope_kind = 'service'` is a request Claude Code made outside the transcript (session title, compaction): it has tokens and cost and no counterpart in the counters. The rule is the missing transcript counterpart, never the value of `query_source`; values seen so far are `repl_main_thread`, `sdk`, `agent:builtin:<type>`, `generate_session_title` and `compact`.
- `model` is normalised, for a request known from OTel only by the plugin's steps, so a model has one name in every row; fast mode and the inference region are in `speed` and `inference_geo`, not in the model name. `cost_daily.model_name` keeps the raw OTel name.
- `source_cost_usd` is the cost OTel reported. A request known from the transcript only has NULL there (0 in `cost_daily`): price it from its tokens. A row built from OTel only has the cache-write total in `cache_creation_tokens` and the 5m / 1h split from the `api_request` attributes `cache_creation_5m_tokens` / `cache_creation_1h_tokens` when present, NULL otherwise. A matched request takes the cache-write total and split from its transcript; when the transcript has no split, it takes the OTel record's total and split instead, never one from each.
- The hours of a day in `session_usage_hourly` sum to the request-derived rows of `session_usage`. Rows with `attrs.token_source = 'subagent_usage'` are subagent totals and have no hourly rows.
- `attrs.otel_requests` on a `session_usage` row tells how many OTel records went into it; `subagent_invocations.attribution` is `hook` when the row rests on a usage event or usage rows, `heuristic` when only start and stop were seen.
- `team` is the tag the client's configuration states, and `feature_id` is derived from the branch; neither is a roster team or a tracker epic.

## Money

Every money value of CLI Analytics (COST, per user, per model, per session, per repository, cache-read cost, `bloat_pct`, Wasted) is token counts × the platform catalog, priced at read time in the handler with the current prices: LiteLLM's `model_info` with the proxy on, the `config/llms` YAML otherwise. The response metadata names the catalog that priced it in `catalog_source` (`litellm` / `yaml`).

- Every aggregate surface prices the same rows: `get_session_model_costs` returns the token sums per (session, raw model), the empty model kept. Each row is priced once; the totals, per user, per model (by the normalised name) and per session are sums of those rows, so they add up to the total.
- Input, output and cache-read tokens are priced at the model's input, output and cache-read price; 5m cache writes at `cache_creation_input_token_cost`; 1h cache writes at `cache_creation_input_token_cost_above_1hr` (optional in the YAML `cost:`; a model without it prices 1h tokens at 0). A cache write without a 5m / 1h split is priced at the 5m price; the split never prices more tokens than the cache write.
- A model without a catalog entry, without a price for a token kind it used, or with an empty name (reported as `""`) contributes 0 for those tokens and is listed in `unpriced_models`.
- Totals-only subagents: `get_session_model_costs` and `get_session_detail_model_costs` UNION the `session_usage` rows with `attrs.token_source = 'subagent_usage'` into the `cost_daily` token columns, so a subagent that reported only totals is priced at read time like any other row. The rollup guard `_totals_are_a_source` is the only double-count protection (it removes the totals rows once requests of that agent exist); the reader adds none. A totals model absent from the catalog prices 0 and is listed in `unpriced_models`. A totals row without a cache split keeps the 5m / 1h sums NULL.
- Sessions list: sessions with dimension events but no `cost_daily` row are listed (`include_costless`) with `cost_usd` 0.0 and `cost_available: false`; `cost_available` is true when the session has at least one token row (`cost_daily` or subagent totals) whose model has a catalog entry (a priced row); it is false when the session has no token rows (cost-less) or only rows of models missing from the catalog, with `cost_usd` 0.0. A model with a catalog entry but no price for some token kind counts as priced, so `cost_usd` may be understated for such a session; a free model with a catalog entry counts as priced. The list and the session detail use the one helper `priced_session_ids` (`session_money.py`). The detail of a costless session resolves too (`get_session_detail_meta` also keys on `session_dims`), with zero cost and no model rows. The count of sessions listed with `cost_available: false` is logged as `no_token_rows` and `unpriced_models` (no user or project data). KPIs, priced aggregates and the other endpoints keep the inner join and do not list them.
- Sessions list paging (every sort and search is decided in PostgreSQL, and so is the framework filter's page and total; the framework rule itself, the customer's regex configuration, is applied in Python to the window's distinct classifier name sets, and Python prices and builds the page's rows):
  - `get_session_page` returns `(total, session_ids)` of one page for `start_time` and `ctx_per_call`; `get_cost_page` does the same for `cost_usd` and also returns the kind flags of the window; `get_framework_page` does it for the framework filter. Order is the sort key DESC, then `session_id COLLATE "C"` ASC, for every sort. `total` is an exact count. The offset is clamped, so a huge page number returns an empty page with the exact total.
  - `start_time` orders by `session_dims.started_at` (page and count are separate statements). The unfiltered shared list (the default Sessions request) runs its page and count on `session_dims_active_shared_cov` (the page an ordered walk, the count index-only); the other scopes and filtered requests use `session_dims_active_started`, and `session_dims_started_at` / `session_dims_started_shared` serve the readers that do not filter by activity. The order key is the stored hook time, while a row's `start_time` is the reported activity start (`least(started_at, activity_started_at, earliest OTel row)`, see Notes for a reader): for a session whose first OTel event or transcript line precedes its first hook the two differ, so such a row can look out of order by that gap. Ordering by the reported start would need a stored sort column with its own index. `ctx_per_call` is the session's cache-read tokens (subagent totals included) per API call, 0 without calls; for the unfiltered shared list (no search, no unattributed filter, no user / project / repository / branch / class filter, the admin `exclude` scope) `sel` outputs the session id alone, so the window's ids are read as an Index Only Scan of `session_dims_active_shared_cov` instead of a Bitmap Heap Scan of the wide `session_dims` rows; every other `ctx_per_call` request, and the other sorts, keep the full lean projection (same ids, order, total and tie-break either way). `cost_usd` is the SQL twin of `CatalogPricer.price` (`round(cost, 9)`) over the catalog rates of `get_cost_models()`, built from one materialised (session, model) token grouping that also yields the kind flags.
  - Search is a case-insensitive literal substring match (`ILIKE ... ESCAPE`, `%`, `_` and `\` never special; case folding follows the database collation) over the stored first prompt, session title, repository and branch, for every sort. A NUL character matches nothing and returns an empty page: the `start_time` and `ctx_per_call` paths issue no statement, while the cost sort and the framework filter still run their model-list and flags statements first (the metadata is whole-window).
  - The per-session queries run for the page's ids only (`LocalAnalyticsFilter.restricted_to` adds `session_id = ANY(...)` inside `sel`, on top of the existing scope, never in place of it).
  - The framework filter is the customer's regex config, so it stays in Python: the reader builds the classifier names of the filtered window into a temp table (one connection, one transaction), returns the distinct name sets, the handler keeps the sets the classifier accepts, and the page is cut from the sessions of those sets. For the unfiltered shared list (the same conditions as the `ctx_per_call` ids-only `sel`) every statement of the framework request reads `sel` as `session_id, started_at` (the names statement, the page statement and the whole-window flags statement of `get_window_model_flags`, which does the same whenever its filter is unfiltered): both columns are in `session_dims_active_shared_cov` (key `started_at`, INCLUDE `session_id`), so the window is an Index Only Scan (0.3-0.5 s) instead of a Bitmap Heap Scan of the wide rows (3-4 s) that is also hashed by every consumer. A search, the unattributed filter or any narrowing filter keeps the full projection. Same ids, order, total and flags either way (live test on a throwaway database).
  - Unpriced-model metadata (`metadata.unpriced`, `catalog_source`) keeps its scope: the models of the page's rows for `start_time`, `ctx_per_call` and search; the whole filtered window for the cost sort and the framework filter. A model is unpriced by the `CatalogPricer.price` rule (positive tokens in some kind and no catalog entry, or a missing rate for a token kind it used). *Changed 2026-11-06 (MR review CR-002, CR-005): an uncatalogued model used to be unpriced on any non-zero token count, a negative sum included; `price()` now counts positive tokens only, as its catalogued branch and the SQL flags (`bool_or(tokens > 0)`) do. `price()` is shared, so the rule applies to every `CatalogPricer` caller, the Cost and Efficiency views included (AC17); served `cost_usd`, `cost_available` and `bloat_pct` do not change, and `metadata.unpriced` differs from before only when every kind sum of an uncatalogued model is at most zero and one is negative, which ingest does not store.*
  - A Sessions request holds one analytics connection for its window statements and at most two for its detail statements (`CliAnalyticsReader.bounded()` takes the first and runs statements one after another; `widened()` adds a second around the detail statements only, so at most two statements run at once; both are released before pricing and row building). The window statements are the long ones and run one after another, so the request does not hold an idle second connection through them. The second connection is waited for only 0.5 s; if the pool has none free the details run on the one connection the request has, so requests that each hold one connection cannot deadlock a nearly exhausted pool. Other endpoints keep their own acquires.
- `cost_daily.cost_usd` and `session_dims.source_cost_usd` hold the producer's cost (Claude Code's OTel `cost_usd`); they are stored and not used for money.

Limitations:

- All history is priced at today's catalog; a price change reprices every day.
- Days without a 5m / 1h split (clients before the split, days older than raw retention) price 1h writes at the 5m price.
- Days older than raw retention are not recomputed: they keep their stored rollups.
- COST differs from Claude Code `/cost`, which uses Anthropic's base prices, not the catalog's.
- A request with web search is charged above its token price; the surcharge is in no event and not in the data.
- Accepted residuals of totals-only subagents: KPI, model-breakdown and users token counts and the dispatch cost do not include totals rows, and the hourly views omit them.

## Operations

| Task | How |
|---|---|
| Schema | Migrated at startup in the background (the API does not wait); a failed migration is retried by the next refresh job. A pod waits up to 2 minutes for another pod's migration, but never at shutdown |
| Jobs | Rollup refresh and maintenance run on one pod at a time (advisory locks); `max_instances=1`, late runs are not dropped |
| Backfill or repair rollups | `python -m codemie.repository.cli_analytics.postgres.backfill --from YYYY-MM-DD --to YYYY-MM-DD [--now]`: re-derives the kind of rows stored before their name was mapped in `vocabulary.py`, then queues the range for the refresh job (`--now` rebuilds it in the command). Each raw source queues the bits its records mark at ingest: `usage_requests` 1, 16, 32 (+ the neighbouring day within 1 h of midnight); `log_events` 1, 32 (+16 for `api_request`, + the neighbouring day within 1 h of midnight with a `request_id`, within 5 s without; +4 for `user_prompt`, `api_request` and `api_error`, also 4 (and 32 with a session id) on the neighbouring day within 1 h of midnight); `hook_events` 2, 32 (+4 for the six fallback hook types, also on the day of `ts - 1 h`; `agent.prompt.submit` also 4 on both neighbouring days within 1 h of midnight; +4 on the neighbouring day for a skill initiator within 1 h of midnight; +4 on the day before for an `Agent` / `Skill` `agent.tool.end` / `agent.tool.error` of any client, at any time of day, so an event on the day after the range marks its last day; +4 on the next day for an `Agent` / `Skill` `agent.tool.end` / `agent.tool.error` at most 1 h before midnight; +4 on the day of every later start of the same `agent_id` for an `agent.subagent.start` with a non-empty `agent_id`; +16 for `agent.subagent.usage`; +8 for an `agent.tool.end` carrying a numeric `lines_added`); `spans` 4, 32 (tool, execution and interaction spans also 4 on the day of `ts - 1 h`; an execution span also 4 on the day before, at any time of day, and on the next day at most 1 h before midnight; a Skill tool span also 4 on the neighbouring day within 1 h of midnight); `metric_points` 8, 32; intersected with the requested mask. No day older than raw retention is queued, neighbouring days included. The reported count is per one-day statement, so a neighbour day queued by two statements counts twice. A row created by `--now` has `delivery_framework` NULL until the refresher recomputes it |
| Alert on | WARNING `rollup queue has N keys, the oldest waiting Ns` (repeats every 5 min while stale); WARNING `recomputing rollup key ... timed out (N of 3 in a row); it is retried in N minutes`; ERROR `dropped rollup key`; ERROR `maintenance step ... failed`, `cannot create partition`, `purging expired rows of ... failed` (for sessions, a statement timeout on every run means the first batch counts more child rows than the timeout allows: lower `CLI_ANALYTICS_SESSION_PURGE_BATCH_SIZE`); ERROR `the session purge skipped N idle sessions whose rows another transaction holds` (a held child row or a held `session_dims` row; names up to 10 ids; repeating on every run means a transaction outside the code holds them); ERROR `could not count the idle sessions the session purge left`; ERROR `the session purge stopped: a batch of N idle sessions ... deleted none and skipped none`; WARNING `rows outside every planned partition`; WARNING `dropped a telemetry record PostgreSQL rejects`; WARNING `a request holds more records PostgreSQL rejects than one attempt isolates`; ERROR `cannot drop expired partition`; ERROR `the configured analytics storage cannot be used` (startup) |
| Retention | Whole partitions are dropped; DEFAULT partitions, `session_skills` (rollup retention), `session_attributes` and OTel resources (raw retention) are purged by date. `session_dims` is not on rollup retention: with `CLI_ANALYTICS_SESSION_RETENTION_DAYS` = 0 it is kept. Above 0 the maintenance job first deletes whole sessions whose `coalesce(greatest(last_event_at, ended_at), updated_at)` is before the midnight-UTC cutoff, in batches: each statement takes up to `CLI_ANALYTICS_SESSION_PURGE_BATCH_SIZE` idle sessions and deletes those whose child rows (`session_usage`, `session_usage_hourly`, `subagent_invocations`) add up to at most 100 000, each with its `session_dims` row and all its child rows in the same statement. Child rows are reached per session through the primary key, so a statement grows with the child rows of its candidates (each counted up to the row cap + 1 per table), not with the size of the child tables; a batch size is lowered only after a batch succeeds, so a first batch too heavy for the statement timeout fails the same way on every run until the setting is lowered. Each statement is its own transaction with a 2 s `lock_timeout` beside the statement timeout; the batches go on until one finds no idle session left. The purge never waits for a row lock: a session with a row another transaction holds in any of the three child tables is skipped whole, left out of the rest of the run and logged, and a later run takes it once released; a held `session_dims` row is skipped by `SKIP LOCKED`, then found by one plain count (no lock) of the idle sessions left after the batches and parts, and logged in the same skipped-sessions ERROR; the count runs only after a purge that ended normally, not after a failed statement or the "deleted none and skipped none" stop, whose sessions left were never tried; it leaves out rows whose `updated_at` is after the purge started, since the rollup refresher can re-create or update an old session's `session_dims` row during the run, idle but held by nobody, while a row actually held keeps its earlier committed `updated_at`; the refresher sets `updated_at` to its transaction's start, so a refresher transaction already open when the purge started can still put such a row in the skipped ERROR once, and the next run no longer reports it; a count that fails is logged and is not a purge failure; a session another transaction changed meanwhile is tested again and kept whole when it is no longer idle. A session loses its `session_dims` row only when every child row counted for it was actually deleted; one whose child row another transaction changed during the statement keeps its `session_dims` row, is logged with the skipped sessions and is finished by a later run. A session with more than 100 000 child rows is deleted after the batches, in parts of up to 100 000 child rows per transaction, its `session_dims` row last, so it exists partly between its parts; if it turns active between parts it keeps what is left, and the rows already deleted are older than the raw retention, so the refresher cannot rebuild them. A statement that fails (a timeout, a lock timeout, a deadlock) ends the run's session purge: the batches and parts before it stay deleted and the next run continues. Batches take sessions in no particular order: an index on the idle time would cost HOT updates of `session_dims` on every rollup update of an active session, and without one an age order needs a full scan per batch. Then rows of those three tables with no `session_dims` row are deleted by their own date (`day`, `hour`, `coalesce(ended_at, started_at)`; a subagent row with no date is kept). `last_event_at`, `ended_at` and a subagent's dates come from the client: a value after today (UTC, by the maintainer's clock) is ignored, so a wrong client clock cannot keep a row past its retention |
| Index and activity-facts runbook (revision `a1c1a0000011`: the columns, then the indexes: columns `has_activity`, `last_activity_day`, `resumed` and indexes `session_dims_started_at`, `session_dims_started_shared`, `session_dims_active_started`, `session_dims_active_shared_cov`, `session_dims_resumed_last`, `session_dims_activity_pending`; `session_activity.py`) | **Schema.** One revision, `a1c1a0000011`, in two steps with a commit between them (`run_migrations` runs each revision on its own connection, with a session-level advisory lock that outlives that commit): it adds the three columns (nullable, no default: no rewrite, NULL reads as not derived) under a 5 s `lock_timeout`, commits them (`op.get_bind().commit()`), then creates the six indexes with plain `CREATE INDEX IF NOT EXISTS` under a single 5 s `lock_timeout` (then restores the runner's value). The columns are what every Sessions reader needs, so they are committed first: a lock timeout of the index builds rolls back the indexes alone, the revision is not recorded, the next job runs it again (both steps are idempotent), and meanwhile the lists are correct and only slower (NULL facts are asked of the tables). Before the columns have been committed (a new pod ahead of the migration, which runs in the background) the readers still fail with a missing column, for the seconds that step takes. The columns' `ALTER TABLE` holds an ACCESS EXCLUSIVE lock for an instant; the index builds' SHARE lock, held to the revision's commit (11.4 s on 1.9M rows, measured below), blocks **writers** (the ingest session binding, rollup batches) but not readers. This is why the pre-build below is still required above the threshold: with the six indexes built beforehand (`CONCURRENTLY`), the revision's statements find them and hold the lock for an instant. **Build time.** Measured 2026-11-05 on a disposable copy of the dev `session_dims` (1.9M rows, noisy host, one run, `scripts/cli_analytics_bench/index_build_bench.py`) for the first three indexes in one transaction: 0.5 s SHARE-lock wait, builds of 4.1 + 3.2 + 2.8 s, lock held **10.0 s**, ingest bindings blocked up to 10.6 s answered 503 after their 1 s acquire timeout. **Measured 2026-11-06** with the updated script (`all_six`) on a disposable copy of the dev `session_dims` (1.9M rows, writers running, the host calmer than on 2026-11-05, one run; the copy already held derived facts, so the three fact indexes were built over populated data and `session_dims_activity_pending` over an empty set; at migration time the first three are empty and the last holds every row, which brackets the same total): the six builds in one transaction wait 2.7 s for the SHARE lock, build for 2.6 + 1.8 + 2.6 + 3.3 + 0.7 + 0.5 s and hold the lock for **11.4 s**; ingest bindings blocked behind it waited up to **14.0 s** (single-index runs: lock holds 0.9 to 4.2 s, waits up to 5.9 s) and answer 503 after their 1 s acquire timeout (plugins retry). Scaled linearly (about 6 s per million rows) the hold stays below the 1 s acquire timeout of ingest bindings up to about 165,000 rows, so the threshold is 150,000 rows (the same hold is the time dashboards reading `session_dims` wait, so a larger table also stalls the dashboards for the build) (`bench/ac18-index-build-six.local.json`); the figures are one run on one host, re-measure on production-sized data. **Required above 150,000 `session_dims` rows:** pre-build all six before the deploy with `CREATE INDEX CONCURRENTLY <name> ON session_dims (...) [INCLUDE (session_id)] WHERE <predicate>`, under the same names and with the migration's own definitions (`CREATE_*` in the revision file); the migration then finds them and does nothing (`IF NOT EXISTS`). The columns need no pre-build (the first step of revision `a1c1a0000011` adds them in an instant). Check `SELECT indisvalid FROM pg_index WHERE indexrelid = '<name>'::regclass` for each: a failed CONCURRENTLY build leaves an invalid index of that name; the migration drops an invalid one itself before its `CREATE INDEX IF NOT EXISTS`, and a manual `DROP INDEX CONCURRENTLY` before the deploy (then build again) avoids the plain rebuild's lock. Without the pre-build above the threshold, a lock wait past 5 s fails the migration, which leaves the schema not ready: the refresher on that pod pauses and the next job repeats the attempt every tick. Symptom: a repeating `lock timeout` migration failure in the logs and stale rollups (`rollup queue has N keys`). **Write cost.** The predicates' columns (`subscription_type`, `project_origin`) are written once, at session binding; the facts are written by the refresher once per session and again only when its activity days change, a non-HOT update (they are indexed); `session_id`, the INCLUDE column, is the primary key. **Roll-out of the facts.** Sessions that existed before the revision are NULL until derived. **Nothing is run by hand**: the maintenance job derives them, oldest first, `FOR UPDATE SKIP LOCKED` (two pods never take the same ones), 5,000 sessions per transaction. A run works 120 s; while more than 50,000 sessions still lack their facts (right after the deployment) it works up to 600 s, so a large database is derived in a few hourly runs and the budget falls back to 120 s when the backlog is small (the count it takes is capped at 50,001 rows). Until a session is derived the Sessions list is exact but pays the old per-session probes for it, so on a large database the first hours after the deployment are slow for the oldest underived sessions first; `CLI_ANALYTICS_MAINTENANCE_INTERVAL_MINUTES` can be lowered during the rollout to shorten that. Measured on the dev database (1.9M sessions, loaded host): a loop of the same step derived the last 1.06M sessions in 854 s, about 1,200 a second. check progress with `SELECT count(*) FROM session_dims WHERE has_activity IS NULL`. Each pre-existing row is updated once (non-HOT), so a 1.9M-row table roughly doubles on disk until vacuum: run `VACUUM (ANALYZE) session_dims` when the count reaches 0 (17 s on the dev table). A session written outside the refresher (an ingest binding) stays NULL until the refresh or maintenance job derives it. **Rollback.** The revision's downgrade drops the indexes, then the columns; the previous code ignores the columns. **A database that already ran an earlier revision of this branch** (an earlier `a1c1a0000010`, `a1c1a0000011` or `a1c1a0000012` of this MR, renumbered after the rebase onto `main`'s own `a1c1a0000010`; the revision is stamped, so Alembic does not run it again, or cannot find it) may have neither the columns nor the later indexes: apply the migration's statements by hand (`ADD_COLUMNS`, the missing `CREATE_*`; `CONCURRENTLY` above the size threshold), drop `session_dims_started_shared_cov` if it exists (the revision no longer creates it: `session_dims_active_shared_cov` supersedes it), then `VACUUM (ANALYZE) session_dims` so the pages are marked all-visible and the planner takes an Index Only Scan |
| Rejected data | A record PostgreSQL rejects is dropped, logged and entered in the ledger (a re-send skips it); the rest of its request is stored and the answer is 200 with OTLP `partial_success`. Past 64 failed attempts in one request the answer is 503 and the plugin's re-send carries on |
| Slow rollup keys | A batch past the 5-minute limit has its keys flagged `alone` in `rollup_dirty` and taken one at a time by any pod; a key timing out alone is retried after 10, then 20 minutes and dropped at the third timeout in a row |
