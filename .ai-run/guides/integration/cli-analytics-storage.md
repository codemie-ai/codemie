# CLI Analytics Storage

OTel telemetry from coding agents, sent by CodeMie CLI (formerly the sdlc-analytics plugin): Claude Code OTLP plus hook events, is stored in PostgreSQL, the only storage engine, behind the ports of `codemie.repository.cli_analytics`. The dashboards are served under `/v1/analytics/cli-analytics/*`.

OTel stays a data source, decoded inside the API: the OTLP endpoints of the API ingest directly, and a background job refreshes the rollups. There is no Collector and no second database; the analytics tables live in the application's PostgreSQL by default (see PostgreSQL Settings). Local stack: `docker compose up -d codemie postgres`.

The analytics role needs DDL on its schema, DML on its tables and `TEMPORARY` on the database (PUBLIC has it by default; the refresher stages its keys in a temporary table). A DBA may create the schema for it; the role then needs no `CREATE` on the database.

## Window Semantics

On the PostgreSQL reader a session is in a date window if `session_dims.started_at` is in `[start_dt, end_dt]` (inclusive, bounds truncated to ms) AND the session has ever produced at least one `turns_daily`, `tool_facts_daily`, `cost_daily`, `session_usage` or `lines_daily` row on or after the window's first UTC day and, for a window of a day or less that does not cover its days whole, a raw real-work record stamped inside `[start_dt, end_dt]` (`_activity_from_window_start`), OR it has activity inside the window (`_active_in_window`): one of those same five rows on a UTC day wholly inside `[start_dt, end_dt]`, or one on a day the window covers only in part together with a raw activity record stamped inside `[start_dt, end_dt]`. The predicate lives once, in `_sessions_cte` (`sel`); every windowed fact query scopes or inner-joins to `sel` and carries no day, timestamp or hour predicate of its own, so an in-window session contributes all its data whatever the fact's own day, and a session that is out of the window on both halves of the predicate contributes nothing. Sessions without `started_at` are excluded. Session-detail and skill-name lookups keyed by `session_id` are not windowed.

This is a hybrid, not a pure activity check: a session whose `started_at` falls inside `[start_dt, end_dt]` keeps the exact sub-day window-boundary precision earlier design decisions depend on, as long as it has produced at least one real signal on or after the window's first UTC day — `_activity_from_window_start` gates that arm so a session that only ever got `session.start`/`session.env` hooks is excluded from `sel` entirely, not merely flagged, and so is a session whose only activity lies before the window and whose start was moved into it by a reopen that did nothing (the first run had left no dimension hook, so the reopen's `agent.session.start` became `started_at`), whether that activity is on an earlier day or earlier the same UTC day: a day row says only the day, so a raw real-work record stamped between `start_dt` and `end_dt` must confirm it (`_real_work_from_window_start`); work after the window's end does not count, so a session started at 10:00 whose only prompt is at 11:00 is not in a 10:00–10:30 window (EPMCDME-16496 AC4 review). That confirmation applies to a window of a day or less that does not cover its days whole (Last hour, Last 6 hours, Last 24 hours, Today, a custom time range) and that starts inside the raw retention: a window that starts before `CLI_ANALYTICS_RAW_RETENTION_DAYS` ago asks for no raw record (they may be purged), and the day rows decide, as for a longer window. A longer window (Last 7 days, a custom range) keeps the day-granular rule: a session whose last real work was earlier on the window's first day and that was then reopened idle is still listed for it (accepted risk R19). A raw check there would drop sessions whose raw rows are past retention and add five probes per candidate to the default list; closing it needs the exact last real-activity time stored on `session_dims`. The second half (`_active_in_window`) only *additionally* rescues a session whose `started_at` is outside the window but has fresh activity in it — an old session resumed with no new activity in the window stays excluded, one resumed with fresh activity is included. A day row has no time of day, so it decides alone only for a UTC day wholly inside the window (from `_FIRST_WHOLE_DAY_UTC` to `_LAST_WHOLE_DAY_UTC`). For a day the window covers only in part (every day of a Last hour, Last 6 hours or Last 24 hours window, today in Last 7 days, both ends of a custom range) the session also needs a raw activity record stamped inside the window (`_raw_activity_in_window`): an `agent.prompt.submit`, `agent.session.stop`, `agent.turn.error`, `agent.tool.*`, `agent.subagent.*` or `agent.skill.dispatch` hook, any `usage_requests` row, an OTel log record that is not a startup record, a built-in command (`BUILTIN_COMMAND_NAMES`) or a command prompt such as `/cost` or `/status` with no model request on its span, a span of a known kind (an interaction span counts only with a model request or a typed prompt on its own span: the span of a local command, one exported before its records and one whose command record carries no span id do not), or a lines-of-code metric point: the same real-work definition that ends a session (`real_work_sql.real_work_filter`). Lifecycle hooks (`session.start`, `session.env`, `session.end`, `git.snapshot`, summary) are not activity, so a same-day `--resume` with nothing typed is not listed for a window that holds only those hooks, and a session that started after a sub-day window is not listed for it. The raw check is an AND on top of the day row, so it can only narrow the day-row rule. Raw rows are kept for `CLI_ANALYTICS_RAW_RETENTION_DAYS` only: whole days keep the day-row rule for that reason, and a partial first day older than the raw retention admits nobody through this arm — except a session that started inside the window but continued past its start day (arm 6, and arm 2's live-resumed branch, `_SESSION_ADMITTED_IN_WINDOW`'s other use of `_active_in_window`), where `_active_in_window`'s `resumed_bypass` lets the day row decide alone once the window predates the retention, the same way `_no_raw_check_needed` already does for the `_STARTED_IN_WINDOW` gate: that cohort's pre-fix check had no raw dependency at all, so a purged raw record must not drop it either. A session whose `started_at` is outside the window keeps the plain raw requirement regardless of the window's age. The raw checks use the `(session_id, ts)` index of each raw table. A finer check would mean reading these raw tables for every admission decision instead of the day-partitioned rollups, which exist specifically to avoid that scan cost, so it is left as-is unless a future ticket asks for it explicitly.

**Sub-agent sessions:** a Copilot client forwards the sub-agent's session id as `agent_id` of the parent's `agent.subagent.start`. The rollup sets `session_dims.is_subagent` from that event (one rule, `hook_row_sql.names_subagent_session`: a Copilot platform, a non-empty session of its own, an `agent_id` that is another session), and the session listing and every aggregate built on it leave such a session out unless it has `cost_daily` rows of its own. Its work is not counted under the parent: it is dropped from the session-level aggregates, and Session Detail by its id still opens. Claude Code sends the sub-agent's own short id under the parent's session, which is no session, so its start events flag nothing.

Six indexes serve the window, all from revision `a1c1a0000011` (which adds the columns they cover first): `session_dims_started_at` (`started_at`) and the partial `session_dims_started_shared` (`started_at` where the session is not owner-private, the scope of the shared list), which the readers that do not filter by activity use (the framework counts); and, over the stored activity facts below, `session_dims_active_started` (`started_at` where `has_activity`, the page of any scope), the covering `session_dims_active_shared_cov` (the shared predicate and `has_activity`, `INCLUDE (session_id)`: the unfiltered shared list's page, count and ids-only statements were index-only scans before arm (1) was bounded by `last_activity_day`, which this index does not hold: arm (1) now reads the heap, measured as 1,626 buffers instead of 63 for the ids-only count of a 7-day window over 100,000 sessions, equal time with a warm cache; re-measure at 10^6 sessions, or add `last_activity_day` to the `INCLUDE` list in a migration), `session_dims_resumed_last` (`last_activity_day` where `resumed`) and `session_dims_activity_pending` (`started_at` where `has_activity IS NULL`, empty once every session is derived). See *Index and activity-facts runbook* in Operations.

**Stored activity facts (EPMCDME-16427).** The rule above asks five rollup tables for each session; for ~10^6 sessions that is a scan of the window (a 30-day default page timed out). `session_dims` therefore stores `has_activity` (a row exists in any of the five tables), `last_activity_day` (the latest such day) and `resumed` (a row exists on a UTC day other than the session's start day), written by `session_activity.derive_session_activity` for every session of each rollup batch, in the batch's transaction, after the last rollup statement. `_admitted_arms` builds `sel` as five `UNION ALL` selects, each on its own index: (1) started in the window, `has_activity`, `last_activity_day` on or after the window's first UTC day and, for a window that does not cover its days whole, a raw real-work record inside the window; (2) started in the window, facts not derived (NULL), asking `_activity_from_window_start`; (3) started outside the window, facts NULL, asking `_active_in_window` as before; (4) started outside the window, `resumed`, with `last_activity_day` on or after the window's first UTC day, decided by the unchanged `_active_in_window` with per-row probes; (5) started outside the window, not `resumed` (all rows on the start day), with that start on the window's first day before it or on its last day after it, decided by `_active_in_window` with the raw records tested first. The unfiltered `start_time` page and count read arm (1) (`sel_main`) and arms (2) to (5) (`sel_rest`) separately: the page is the first rows of the ordered walk of arm (1) merged with the few rows of the rest, and the count is one count of arm (1) (index-only before it was bounded by `last_activity_day`) plus a count of the rest; every other reader reads `sel`, the union. A candidate filter can only narrow what the exact predicate sees, never widen it, and every session the predicate can admit is a candidate (a session with a day row in the window and a start outside it either has a row off its start day, so it is `resumed` with a last day in or after the window, or all its rows sit on its start day, which then lies on the window's first or last day). The fast-path callers of `sel` that read only ids (`ids_only`: the `ctx_per_call` sort, the framework filter, the cost-model list) use the same five arms. They read the window alone before this change, so a session with no activity was counted by them and not by the list; they now agree. The facts depend on the day rows of the five tables and on `session_dims.started_at`, and both are written only by the rollup refresher, which derives the facts of every session of the batch in the same transaction; the session binding (ingest) writes neither, so the facts cannot go stale behind a writer (`test_session_activity.py` guards the binding). NULL facts are "not derived yet" (a session that existed before the revision, or one written outside the refresher): the lists are exact at every point of the roll-out, and only slower for those sessions. The facts are kept at refresh time, so a session whose rollup rows all pass retention stays `has_activity` (**an accepted divergence from `_SESSION_ADMITTED_IN_WINDOW`, requester 2026-11-06:** for a window older than `CLI_ANALYTICS_ROLLUP_RETENTION_DAYS`, 365 days by default, a session that started in it stays admitted, with no data, where the rule would exclude it; the API caps the length of a window, not its age) (the session itself is purged by `CLI_ANALYTICS_SESSION_RETENTION_DAYS` when set); `resumed` follows the start day the refresh saw, and a start moved by a later refresh is re-derived with it.

The window decides membership only. The start, end and duration a session reports are its activity range (see Notes for a reader), which can begin before `started_at`: a session whose first OTel event precedes its first hook is still in the window of its `started_at`.

Overview's `total_sessions` (`get_cost_kpis`), per-developer `session_count`/`session_ids` (`get_users`) and per-developer-per-day activity (`get_users_daily_activity`) all count every session of `sel`, priced or not — the same costless-inclusive universe the Sessions list already uses via `get_session_cost_facts(..., include_costless=True)`. This replaces the earlier "D1 rule" that restricted all three to the `cost_daily`-only (priced) universe. `get_users_daily_activity`'s day bucket comes from a `UNION` across all five activity tables (not just `cost_daily`), so a costless session's day comes from whichever table it actually has a row in. `get_class_lists(f, "all")` (the subscription-type/project-origin breakdown merged into Overview's and Cost's KPIs) likewise covers every session of `sel`, not only ones with a `cost_daily` row.

`get_cost_kpis`'s `spend_sessions`/`total_cost_usd` and `get_users`'s `cost_usd` count only sessions with an actual `cost_daily` row: they read the `c` side of the `sel`/`cost_daily` LEFT JOIN, which is NULL for a costless session, so `count(DISTINCT c.session_id)` and `sum(c.cost_usd)` skip it. There is no billing-class exclusion on top of that any more: since EPMCDME-17260 every aggregate cost covers every selected session, Personal-paid included (`_spend(alias)` is gone), and the `personal_billed` buckets only split that total.

Every query that names a developer (`get_users`, `get_cost_by_user`, `get_users_daily_activity`, `get_session_cost_facts`, `get_users_last_active`) resolves it through the single `_DEVELOPER` constant: the session's own email, else its smallest non-empty `cost_daily` email, else its smallest non-empty `lines_daily` email, else `'unknown'`. The expression is self-contained (its own correlated subqueries against `s.session_id`), not borrowed from whatever `c`/`d` alias happens to be in scope, specifically so every one of those callers agrees on a costless session's developer the same way instead of silently diverging per query. `get_users`' leaderboard `ORDER BY cost_usd DESC NULLS LAST` matches `_TOP_MODEL`'s own `DESC NULLS LAST` pattern a few lines above it: Postgres defaults `DESC` to `NULLS FIRST`, which would otherwise sort every costless developer (`cost_usd` NULL after the `RIGHT JOIN sel s` widening) above every priced one.

A session admitted to `sel` only through activity (no cost row at all) needs at least one row in one of the five `_ACTIVITY_TABLES` to be admitted at all (see `_activity_from_window_start` above) — a live-Postgres test fixture that seeds only `session_dims` (no rollup row of any kind) represents a true zero-activity session per gap (b), not a costless-but-active one, and is now excluded from every list/aggregate, including a session's own owner's private view.

**Scan cost of the admission rule:** the `OR` of the rule (`_STARTED_IN_WINDOW` vs. `_active_in_window`) made Postgres run up to ten correlated EXISTS per `session_dims` row, five with no day bound, and no index could prune rows before them; on the dev data (1.9M sessions, ~949K started in 30 days) the default sort and the count timed out after the rule landed on `main`. The stored activity facts above replace the five unbounded probes with one indexed column and confine the day probes to a candidate set that is small whenever sessions mostly end on their start day (a continued session is the rare case). The candidate filter is not a pre-filter on the rule's meaning: the rule is still evaluated, unchanged, on every candidate. Measured 2026-11-06 on the dev database (1.9M sessions, ~947K started in the 30-day window, every session derived, `VACUUM (ANALYZE)` run), through the running API on a loaded host (load average 15-24): `GET /sessions?per_page=20&sort_by=start_time` answered 200 in 0.16 s for 7 days and 0.46 s for 30 days (0.79 s on the second default-window call, 3.3 s on a cold first one); before the facts, the same request timed out at the 30 s statement timeout. In the plan the started arm's page is an ordered walk of `session_dims_active_shared_cov` (about 0.2 ms for 20 rows) and its count an index-only scan (both measured before arm (1) was bounded by `last_activity_day`); what remains is the exact check of the sessions that started earlier on the window's first day (about 10,600 here, per-row probes). The dev data has few continued sessions (10 `resumed`), so the resumed arm is a lower bound. Single runs: use `scripts/cli_analytics_bench/run_sessions_bench.py` for a quiet-host figure. The section 6.6 latency budget (825 ms per endpoint) is met by the default sort when the window starts at 00:00 UTC (the presets); a window with a partial first day adds the exact check of that day's sessions (1.7 to 4 s here). The other sorts and the framework filter are above the statement timeout at 30 days: see *Final code, measured 2026-11-06* below.

**Known gap, out of scope by the plan — fact values are not period-clipped:** `_scope` (shared by Overview, Cost, Users, Sessions, Efficiency, the repositories view and the heatmap) carries no day bound at all — once a session is admitted to `sel` for a window, every fact query sums or reads that session's entire lifetime of rows, not just the rows inside the viewed window. The plan is explicit that this task changes session *membership* only, fact *values* stay all-time sums ("list row numbers are NOT period-clipped"), so this is a known, deliberate limitation carried over from the original design, not a gap this ticket's comments ask to close. This is not only an inflated-totals issue: `get_users_daily_activity`, `get_lines_daily` and `get_class_lists(f, "day")` read their day bucket the same unbounded, session-scoped way (`_scope`, no day filter), so a day-bucketed chart for a short window (e.g. "Last 7 days") can render a bucket for a day outside that range whenever an admitted session's unrelated activity happens to fall there — not just a wrong number on an otherwise-correct axis, but an out-of-range axis entry. Clipping fact values (or at minimum these day buckets) to the window touches the day bound of every query `_scope` feeds and was explicitly scoped out of this round; it needs its own task.

The section 6.6 latency budget (825 ms per endpoint) was measured for the Sessions list on the 1.9M-row dev database (about 950K sessions in a 30-day window; see *Known performance limits* and *Final code, measured 2026-11-06* there); the other whole-session scans were not re-measured.

### Project policy (per-project ingest gate)

Whether a project's analytics is stored is a flag in the main database, not in the analytics database: `applications.cli_analytics_enabled` (NOT NULL, default `false`). The migration therefore turns ingestion off for every existing project until a global administrator or maintainer enables the pilot projects; enable them only after their CLI versions send `X-CodeMie-Project`. The gate is `codemie.service.analytics.cli_analytics_project_gate.build_ingest_gate`: the router builds it per request and hands it to the ingestor as a callable, because the adapter may not import `codemie.service`. The ingestor decodes once, calls the gate with the explicit project values and the wire count the decoder collected, and on a discard returns before `_store`, so a discarded request writes no raw rows, resources, dedup entries or rollup work. The reasons, answers and counting rules are in [`cli-analytics-events.md`](cli-analytics-events.md#project-gate).

The setting is visible in the project API (`cli_analytics_enabled` on list, detail, create and PATCH) only to global administrators and maintainers and to the Project Admin of that project; for everyone else the key is absent. Only a global administrator or maintainer may write it: any request body that contains the field from someone else, even `null` or an unchanged value, is 403 before anything is applied. Personal projects stay `false`.

Gate discards are visible as one INFO log line per discarded request (`codemie.repository.cli_analytics.gate_discards`) with route (`otlp` / `hooks`), reason code, dropped record count, `session_count` (distinct non-empty session ids of the kept records), `session_ids` and, when `CLI_ANALYTICS_LOG_HMAC_KEY` is set, `user_hash` (first 16 hex characters of HMAC-SHA256 of the user id, computed only when a discard is recorded: the gate's `user_hash` property, part of the `IngestGate` protocol). A discard of a request with zero records is logged too (`dropped=0 session_count=0`, no `session_ids`). `session_ids` appears only when `session_count` is above 0 and is a sample: at most 3 ids, each with every whitespace or non-printable character replaced by `?` and cut to 64 characters, de-duplicated after sanitizing and sorted; `session_count` counts the raw ids, so two ids that sanitize alike count twice and show once. Limitations: the count undercounts records that carry no session id, metric point types the decoder does not keep and hook events dropped for `RecursionError`; an id is client-supplied text and may embed sensitive text, so treat the line like any application log; an id containing `,` or `=` still stays one bounded line, so grep the line and do not parse it. The HTTP answer is unchanged. The key defaults to empty: until it is set, no `user_hash` field appears in the discard log. Rollout: set `CLI_ANALYTICS_LOG_HMAC_KEY` per environment (a secret, different from `MCP_AUTH_HMAC_SECRET`); changing it changes every hash. The log never carries an email, a project name or a raw user id, and the hash is a log field only, never a metric label. `CLI_ANALYTICS_LOG_HMAC_KEY` is separate from `MCP_AUTH_HMAC_SECRET`.

### Deduplication by `event_id`

- With a non-empty `event_id` the record hash is over (type, session key, event_id) on both paths, so a re-send is recognised whatever the sender's email and two sessions sharing an `event_id` are both kept. The first stored version stays: a changed event, a new summary for one, must carry a new `event_id`. Without one, the old content hash applies.
- The ledger key is `(day, h)` and is kept `CLI_ANALYTICS_DEDUP_RETENTION_DAYS` (14) days: a repeat is dropped when it carries the same UTC day and arrives inside that window.
- On OTLP, a record with an `event_id`, and any `agent.usage.request`, takes `ts` from its `timestamp` attribute (record time when absent or unparseable), as `/event-hooks` does.

### Rollup families 16 and 32

`RollupFamily` gains `USAGE_FACTS = 16` and `SESSION = 32` (`rollup_dirty.kinds` is an integer: no migration).

| Record | New bits |
|---|---|
| `usage_requests` row | `USAGE_FACTS`, plus `LOG_FACTS`; `SESSION` when the session id is non-empty; never `DIMENSIONS` |
| OTel `api_request` | `USAGE_FACTS` on the key of its `LOG_FACTS` |
| OTel `user_prompt`, `api_request`, `api_error` | `SPAN_FACTS` (plus `SESSION` with a session id), on its own day and on the neighbouring day within 1 hour of midnight |
| `hook_events` row of type `agent.prompt.submit` | `SPAN_FACTS` on its own day and on both neighbouring days within 1 hour of midnight |
| `hook_events` row of type `agent.subagent.usage` | `USAGE_FACTS` |
| Any log, hook, span or metric record with a session id | `SESSION` |

- Midnight rule (marking): a `usage_requests` row at most 1 hour after 00:00:00 UTC also marks the previous day, and at most 1 hour before the next midnight the next day, with bits 1, 16 and 32 (`USAGE_REQUEST_REACH` in `dirty.py`, one constant shared with the recompute). An OTel `api_request` with a non-empty `request_id` marks the neighbouring day within the same 1 hour with the bits of its own day (1, 16 and 32 when the session id is non-empty); without a `request_id` it does so only within 5 seconds; this 5 s / 1 h reach is the usage rule. For turns, an OTel `user_prompt`, `api_request` or `api_error` marks `SPAN_FACTS` (plus `SESSION` with a session id) on the neighbouring day within 1 hour of midnight on either side, and an `agent.prompt.submit` hook marks `SPAN_FACTS` on both neighbouring days within 1 hour: a request or an auto-prompt hook that arrives later re-counts the turn of a span on the other side of midnight. A skill initiator hook event (`agent.skill.dispatch`, a Skill `agent.tool.start` / `agent.tool.end`) and a Skill `TOOL` span within the same 1 hour also mark the neighbouring day with bit 4: a fork may start on the next day. Both bounds are inclusive. An `agent.tool.end` / `agent.tool.error` of an `Agent` or `Skill` call of any client, and a `TOOL_EXECUTION` span, also mark the day before with bit 4, at any time of day: the evidence of a call, and a fork's initiator, may arrive up to 1 day later. A `TOOL_EXECUTION` span and an `Agent` or `Skill` `agent.tool.end` / `agent.tool.error` at most 1 hour before the next midnight also mark the next day with bit 4: the evidence of a call may lie up to 1 hour before it. An `agent.subagent.start` with a non-empty `agent_id` also marks with bit 4 the day of every later start of the same `agent_id` in the session: only the first start counts, so a first start that arrives late undoes a later one's count. Ingest runs this lookup, and the one of the own day of the fork or agent an `Agent` / `Skill` `agent.tool.end` names, after the batch's rows are inserted and under a transaction-scoped advisory lock per session of the batch (`pg_advisory_xact_lock`, keys sorted), so of two concurrent batches of one session the second waits for the first to commit and its lookups see the other's rows. An `agent.tool.end` carrying a numeric `lines_added` marks bit 8 on its own day; with a non-empty `tool_use_id` a lookup run the same way (after insert, under the same lock) also marks bit 8 on the day of every stored copy of the same `(session_id, tool_use_id)` carrying a numeric `lines_added` dated on another day: a call counts its lines once, by its earliest copy, so a copy dated earlier that arrives late moves the count off the later copy's day. When its session switches source with this batch (no such event of the session was stored before the batch; checked before the batch's rows are inserted), a lookup run the same way (after insert, under the same lock) also marks bit 8 on every day of the session that has `lines_daily` rows or lines metric points (`metric_points` of the lines metrics only; a day without them has no metric lines to replace), back to today minus `CLI_ANALYTICS_RAW_RETENTION_DAYS` (the cutoff the refresher drops keys by): the session's lines then come from its hook events on every day. A later batch of a session already on its hook events marks only its own day. A metric batch with a lines metric point takes the same per-session lock before it commits (other metric points take none), so a lines metric day committed after a hook batch's lookup is recomputed only once that hook batch has committed. An event dated on the first or the last day of the calendar (0001-01-01, 9999-12-31) marks its own day only.
- Request matching (recompute of day D): tier 1 pairs a transcript request with the OTel `api_request` of the same session and the same non-empty `request_id` (n-th with n-th in time order) when each record lies within 1 hour of the other one's UTC day, in both directions: on the same day anywhere, or across a midnight with both records within 1 hour of it. D therefore reads transcript requests whose latest line is in [D - 1 h, D + 1 day + 1 h) and OTel records in the same range. The matched row is written only on the transcript request's own day; the paired OTel record is not written on its own day as a service or OTel-only row, so a cost is never counted on two days. Tier 2 (fingerprint, no identifier) stays at 5 seconds: both records within the day widened by 5 s and at most 5 s apart. Tier 2 requires the input, output, cache-read and cache-write totals equal for every transcript request, a partial one included, so a partial request cannot take the exact match of a final one. Tier 3 handles the partial transcript requests (no `stop_reason` on a non-`is_api_error` request, positive output) and the OTel records that tiers 1 and 2 left unpaired: same session, the same UTC day (`a.t_day = b.o_day`), the OTel `model` equal to the transcript's raw model, both records within the day widened by 5 s, the OTel output at least the transcript output, at most 30 s apart (`_MATCH_PARTIAL`), and not both `request_id`s present. Input and cache totals are not required (Claude Desktop reports them differently). A main-thread transcript request (empty `agent_id`) is paired only with an OTel record whose `query_source` is empty, `repl_main_thread` or `sdk` (so never a `compact`, `generate_session_title` or `prompt_suggestion` side call, nor a subagent's record); a subagent request (non-empty `agent_id`) only with a record whose `query_source` is empty or starts with `agent:`. Tier 3 is resolved one to one like tier 2 and never takes a record paired by tier 1 or 2; each request takes the first free candidate by: input, cache-read and cache-write totals equal, then the transcript `agent_type` equal to the OTel `agent.name` or to the last `:` part of an `agent:` `query_source`, then the nearest gap (ties to the earlier OTel record). A final request, an `is_api_error` one and a partial one with a 0 or NULL output are never paired by tier 3. Known limits of tier 3: two subagents of one type running in parallel within 30 s can swap their OTel records (the session totals stay right, the per-agent attribution may shift); the main-vs-subagent filter does nothing when `query_source` is empty (Claude Desktop does not document it), where only the totals and the agent-name preference apply; a partial request and its OTel record on two sides of a midnight stay unpaired, so both days recompute to the same result. The lines of one transcript request are grouped across the same 1 hour reach, so a request straddling midnight is never counted on two days.
- Every family recomputes: bit 16 rebuilds `session_usage` and `session_usage_hourly`, bit 32 the new `session_dims` columns and `subagent_invocations`. The `SESSION` statements run for the session of every claimed key with bit 1, 4, 8 or 32, after the daily and hourly rollups and `DIMENSIONS`. A key holding only bit 32 for a session with no rollups runs without error.
- A day is recomputed only inside raw retention; older keys are dropped with a WARNING and their rollups are kept.

### Session tables

| Table | Key | Recomputed |
|---|---|---|
| `session_usage` | `session_id, day, model, speed, inference_geo, scope_kind, scope_name, agent_id` (`''` = unknown) | Per `(day, session)` by bit 16: delete the day's rows, insert from `usage_requests` and OTel `api_request` |
| `session_usage_hourly` | the same plus `hour` and `service_tier` | Same recompute, one row per hour of the request time; the hours of a day sum to its `session_usage` rows |
| `subagent_invocations` | `(session_id, agent_id)` | Bit 32, upserted; the latest `agent.subagent.usage` wins; `attribution` is `hook` or `heuristic` (only start/stop seen); a `duration_ms` computed from the two times is NULL when the end is before the start |
| `session_dims` (new columns) | `session_id` | Bit 32, merged into the stored row; `DIMENSIONS` (bit 2) keeps the columns of the initial schema |

- Subagent totals are read from the agent's latest `agent.subagent.usage` event that carries them (`usage` is an array with at least one object); a later event without them replaces nothing. They become `session_usage` rows only when the session has no `usage_requests` for that agent, no OTel `api_request` and no `session_usage` row of the session (any day, any `agent_id`) carrying `attrs.otel_requests`; otherwise they stay in `subagent_invocations.attrs`. They are never added to per-request rows and have no hourly rows. The last condition keeps the tokens from being counted twice once raw retention has purged the OTel records: a later recompute of the totals' day still sees the marker. The delete of stale totals rows uses the same predicate.
- `api_calls`, `web_search_requests` and `web_fetch_requests` of `session_usage` and `session_usage_hourly` are `int` columns. A sum that does not fit is stored as NULL, so the recompute of the key never fails on it.
- `attrs.otel_requests` on a `session_usage` row is the number of OTel `api_request` records that went into the row: matched rows, `service` rows and OTel-only rows. The key is present only when the number is above 0. It is not a `token_source` value: a matched row takes its tokens from the transcript and only its cost from OTel, except the output of a partial request (no `stop_reason` on a non-`is_api_error` request), which is `greatest(transcript, OTel)`. A partial request with a positive output that tiers 1 and 2 did not pair is paired with the OTel record of its model on the same UTC day within 30 s whatever the input and cache totals (tier 3, with the main-thread / subagent filter and the preference order described under request matching), so it is one request, not a transcript row plus a service row. A partial request with no such OTel record (including one across a midnight), or with a 0 or NULL output that tier 2 did not pair, keeps its transcript output as a lower bound.
- `session_dims` merge kinds (a NULL never overwrites a value):

| Kind | Rule |
|---|---|
| summary | Counters, lists, `title`, `ended_at`, `client_versions` and similar come from the latest `agent.session.summary`, written only when its `ts` is not older than the stored `summary_ts` |
| fallback | The same columns for a session with no summary, computed from raw rows; written only while `summary_ts` is NULL |
| priority | (`user_email`, `identity_source`) and (`story_id`, `story_source`) are replaced only by a higher rank, or the same rank and a later timestamp |
| latest value | Columns from `agent.session.env`, `agent.git.snapshot`, common fields and `session_attributes`: the latest non-empty value |
| latest session name | `session_title` is the latest non-empty `session_title` field of the session's events, trimmed of spaces, tabs, carriage returns, line feeds and no-break spaces (U+00A0) and cut to 200 characters; a blank value shadows nothing. It is a column of its own, never a key of `session_dims.attrs`, and is separate from the summary's AI-generated `title`, which is stored but not served. For a Desktop-hosted session (`entrypoint` one of `claude-desktop`, `claude-desktop-3p`, `local-agent`, `remote_cowork`), this merge rule is unchanged — `session_title` is still stored and merged the same way — but it is not used to build the served `prompt` (EPMCDME-17317) |
| accumulating | `sources`, fallback `client_versions` and `attrs` are merged with the stored value; an `attrs` key is never removed |
| rollup-derived | `active_ms`, `source_cost_usd`, `delivery_framework` (classified from skill names and subagent types), `feature_id` are recomputed each time |

- `tool_calls`, `tool_errors` and `tools` follow a stricter summary rule, because a fallback value includes subagent calls and a harvester adds the subagents' counts to a summary's. When a summary wins, a present value replaces the stored one (0 included); when the summary omits the field (absent, NULL, malformed or out of range), the stored value is kept only if the row carries `attrs.tool_counters = 'summary_only'`, else it becomes NULL. Every summary win writes that marker, a first insert of a session that already has a summary included (an older summary that loses never does), so on a marked row each of the three is a summary value or NULL. The marker is the compatibility signal: a harvester must add subagent counts only to a marked row, and treat an unmarked row (or a backend that never writes the marker) as not safe. Limits: a row stored before this rule has no marker even when `counters_source` is `summary` (the flag can sit on fallback values), so its next summary win NULLs the fields that summary omits, and its current values are not repaired. Repair is a backfill that marks the retained raw sessions dirty and recomputes them from the retained summary events (an equal `ts` wins); where raw summaries have expired, the per-field origin cannot be rebuilt and nothing is repaired. Deploy this backend before enabling the harvester, then backfill only the sessions that matter.
- When the stored `activity_started_at` is earlier than the earliest raw record now present (raw rows were purged), fallback columns sourced from raw rows keep their stored value.
- A `session_dims` row created by a backfill rebuild (`--now`) keeps `delivery_framework` NULL until the next recompute by the refresher: the command passes no classifier.

### Counter fallback

A `(day, session)` pair is a fallback pair when it has no span of kind `TOOL`, `TOOL_EXECUTION` or `INTERACTION`; the test is by kind, never by name. Its `turns_daily`, `tool_facts_daily`, `invocations_hourly` and `session_files_daily` rows are counted from `hook_events` (`agent.prompt.submit`, `agent.tool.start`/`end`/`error`, `agent.skill.dispatch`, `agent.subagent.start`); a pair with spans uses spans. Tool calls, turns, files and agents have one source per pair, never both. Skills are read from spans and hooks on every pair, and each skill invocation counts once: an `agent.tool.start` of a call that has a `TOOL` span is left out, and so is a forked skill's `agent.subagent.start` joined to a counted initiator. An `agent.subagent.start` counts once per `agent_id`, by the first start of that `agent_id` in the session: SendMessage continues an agent or a fork under its `agent_id` with a new start, which is no new invocation; a start with an empty `agent_id` counts on its own. Skill and agent counts therefore also read the fork a Skill call's hook `agent.tool.end` names (its `fork_agent_id`, else the complete `agentId` in `tool_response`; never the typed `agent_id`, which on a call made inside a subagent is the caller's) and `agent.skill.dispatch` `prompt_id` (a slash command's fork, only when the dispatch is the one of its `prompt_id`: a start of its skill name, else a foreground one without a skill name that no `Agent` call names), on any day of the session, a day with spans included; these fork rules read Claude Code events only (`platform` `claude-code` or absent). `turns_daily` counts every `agent.prompt.submit` except a Claude Code hook's (`platform` `claude-code` or absent) prompt starting with `<task-notification>` or `<agent-message`; an empty `prompt_body` still counts. `success` is an `agent.tool.end` with the same `tool_use_id`, counted on the day of the start. The reader has no fallback query of its own: it reads these rollups for the sessions of the window.

### Session prompt (`prompt` of the sessions list and the session detail)

The served `prompt` is the session's name when `session_dims.session_title` is non-empty after trimming; otherwise it is the first prompt, cleaned again at read time (`strip_pasted_content`: the `<pasted_content ...>` and `</pasted_content>` tags removed, the pasted text kept, trimmed of spaces, tabs, carriage returns, line feeds and no-break spaces (U+00A0) at both ends; the tag's attributes are complete quoted `name="value"` pairs separated by ASCII whitespace (`[ \t\n\r\f\v]`, never the locale-dependent `\s`); a tag cut off at the very end of the text is removed too, while a stray `<pasted_content` followed by prose is left in the text). The read-time cleaning serves a `first_prompt` stored with the tags clean even when its raw rows are past retention and cannot be recomputed. When the cleaned first prompt is empty (an old-CLI prompt cut inside the open tag), the served `prompt` is the session's repository, else its branch, else an empty string; the fallback order is title, cleaned first prompt, repository, branch — except for a Desktop-hosted session (`entrypoint` one of `claude-desktop`, `claude-desktop-3p`, `local-agent`, `remote_cowork`), whose `session_title` is Desktop's own auto-name rather than an explicit rename, so it is skipped entirely and the fallback starts at the cleaned first prompt (EPMCDME-17317). Efficiency's `worst_session_prompt` uses the same label (truncated to the preview length; `null` when it is empty). The search term of the sessions list is matched in SQL against the stored `first_prompt` (not cleaned at read time), the stored `session_title`, the repository and the branch; a session whose title is empty is found by its first prompt, which is also what it is served as — and a Desktop-hosted session's hidden title is excluded from that `session_title` match the same way, so search-by-title stays consistent with what the session list displays. The summary's `title` is stored in `session_dims`, not read, served or searched. `prompt_original` and `session_title` are not copied into `session_dims.attrs` (`session_title` has a column of its own); both stay in `hook_events.attrs` until raw retention (`otlp.py`, the event keys outside `HOOK_KNOWN_KEYS`), and search matches the stored first prompt, not the cleaned one (a pasted-content tag inside the stored prompt is searchable text).

### Slash commands (`get_invocations`, kind 4)

`slash_commands` of `/tools` has one source per session. Only the kind-4 branches of the PostgreSQL reader's `get_invocations` follow this rule.

| Session | Source |
|---|---|
| With a summary (`session_dims.summary_ts` is not NULL) | Every string element of `session_dims.commands`, each counting 1 (duplicates kept, names as stored, without a leading slash). Non-string and empty elements are skipped; an empty or NULL `commands` adds nothing. Its OTel `user_prompt` records (kind 4 of `invocations_hourly`) add nothing |
| Without a summary | `command_name` of its OTel `user_prompt` records, from `invocations_hourly`, as before |

The window is the shared one (see Window Semantics): a session whose `started_at` is in the window adds all its commands, whichever source they come from.

A command name the same session also ran as a skill (a kind-2 row of `invocations_hourly`: an `agent.skill.dispatch` or a Skill call) is not one of that session's slash commands. Both kind-4 branches skip it, so a skill started by a slash command is counted once, under `skills_invoked`, with its kind-2 count. The exclusion is per session: the same name typed as a plain command in another session still counts there, and a command with no kind-2 row in its own session stays a command. `get_class_lists` by invocation applies the same rule, so the per-row lists agree with the counts. Both statements read the skill and agent rows of `sel` once, into the CTE `skill_rows`, and the Skills branch and both exclusions read that CTE. Probing `invocations_hourly` for each command row instead visited every partition each time and made these two queries up to four times slower on a database of 2 million sessions and five years of history. No bound on `hour` is safe for the exclusion: a session that started before the window and was resumed in it has its skill row before the window's start.

| Case | Effect |
|---|---|
| A tool call starts before midnight and its `agent.tool.end` arrives after 01:00 in a later batch | `success` stays 0 on the start's day until that day is recomputed again; a full rebuild gives 1. The span path has the same gap. Hook and span marking are unchanged |
| Tier-1 request matching: a transcript request and its OTel `api_request` (same session, same `request_id`) are more than 1 hour apart around midnight, so one record is outside the 1 hour reach of the other's UTC day | The pair is not matched and a cost can be lost; it is never counted twice, because the matched OTel record is written only with its transcript request |
| A client version changes between batches and there is no summary | `client_versions` accumulates both incrementally and after a backfill over existing rows; a rebuild from an empty schema keeps only the latest |
| Hooks counted a tool call, then an `INTERACTION` span with no tool spans arrives | `tool_calls` keeps the hook value incrementally (a NULL never overwrites); a full rebuild gives NULL |
| A session known from hooks only | `get_session_detail_tools` shows no tools: it reads raw spans only |
| A session with a summary lists a skill in its `commands`, but no skill dispatch or Skill call of that name reached `invocations_hourly` (kind 2): an older client without `agent.skill.dispatch`, or events that did not arrive | The name stays one of the session's slash commands and is not counted under `skills_invoked`: the skills list reads the rollup only, so `session_dims.skills` does not move it. Accepted: such a session has no evidence of a skill run besides its summary |
| A summary, an identity or a story event dated in the future by a wrong client clock | It is the latest by its own time: later, correctly dated events of that session do not replace its values until real time passes that date. The recalculation never compares client times with the current time |

**Turn rule (`turns_daily`).** A turn is an interaction the user started that talks to the model: a typed
prompt, or a slash command that made a model request. Auto prompts are not turns. A `claude_code.interaction`
span counts unless one of three checks, applied in order, finds a row:

1. Auto prompt: a `user_prompt` log row (`event_kind = 2`) of the same session and `span_id` whose `prompt_id`
   is the `prompt_id` of a Claude Code `agent.prompt.submit` hook (`platform` `claude-code` or absent) whose
   `prompt_body` starts with `<task-notification>` or `<agent-message`
   (`vocabulary.CLAUDE_CODE_AUTO_PROMPT_PREFIXES`; leading space, tab, CR and LF are ignored; this turn rule keeps its own trim set, not the blank set above):
   the prompts Claude Code injects itself when a forked skill, background agent or background command finishes,
   and when a subagent hands its result back or a peer session sends a message. In OTel it looks like a typed
   prompt; only the hook tells them apart.
2. Command without a model request: a `user_prompt` row of the same session and `span_id` with a non-empty
   `command_name`, and no `api_request` (`event_kind = 1`) or `api_error` (`event_kind = 6`) row with the same
   `span_id`. The test applies to slash commands only: a typed prompt interrupted with Esc sends no request and
   is still a turn.
3. Injected message without a hook and a model request: on a Claude Code span (name starting `claude_code.`), a
   `user_prompt` row of the same session and `span_id` with a `prompt_id` and no `command_name`, no `api_request`
   or `api_error` row with the same `span_id`, no `agent.prompt.submit` hook with that `prompt_id`, while the
   session has an `agent.prompt.submit` hook carrying a `prompt_id` within 1 hour of the span's `ts` (the plugin
   is present). Claude Code injects a
   `<task-notification>` that fires no `UserPromptSubmit` hook and makes no model call, so the auto-prompt check
   cannot see it; a typed prompt fires its hook, so an Esc-interrupted one stays a turn. Another client's
   interaction span is not tested.

Every row is paired with the span within 1 hour of the span's `ts` on either side (`_CROSS_MIDNIGHT` in
`dirty.py`, the reach at which ingest marks a neighbouring day), and every lookup is bounded by `session_id`
and `ts`, so it reads the `(session_id, ts)` indexes of `log_events` and `hook_events`. The checks are
`NOT EXISTS`, so a duplicated `user_prompt` row cannot count a span twice. A fallback pair counts its
`agent.prompt.submit` hooks except Claude Code's `<task-notification>` and `<agent-message` ones: built-in slash commands fire no `UserPromptSubmit`
hook (checked on Claude Code 2.1.302 with `/model`, `/effort`, `/context`, `/cost`, `/help`, `/status`, `/mcp`,
`/clear`, `/compact` and `/exit`), so there is no command prompt to exclude there, while project and plugin skills
fire it and are turns. The texts Claude Code writes into the transcript itself — "This session is being continued
from a previous conversation…", "Caveat: The messages below were generated by the user while running local
commands", `<command-name>` and `<local-command-stdout>` wrappers — reach neither a `user_prompt` log nor the
prompt hook (checked after `/compact`, with `--continue` and with `--resume`), so they are never counted. Limits: a request more than 1 hour after its command is not seen, and the command is not
counted; without the plugin hooks an auto prompt or an injected message stays a turn; in a plugin session an
Esc-interrupted typed prompt whose hook is lost (or not yet delivered) is not a turn — a late hook re-counts its day.

**`ended_at`/`duration_ms` and a non-final summary.** `agent.session.summary` is sent on every Stop,
not only at `SessionEnd`, each one marked `is_final`. A **final** summary (`is_final: true`, or the
field absent — an older client never sent it, and absence keeps the pre-existing, final-wins
behavior) is authoritative outright: `ended_at`/`duration_ms` come from it alone, even if some
unrelated raw record lands later. A **provisional** summary (`is_final: false`, the shape every Stop
sends since codemie-code v0.15.9) is a lower bound, not the final word: `ended_at` is the *later* of
that summary's own `ended_at` and the session's latest real-work raw record, so a `SessionEnd` cancelled after
the last Stop (a normal `/exit`) does not truncate the stored duration back to that Stop. Tolerance:
once a final summary or a real `SessionEnd` is recorded, the value is exact to the transcript; while
only provisional summaries have been seen, the duration can still undercount by up to the gap between
the true exit and the latest raw record this session has sent so far. That gap narrows with the next
raw event or summary, whichever lands first, and closes outright once the real `SessionEnd` arrives —
**but if neither ever does** (the session goes idle after its last Stop and sends no further
telemetry of any kind, the normal-`/exit`-with-cancelled-`SessionEnd` shape this fix exists for), there
is no later event to narrow or close it: the undercount is not bounded by this mechanism at all and
the duration stays at the last Stop's timestamp indefinitely, the same as before this fix.

This stored `ended_at` is not the whole of the reported duration, and the two layers do not make each
other redundant. The reader derives what a dashboard shows from the activity range
(`greatest(last_event_at, ended_at, latest real-work log_events, latest real-work spans)`, see Window Semantics), so a
tail that lands in `log_events` or `spans` is recovered there even when the stored `ended_at` is cut
at a Stop. The reverse does not hold: those probes read those two tables only, and `last_event_at`
moves for the 11 real-work hook types (`ACTIVITY_HOOK_TYPES`) alone, so a tail that is a lifecycle hook
(`agent.git.snapshot`, which is sent *at the end of the session*), a `usage_requests` row or a
`metric_points` row is invisible to the reader. The fallback range behind `ended_at` spans all five
raw tables, so correcting it here is the only way those tails reach the reported duration — and
`ended_at` is itself one of the inputs to that `greatest(...)`.

**Notes for a reader.**

- Two pairs of times. `started_at` (the first of the 12 dimension hooks other than `agent.session.end`: a lone end, such as GitHub Copilot Chat's pre-warmed session that expires unused, does not start a session, and a start stored from one is replaced by the first start hook, `_MERGED_START`) and `last_event_at` (the last of the 11 real-work hooks: prompt, the stop or the error that closes a turn, tool, subagent, skill dispatch; never a start, end, compact, env, summary or git-snapshot hook) are hook times and decide the dashboard windows. `activity_started_at` and `ended_at` are the first and the last transcript line (the raw range in the fallback).
- The reported session range (EPMCDME-15506). The client stamps a hook after its own setup work, so an OTel `api_request` or tool span can precede the first hook or follow the last one. The reader reports start = `least(started_at, activity_started_at, earliest log_events / spans row)`, end = `greatest(last_event_at, ended_at, latest real-work log_events / spans row)`, and `duration_ms` = end − start: wall clock, idle time included. The end is the last real activity: a startup record (`event_kind` 0), a span of kind 0, a built-in command (`/exit`, `/model`, `/quit`) and the lifecycle hooks never move it, so a reopen that does nothing leaves a session's windows and duration as they were (the same list drives `ended_at`'s raw fallback). Rows stored before this rule keep the values they have: merges never shrink them. Every path looks for OTel rows only within one day of the column bounds, which prunes the other weekly partitions at run time, so the Sessions list and Session Detail always agree; a session without a `session_dims` row (Session Detail only), or without a stored end yet (not rolled up), has no column bound on that side and every row of it counts. The Sessions list, Session Detail, `get_session_durations` (Users Avg Session Duration, the Overview `duration_ms`) and the activity heatmap all report this range. `session_dims.duration_ms` is not read by them.
- `session_dims` counters describe the main thread. Tools, skills and commands of a subagent are in `subagent_invocations`.
- In `session_usage`, `agent_id = ''` is the main thread and `agent_id <> ''` a subagent. `scope_kind = 'service'` is a request Claude Code made outside the transcript (session title, compaction): it has tokens and cost and no counterpart in the counters. The rule is the missing transcript counterpart, never the value of `query_source`; values seen so far are `repl_main_thread`, `sdk`, `agent:builtin:<type>`, `generate_session_title` and `compact`.
- `model` is normalised, for a request known from OTel only by the plugin's steps, so a model has one name in every row apart from the dated / undated pair of a routed and an unrouted request described under `models`; fast mode and the inference region are in `speed` and `inference_geo`, not in the model name. `cost_daily.model_name` keeps the raw OTel name of a matched request and `model_raw` of a transcript-only one, except a Claude Code transcript request run on a LiteLLM route of its own model: its `model` (the plugin's copy of `x-litellm-model-name`) differs from `model_raw`, contains `/` and normalises to the same name as `model_raw` up to a trailing date (`routed_predicate`); such a request is keyed by that route. A request whose transcript lines name more than one route has no route and keeps the name above (`group_model`). Any other `model` (another client, Claude Code on a non-Claude deployment such as `azure/codemie-gpt-…`) keeps the name above.
- `source_cost_usd` is the cost OTel reported. A request known from the transcript only has NULL there (0 in `cost_daily`): price it from its tokens. A row built from OTel only has the cache-write total in `cache_creation_tokens` and the 5m / 1h split from the `api_request` attributes `cache_creation_5m_tokens` / `cache_creation_1h_tokens` when present, NULL otherwise. A matched request takes the cache-write total and split from its transcript; when the transcript has no split, it takes the OTel record's total and split instead, never one from each.
- The hours of a day in `session_usage_hourly` sum to the request-derived rows of `session_usage`. Rows with `attrs.token_source = 'subagent_usage'` are subagent totals and have no hourly rows.
- `attrs.otel_requests` on a `session_usage` row tells how many OTel records went into it; `subagent_invocations.attribution` is `hook` when the row rests on a usage event or usage rows, `heuristic` when only start and stop were seen.
- `team` is the tag the client's configuration states, and `feature_id` is derived from the branch; neither is a roster team or a tracker epic.

## Money

Every money value of CLI Analytics (COST, per user, per model, per session, per repository, cache-read cost, `bloat_pct`, Wasted) is token counts × the platform catalog, priced at read time in the handler with the current prices: LiteLLM's `model_info` with the proxy on, the `config/llms` YAML otherwise. The response metadata names the catalog that priced it in `catalog_source` (`litellm` / `yaml`). With the LiteLLM catalog a route (`litellm_params.model` of a deployment, e.g. `bedrock/eu.anthropic.claude-sonnet-4-6`) prices first at its own deployment's price from the route map the catalog keeps beside its chat list (built from every enabled chat deployment, replaced with the catalog at startup, recovery and `/admin/llm/reload`); a route that two deployments price differently, that has a deployment whose mapping failed, or that is priced at zero rates, is left to its plain name. A route outside the map, or any route with the YAML catalog, prices at its plain name, which `normalize_model` / `normalized_model_name` derive by stripping `bedrock/[<region>.]anthropic.`, `vertex_ai/`, `anthropic/anthropic.`, `anthropic/` and a Bedrock Claude id's trailing `-v1`, and turning Vertex's `@YYYYMMDD` into `-YYYYMMDD`. The last lookup tier, reached only when no alias matched and the name carries no 8-digit date, matches catalog names with their trailing date or `-vertex` removed (the catalog side only) and answers only when every matched entry has the same tariff: `claude-opus-4-6` prices when its dated and `-vertex` entries share a tariff and stays unpriced when they differ.

- Every aggregate surface prices the same rows: `get_session_model_costs` returns the token sums per (session, raw model), the empty model kept. Each row is priced once; the totals, per user, per model (by the normalised name) and per session are sums of those rows, so they add up to the total.
- Input, output and cache-read tokens are priced at the model's input, output and cache-read price; 5m cache writes at `cache_creation_input_token_cost`; 1h cache writes at `cache_creation_input_token_cost_above_1hr` (optional in the YAML `cost:`; a model without it prices 1h tokens at 0). A cache write without a 5m / 1h split is priced at the 5m price; the split never prices more tokens than the cache write.
- A model without a catalog entry, without a price for a token kind it used, or with an empty name (reported as `""`) contributes 0 for those tokens and is listed in `unpriced_models`, by its normalised name (a route as its plain name, deduplicated and sorted). A routed request is listed under the route's name, dated or undated as the route is (`claude-sonnet-4-5` for `vertex_ai/claude-sonnet-4-5`), while a request of that model without a route keeps its transcript name (`claude-sonnet-4-5-20250929`).
- Totals-only subagents: `get_session_model_costs` and `get_session_detail_model_costs` UNION the `session_usage` rows with `attrs.token_source = 'subagent_usage'` into the `cost_daily` token columns, so a subagent that reported only totals is priced at read time like any other row. The rollup guard `_totals_are_a_source` is the only double-count protection (it removes the totals rows once requests of that agent exist); the reader adds none. A totals model absent from the catalog prices 0 and is listed in `unpriced_models`; a totals model that is a route prices like any route above. A totals row without a cache split keeps the 5m / 1h sums NULL.
- Sessions list: sessions with dimension events but no `cost_daily` row are listed (`include_costless`) with `cost_usd` 0.0 and `cost_available: true`. A token row (`cost_daily` or subagent totals) whose tokens are all zero is no usage, by the same test `CatalogPricer.price` uses (no positive count of any priced kind). `cost_available` is false only when the session has usage and none of its usage rows' models has a catalog price, with `cost_usd` 0.0; a session with no token rows or only zero-token rows is a known $0.00 (`cost_available: true`), and its zero-token models are not in `unpriced_models`. *Changed 2026-11-13 (EPMCDME-17138): supersedes the EPMCDME-16441 no-usage → false decision.* A model with a catalog entry but no price for some token kind it used (a cache-read rate, say) counts as priced: the session keeps `cost_available: true`, its `cost_usd` is understated (those tokens cost 0) and the model is listed in `unpriced_models`, which the UI shows as an "Understated" marker, not as an unknown cost (EPMCDME-17138 review CR-002: kept as is, pinned by `test_cost_available_stays_true_for_a_model_priced_for_only_some_token_kinds`); a catalog entry with zero input and output rates and no positive cache-read rate is no price, not a free model (`CatalogPricer.is_priced`, EPMCDME-16522), so a session whose usage is only on such a model is `cost_available: false`. The list and the session detail use the one rule `cost_available` (`session_money.py`; the list through `unpriced_session_ids`). The detail of a costless session resolves too (`get_session_detail_meta` also keys on `session_dims`), with zero cost and no model rows. The count of sessions listed with `cost_available: false` (unpriced models) is logged when non-zero (no user or project data). KPIs, priced aggregates and the other endpoints keep the inner join and do not list them.
- Same-scope pricing of each amount (EPMCDME-17152): the Users rows and `include_chart` entries, the cost-by-user and cost-by-model rows, and the project, repository and branch rows carry `cost_incomplete`, `unpriced_models` and `cost_unknown` over exactly the sessions behind that row's own `cost_usd`; a fully priced row stays unmarked, a partly priced row keeps its priced part, and the window metadata and the funding buckets are never reused for a row. `cost_unknown` is true only when the amount is incomplete and no used token kind of it had a rate, false when one had, and `null` where the source cannot tell (stored rollups with $0 and incomplete): a $0 never implies unknown, and neither does the absence of incompleteness (a row with no used token is complete and no evidence). The evidence is a (session, model) row with a positive used kind that has a rate, a zero rate included (SQL `has_rate` of `priced_groups` → `cost_priced`; Python `CatalogPricer.prices_some_usage`, the same rate resolution as `price_flagged`); positive money is evidence too. Roll-ups (branch → repository → project) merge their children's evidence (`_priced`, dropped before the response), never their completeness. Every viewer authorized for an endpoint receives the model names in its `unpriced_models` fields. Endpoint access and session scope still apply.
- Sessions list rows and Session Details supply their own `cost_incomplete` and `unpriced_models`. Overview and Cost KPIs also carry `cost_incomplete`, `unpriced_models` and `cost_unknown` for their estimate, derived from the existing money group's priced evidence. An entirely unpriced estimate is unknown; a used zero-rate kind keeps a real zero. Stored rollups with incomplete zero cost and no priced evidence report `cost_unknown: null`.
- Sessions list paging (every sort and search is decided in PostgreSQL, and so is the framework filter's page and total; the framework rule itself, the customer's regex configuration, is applied in Python to the window's distinct classifier name sets, and Python prices and builds the page's rows):
  - `get_session_page` returns `(total, session_ids)` of one page for `start_time` and `ctx_per_call`; `get_cost_page` does the same for `cost_usd` and also returns the kind flags of the window; `get_framework_page` does it for the framework filter. Order is the sort key DESC, then `session_id COLLATE "C"` ASC, for every sort. `total` is an exact count. The offset is clamped, so a huge page number returns an empty page with the exact total.
  - `start_time` orders by `session_dims.started_at` (page and count are separate statements). The unfiltered shared list (the default Sessions request) runs its page and count on `session_dims_active_shared_cov` (the page an ordered walk, the count index-only before arm (1) was bounded by `last_activity_day`, a heap read now); the other scopes and filtered requests use `session_dims_active_started`, and `session_dims_started_at` / `session_dims_started_shared` serve the readers that do not filter by activity. The order key is the stored hook time, while a row's `start_time` is the reported activity start (`least(started_at, activity_started_at, earliest OTel row)`, see Notes for a reader): for a session whose first OTel event or transcript line precedes its first hook the two differ, so such a row can look out of order by that gap. Ordering by the reported start would need a stored sort column with its own index. `ctx_per_call` is the session's cache-read tokens (subagent totals included) per API call, 0 without calls; for the unfiltered shared list (no search, no unattributed filter, no user / project / repository / branch / class filter, the admin `exclude` scope) `sel` outputs the session id alone, so the window's ids are read as an Index Only Scan of `session_dims_active_shared_cov` (arm (1) is a Bitmap Heap Scan of `session_dims_active_started` since it reads `last_activity_day`) instead of a Bitmap Heap Scan of the wide `session_dims` rows; every other `ctx_per_call` request, and the other sorts, keep the full lean projection (same ids, order, total and tie-break either way). `cost_usd` is the SQL twin of `CatalogPricer.price` (`round(cost, 9)`) over the catalog rates of `get_cost_models()`, built from one materialised (session, model) token grouping that also yields the kind flags.
  - Search is a case-insensitive literal substring match (`ILIKE ... ESCAPE`, `%`, `_` and `\` never special; case folding follows the database collation) over the stored first prompt, session title, repository and branch, for every sort. A NUL character matches nothing and returns an empty page: the `start_time` and `ctx_per_call` paths issue no statement, while the cost sort and the framework filter still run their model-list and flags statements first (the metadata is whole-window).
  - The per-session queries run for the page's ids only (`LocalAnalyticsFilter.restricted_to` adds `session_id = ANY(...)` inside `sel`, on top of the existing scope, never in place of it).
  - The framework filter is the customer's regex config, so it stays in Python: the reader builds the classifier names of the filtered window into a temp table (one connection, one transaction), returns the distinct name sets, the handler keeps the sets the classifier accepts, and the page is cut from the sessions of those sets. For the unfiltered shared list (the same conditions as the `ctx_per_call` ids-only `sel`) every statement of the framework request reads `sel` as `session_id, started_at` (the names statement, the page statement and the whole-window flags statement of `get_window_model_flags`, which does the same whenever its filter is unfiltered): both columns are in `session_dims_active_shared_cov` (key `started_at`, INCLUDE `session_id`), so the window is an Index Only Scan (0.3-0.5 s) instead of a Bitmap Heap Scan of the wide rows (3-4 s) that is also hashed by every consumer. A search, the unattributed filter or any narrowing filter keeps the full projection. Same ids, order, total and flags either way (live test on a throwaway database).
  - Unpriced-model metadata (`metadata.unpriced`, `catalog_source`) keeps its scope: the models of the page's rows for `start_time`, `ctx_per_call` and search; the whole filtered window for the cost sort and the framework filter. A model is unpriced by the `CatalogPricer.price` rule (positive tokens in some kind and no catalog entry, or a missing rate for a token kind it used). *Changed 2026-11-06 (MR review CR-002, CR-005): an uncatalogued model used to be unpriced on any non-zero token count, a negative sum included; `price()` now counts positive tokens only, as its catalogued branch and the SQL flags (`bool_or(tokens > 0)`) do. `price()` is shared, so the rule applies to every `CatalogPricer` caller, the Cost and Efficiency views included (AC17); served `cost_usd`, `cost_available` and `bloat_pct` do not change, and `metadata.unpriced` differs from before only when every kind sum of an uncatalogued model is at most zero and one is negative, which ingest does not store.*
  - A Sessions request holds one analytics connection for its window statements and at most two for its detail statements (`CliAnalyticsReader.bounded()` takes the first and runs statements one after another; `widened()` adds a second around the detail statements only, so at most two statements run at once; both are released before pricing and row building). The window statements are the long ones and run one after another, so the request does not hold an idle second connection through them. The second connection is waited for only 0.5 s; if the pool has none free the details run on the one connection the request has, so requests that each hold one connection cannot deadlock a nearly exhausted pool. Other endpoints keep their own acquires, except `/users`, `/user-charts` and `/cost` (EPMCDME-17051): each of those runs its statements one after another on one held connection (`bounded()`), inside `asyncio.timeout(CLI_ANALYTICS_DASHBOARD_REQUEST_BUDGET_S)` (540 s, below the 600 s ingress `proxy-read-timeout`), builds its rows after the connection is back in the pool, and answers a timeout with 504. The `gather` over several connections is gone for them. Each pod also caps these three at `CLI_ANALYTICS_DASHBOARD_MAX_CONCURRENT` concurrent requests (default 0: `CLI_ANALYTICS_PG_POOL_SIZE` minus 4, at least 1, so ingestion keeps four connections of the default pool of 8; minus 2 left the pool at 8/8 under the 600K load and ingest got 503); the rest wait in arrival order, the wait counts against the 540 s budget, and one that waits it out answers the same 504 (`dashboard_slot()` in `cli_analytics_handler.py`, a per-event-loop semaphore entered inside the timeout; `/sessions` and the other endpoints do not use it).
- `cost_daily.cost_usd` and `session_dims.source_cost_usd` hold the producer's cost (Claude Code's OTel `cost_usd`); they are stored and not used for money.

Limitations:

- All history is priced at today's catalog; a price change reprices every day.
- Days without a 5m / 1h split (clients before the split, days older than raw retention) price 1h writes at the 5m price.
- Days older than raw retention are not recomputed: they keep their stored rollups.
- COST differs from Claude Code `/cost`, which uses Anthropic's base prices, not the catalog's.
- A request with web search is charged above its token price; the surcharge is in no event and not in the data.
- Accepted residuals of totals-only subagents: KPI, model-breakdown and users token counts and the dispatch cost do not include totals rows, and the hourly views omit them.

## Stored Session Sort Keys

EPMCDME-16427 part 2. The three expensive Sessions list requests (`sort_by=ctx_per_call`, `sort_by=cost_usd`, `framework=`) read per-session values stored on `session_dims` instead of recomputing them over the window. Code: `session_sort_keys.py` (derive, backfill, re-price, enable/disable), `sort_keys_cli.py`, `stored_mode.py` (the read decision), `cost_key_sql.py`, `kind_masks.py`, `rates_version.py`, the stored statements in `reader.py` and `session_page_sql.py`. Measured numbers: `scripts/cli_analytics_bench/bench-results.md`.

### Columns, control row, stamp

| Item | Revision | Meaning |
|---|---|---|
| `cache_read_total`, `api_call_total` | `a1c1a0000012` | inputs of the ctx_per_call key |
| `classifier_names` | same | the session's classifier names, ordered; the framework filter and grouping read them |
| `models_used`, `kind_masks` | same | priced models and, per model, the token kinds used (the cost key is priced from them at request-time rates) |
| `cost_key` | same | the cost sort key |
| `rates_version` | same | the per-session stamp: non-NULL = the stored columns are derived; for `cost_key` it names the rate set that priced it |
| `session_sort_keys_control.enabled` | same | one row, false until an operator turns the stored readers on; the kill switch |

All columns are nullable without a default (no rewrite). Index (`a1c1a0000012`, step 2 of the same revision, partial `WHERE has_activity AND <not owner-private>`, the `SHARED_PREDICATE` copied byte for byte from `a1c1a0000011`): `session_dims_fw_win` (`started_at`, INCLUDEing id, stamp, classifier names, `cache_read_total`, `api_call_total`, `cost_key`, `models_used`, `kind_masks`; index-only scan: the framework statements and the unfiltered ctx and cost lists read their inputs from it without touching the heap; it makes every stored column an indexed one, so a refresh that changes any of them is not a HOT update) and `session_dims_rates_version` (the stamp alone, deduplicated, a few MB: set S, the unstamped sessions, is read from it). Two more (ctx key, cost key) were designed and are not built: they cannot serve the statements, which sort the merged stored/live key.

### Writers

1. The rollup refresher derives a session's columns after the activity facts, in the same transaction (`RollupRefresher._write_sort_keys`).
2. The maintenance job derives sessions without a stamp and re-prices those stamped by another rate set, on every run.
3. `sort_keys_cli` does the first backfill, a hand re-run and the switch (see Operations). Every command takes the `maintenance` advisory lock and exits 1 when the job holds it.

### Reader: stamp, set S, fallback

A stored read is taken when the kill switch is on, the viewer scope is expressible over `session_dims` columns and the whole table holds at most `s_cap` (5000) sessions without a usable stamp (S is counted over `session_dims`, not over the request's window, and includes the sessions marked oversized or skipped, which are never stamped: a retention partition drop or a long run of marked sessions can push it over the cap, and every ctx, cost and framework request then runs today's statements until `backfill` catches up). Those sessions are set S: their values are computed live from the rollup tables and merged into the stored page, so a list is correct at every point of the roll-out. For the cost key a stamp is usable only when it equals the current rates version. Otherwise the request runs today's statements unchanged. Each fallback and each merge of a non-empty S logs a WARNING at most once per reason per 60 s (`stored_mode.py`): `disabled`, `s_over_cap`, `unexpressible`, `no_rates_version`, `s_merged` (a merge, not a fallback). `cli_analytics: framework groups=N accepted=N sessions=N` (INFO) reports the distinct classifier name sets of the framework read: a large N is the signal to look at the classifier names.

### Rollout and rollback

Order: (1) deploy the code and run the migrations (`a1c1a0000012`). The kill switch (`session_sort_keys_control.enabled`) is seeded **off**, and **no manual `enable` is needed**: the maintenance job turns it on by itself, right after its backfill and re-price step, as soon as no session lacks a usable stamp (none with `rates_version` NULL or different from the current rates version, the stamp the readers trust, cost key included, apart from sessions that arrived in the last 10 minutes; never under an empty catalog), and logs one INFO line `stored session sort keys enabled automatically`. Almost no unstamped sessions is the threshold because the benchmark showed that even 190 unstamped sessions in a 30-day window multiply the cost request by 3 and the framework request by 17. Until then every request stays correct: a window with more than `s_cap` (5000) unstamped sessions takes today's statements. (2) `sort_keys_cli disable` records the operator's intent (`operator_disabled`): the job never turns the readers on again until `sort_keys_cli enable --since <timestamp the switch was cleared> | --all`, which nulls the stamps of sessions active since then, turns them on and clears the intent. (3) Roll all pods onto the new code promptly: a pod on the old code writes sessions without stored values; the job re-derives only unstamped or re-priced sessions, the automatic switch-on waits while any connection to the database still carries the application name of the previous code (`codemie-cli-analytics`; this code connects as `codemie-cli-analytics/sort-keys`), that is while a pod of the roll-out has not been replaced, and first nulls the stamps of the sessions active in the last hour. That is not airtight: an old pod with no open connection at that moment (the pool keeps none open) is not seen, and a pooling proxy may not pass the application name on, so it may switch on early. A pod on the old code that writes after the switch leaves stale keys behind: run `sort_keys_cli enable --since <deploy start>` if that may have happened. Anything that filters connections by the old `application_name` no longer matches the new pods. A session whose `classifier_names` and `models_used` together exceed 2300 bytes (client-sent names; a btree entry holds about 2.7 kB) is not stamped: its arrays are not stored, the marker name `~oversized~` stands in `classifier_names`, and the readers compute it live. The backfill, the re-price and the automatic enable skip a marked session, so it blocks none of them; a later recompute re-derives it, and it gets its stamp back once the names have shrunk. Any other derivation error of one session is logged as `stored sort keys of session … skipped` and the run goes on. (4) The job works a time budget per run (`_SORT_KEYS_BUDGET_S`, 120 s), so a large table fills over many runs; `sort_keys_cli backfill` speeds up the first fill (about 4.4k sessions/s and 362 MB WAL per 300k sessions measured; run it in a quiet window, then `VACUUM (ANALYZE) session_dims`). On a very large `session_dims` the CLI needs `CLI_ANALYTICS_PG_STATEMENT_TIMEOUT_MS` raised above its 30 s default and a smaller `--batch`: a batch of 1000 sessions hit the 30 s statement timeout on local data. (5) Check the index `session_dims_fw_win` is valid (an invalid one is dropped and rebuilt by the migration; for a large table pre-build it CONCURRENTLY under the same name before the migration). Rollback: `sort_keys_cli disable` (instant, every request returns to the rollup statements; no data is lost). Downgrade of both revisions drops the columns, the control table and the index.

**A database that already ran an earlier form of `a1c1a0000012`** (QA and local databases that deployed this MR before its final head; the content of the revision changed while its id stayed the same): the revision is stamped, so Alembic does not run it again and `CREATE INDEX IF NOT EXISTS` would keep an old narrow `session_dims_fw_win`. Such a database may lack `session_dims_rates_version`, the wide `session_dims_fw_win` (eight INCLUDE columns) or the control table's `operator_disabled` column, so every Sessions request reads S with a scan of `session_dims` and the stored ctx and cost reads are not index-only. With the final code deployed, run the revision's `DOWNGRADE` statements by hand after `SET search_path TO codemie_analytics` (the statements name their tables unqualified; every one is `IF EXISTS`: the indexes in reverse order, the control table, the columns of `session_dims`), run `UPDATE cli_analytics_alembic_version SET version_num = 'a1c1a0000011'` in the same session (checked on a throwaway PostgreSQL 17 database built with the first form of the revision: after the next migration run its schema equals a fresh database's), then let the next migration run (any pod start or refresh job) apply the revision again; the maintenance job derives the stamps again and enables the stored reads by itself. A database that never ran an earlier form needs nothing.

### Cost of the plain index build

`a1c1a0000012` builds its index in its second step, after the columns and the control table are committed (the figures below were measured with the first form of the revision, four indexes in one build; one index takes roughly a quarter of those times) under one SHARE lock on `session_dims`, in one transaction under one SHARE lock on `session_dims`, which blocks every writer (ingest bindings and the refresher) for the build. Measured lock hold: 534 ms at 100k rows, 2.64 s at 300k (idle), 3.37 s at 600k, i.e. 114-187k rows/s. An ingest binding blocked longer than the 1 s acquire timeout answers 503 (blocked up to 3.8 s at 600k rows); the migration's own `lock_timeout` is 5 s. Threshold: plain build is fine up to about 100k `session_dims` rows; from about 115-180k rows pre-build the index CONCURRENTLY (same name), and a plain build above about 570-890k rows fails on the 5 s timeout. A failed attempt is retried by the next job.

### HOT updates

The refresher's UPDATE of the stored columns is HOT only when no indexed column changes and the page has room. The classifier names and the stamp are now indexed (`a1c1a0000012`), and the same UPDATE also writes `has_activity`, `last_activity_day` or `resumed`, so it is never HOT: measured HOT ratio 0.0 (0 of 23.5k updates). The `a1c1a0000012` docstring says these columns are in no index; that was true for that revision alone. No fillfactor was applied: it cannot make these updates HOT and it wastes space on a mostly append-only table. Table bloat after a backfill is returned by `VACUUM`, not by the indexes (154 -> 163 MB at 366k rows).

## Users tab requests (EPMCDME-17051)

The Users tab needs neither of the first two: it sends them as `false` with `include_chart=true`, and only then is the request answered from the start-day rollup.

| Parameter | Default | Effect when true |
|---|---|---|
| `include_chart` | `false` | Adds `data.chart`: every user of the window, in rank order, as `{developer_name, cost_usd}`. The page's rows are the ones the page alone would give. The Users tab sends this and no longer calls `/user-charts` |
| `include_daily_activity` | `true` | Fills each row's `daily_activity` (a read over the whole window); empty when `false` |
| `include_avg_duration` | `true` | Fills `avg_session_duration_ms` (a read over the whole window); null when `false` |

## User Start-Day Rollup

EPMCDME-17051. `/users` and `/user-charts` read, for a window of whole days up to now, one row per (UTC day a session started, developer, subscription class, project-origin class) instead of pricing and summing every session of the window. The two classes are the values the `subscription_type` and `project_origin` filters compare, so a request with either filter sums the rows of the classes it asks for.

| Item | Meaning |
|---|---|
| `user_day_rollup` (`a1c1a0000014`) | Per (start day, developer, subscription class, project-origin class): session count, token sums, turns, tool calls and successes, net lines, the latest event, and the keys of the developer's top model (calls, day, session, e-mail, model, query source) so the top model of a window is the first of the rows' keys. A developer's class lists are the distinct classes of their rows |
| `user_day_money_rollup` | Per (start day, developer, the two classes, funding route, personal-billed): the priced cost and the number of priced sessions, over every priced session (`*_all`) and over those whose token rows all come from `cost_daily` (`*_cd`, which /cost reads and /users does not), with the unpriced raw model names of each |
| `user_day_model_rollup` (`a1c1a0000015`) | Per (start day, subscription class, project-origin class, normalised model): the spend money of the sessions that used the model (cost, sessions, unpriced raw names), taken from the live `G_MODEL` grouping. What /cost's "Cost by Model" sums |
| `user_rollup_day_state` | Per start day: the signature of its sessions in `session_dims` (their number, those with activity, sums of the latest event, the cost key and hashes of the developer's e-mail and of the stored subscription type and project origin), the rates version the money was priced with, the `shape` (1: developer rows only, 2: also model rows, 3: also Overview rows, 4: the money of every row covers every session, Personal-paid included, EPMCDME-17260; every reader asks for shape 4 now, so a day of a lower shape is refused, answered by the live statements and rebuilt by the job, while a day of a higher shape is neither refused nor rebuilt down) and when it was built |

A session is in exactly one row, on the day it started, with its whole-lifetime values, so a window is a plain sum and equals the live statements for the sessions that started in it. Nothing is computed by a second implementation: `gather_cohort` runs the live reader's own statements over a temp table holding one day's sessions of one class pair (`materialize_sel(f, cohort="started")` under that pair's `subscription_types` and `project_origins` filter), once per pair the day has.

**The job** (`cli_analytics_user_rollup`, `postgres/user_rollup.refresh`, on the one connection that holds its advisory lock): days with no usable state (never built, or built under other rates) are rebuilt first, newest first, then the days whose signature changed; a changed day waits `MIN_REBUILD_S` since its last build (ten times that for a past day), and the signature of the last two days is checked on every run, of all days every 10 minutes. A run stops starting days after `CLI_ANALYTICS_USER_ROLLUP_RUN_S`. Days older than the window drop out. A rates change makes every day stale, which is a backfill in the background; until it ends the windows that need those days take the live statements.

**The read** (`PostgresCliAnalyticsReader.rollup_users`, `user_rollup.serve`) answers only when: the scope is an unrestricted `exclude` one (the viewer's e-mail never enters its SQL, so every super admin shares it) and no filter other than `subscription_type` and `project_origin` narrows the sessions; the window starts at midnight UTC and ends within two minutes of now (the latest-event column is the lifetime maximum); every day of the window has a state under today's rates and today's was built lately; and at most 2,000 sessions started earlier and are active in the window. Those sessions (`resumed`, or not derived yet) are read live under the request's filters and combined, which is what makes the result equal the live admission rule. That read runs with `random_page_cost = 1.1` on its held connection (reset after it): under the default the planner joined the few sessions to a scan of every partition of the fact tables, 8 to 12 s at 700K sessions against about 2 s with index lookups. Anything else, a failed read included, returns None and the caller runs the live statements. The handler asks only when the request needs neither daily activity nor the average duration, and caches the answer for the cache TTL.

**/cost from the rollup** (`PostgresCliAnalyticsReader.rollup_cost`, `user_rollup.serve_cost`): `GET /cost` takes `include_class_lists` and `include_buckets`, both on by default (a request that sends neither gets the lists and buckets it always got). With both `false` (what the Cost tab sends) the handler asks the rollup first: the spend total, per developer (the `cost_daily`-only figures), per model (the model rows), the developers it lists, the session totals and the token total all come from it, under the same eligibility rules as /users. With either on, or when the rollup cannot answer, the live statements run (the class lists and the buckets are not in the rollup). `/user-charts` and `/users` do not read the model rows. Checked against the live statements on 98K sessions for 7 and 30 days with and without the class filters: equal.

Verified on a 300K-session database (30-day window): the ranking, the six money groupings and every per-user field equal the live result. Build: about 0.75 ms per session of the day (4.7 s for a day of 6K sessions); a day of 20K sessions took 45 s in the dev container. Reading: 5 to 9 s cold, of which the resumed-session correction is most; the live money page alone took 9 s.

## Stored Model Groups

EPMCDME-17051. The money statements of `/users`, `/user-charts` and `/cost` price one set of (session, raw model) token groups (`priced_groups` in `grouped_cost_sql.py`). Building it from `cost_daily` and `session_usage` took about 22 s at 600K sessions, so the token sums are stored per session and the statements read them.

| Item | Meaning |
|---|---|
| `session_model_groups` (`a1c1a0000013`) | One row per (`session_id`, `model_name`): `normalized_model_name`, input, output, cache-read, cache-creation tokens, the 5m / 1h cache-creation split (NULL when unknown) and `has_cost_daily`. Primary key (`session_id`, `model_name`), fillfactor 90, no foreign key, no partitioning. Tokens only: a rate change invalidates nothing, the cost is priced at read time from these sums with the same builders as the live path (`unpriced` is also computed at read) |
| `session_dims.model_groups_rev` | `smallint`, NULL = never derived. The rows of a session are trusted only when `rates_version IS NOT NULL AND model_groups_rev = MODEL_GROUPS_REV` (1). A format change bumps the constant and makes every row untrusted until re-derived. `-MODEL_GROUPS_REV` (`MODEL_GROUPS_NEVER`) marks a session with a raw model name above 1024 bytes: it holds no rows and the readers compute it live; the backfill and the automatic enable skip it. A partial index `session_dims_model_groups_pending` serves the pending predicate |
| `session_sort_keys_control.model_groups_enabled`, `model_groups_operator_disabled` | The kill switch of the stored groups, **separate** from the Sessions switch (`enabled`). Seeded off |

Writers: the same derivation as the sort keys (`SORT_KEYS_SQL`: the rollup refresher's stamp and the maintenance re-derive) upserts the rows in sibling data-modifying CTEs, deletes the rows of models a session no longer has, and sets `model_groups_rev`; a re-derive that changes nothing writes nothing. The maintenance job also backfills `_MODEL_GROUPS_BATCH` (1000) pending sessions per run and turns the groups switch on by itself once none is pending (apart from sessions that arrived in the last 10 minutes) and no connection of the previous code is open, logging `stored model groups enabled automatically`; never after `disable-groups`. Retention: `session_purge.py` and the orphan sweep of the maintenance job delete the rows with their session.

Reader (`stored_mode.model_groups_mode`): the three statements read the table when the switch is on and at most `s_cap` (the reader's configured cap, 5000 by default) sessions of the table are not valid (S is read from the pending index, not the window). Those sessions are set S, bound as `$stale`: their groups are built live in the same statement (`priced_groups_cte(stored=True)` unions the stored arm and the live arm over the CTE `live`) and the output columns of `priced_groups` and `gc` are unchanged (the EPMCDME-17052 contract). Otherwise the statements run the live form. WARNINGs, at most once per reason per 60 s: `model_groups_disabled`, `model_groups_s_over_cap`, `model_groups_read_error`; `model_groups_s_merged` is a merge, not a fallback.

Shared `sel` (EPMCDME-17051): `/users`, `/user-charts` and `/cost` call `materialize_sel(f)` first on their bounded reader. It evaluates the window's `sel` once (the admission arms, 8-12 s at 600K) into a TEMP TABLE `request_sel_<uuid>` of the held connection, with the `developer` column and the stored flag columns, and runs `ANALYZE` on it. Every later statement of the request (the money statements, the fact reads, the class lists) reads the table through `_sel_cte`, which gives the same columns as `_sessions_cte`; a statement with a different selection (other filters or ids) builds its own CTE, and a developers filter that is a subset of the table's is applied to the `developer` column. `bounded()` drops the table before the connection goes back to the pool (a temp table survives asyncpg's reset), also after an error or a cancel; if the drop itself fails the connection is closed, never reused. `widened()` does not take a second connection while a temp table exists, because the table is visible to its own connection only.

| Alert on | WARNING `rollup queue has N keys, the oldest waiting Ns` (repeats every 5 min while stale); WARNING `recomputing rollup key ... timed out (N of 3 in a row); it is retried in N minutes`; ERROR `dropped rollup key`; ERROR `maintenance step ... failed`, `cannot create partition`, `purging expired rows of ... failed` (for sessions, a statement timeout on every run means the first batch counts more child rows than the timeout allows: lower `CLI_ANALYTICS_SESSION_PURGE_BATCH_SIZE`); ERROR `the session purge skipped N idle sessions whose rows another transaction holds` (a held child row or a held `session_dims` row; names up to 10 ids; repeating on every run means a transaction outside the code holds them); ERROR `could not count the idle sessions the session purge left`; ERROR `the session purge stopped: a batch of N idle sessions ... deleted none and skipped none`; WARNING `rows outside every planned partition`; WARNING `dropped a telemetry record PostgreSQL rejects`; WARNING `a request holds more records PostgreSQL rejects than one attempt isolates`; ERROR `cannot drop expired partition`; ERROR `the configured analytics storage cannot be used` (startup) |
| Retention | Whole partitions are dropped; DEFAULT partitions, `session_skills` (rollup retention), `session_attributes` and OTel resources (raw retention) are purged by date. `session_dims` is not on rollup retention: with `CLI_ANALYTICS_SESSION_RETENTION_DAYS` = 0 it is kept. Above 0 the maintenance job first deletes whole sessions whose `coalesce(greatest(last_event_at, ended_at), updated_at)` is before the midnight-UTC cutoff, in batches: each statement takes up to `CLI_ANALYTICS_SESSION_PURGE_BATCH_SIZE` idle sessions and deletes those whose child rows (`session_usage`, `session_usage_hourly`, `subagent_invocations`) add up to at most 100 000, each with its `session_dims` row and all its child rows in the same statement. Child rows are reached per session through the primary key, so a statement grows with the child rows of its candidates (each counted up to the row cap + 1 per table), not with the size of the child tables; a batch size is lowered only after a batch succeeds, so a first batch too heavy for the statement timeout fails the same way on every run until the setting is lowered. Each statement is its own transaction with a 2 s `lock_timeout` beside the statement timeout; the batches go on until one finds no idle session left. The purge never waits for a row lock: a session with a row another transaction holds in any of the three child tables is skipped whole, left out of the rest of the run and logged, and a later run takes it once released; a held `session_dims` row is skipped by `SKIP LOCKED`, then found by one plain count (no lock) of the idle sessions left after the batches and parts, and logged in the same skipped-sessions ERROR; the count runs only after a purge that ended normally, not after a failed statement or the "deleted none and skipped none" stop, whose sessions left were never tried; it leaves out rows whose `updated_at` is after the purge started, since the rollup refresher can re-create or update an old session's `session_dims` row during the run, idle but held by nobody, while a row actually held keeps its earlier committed `updated_at`; the refresher sets `updated_at` to its transaction's start, so a refresher transaction already open when the purge started can still put such a row in the skipped ERROR once, and the next run no longer reports it; a count that fails is logged and is not a purge failure; a session another transaction changed meanwhile is tested again and kept whole when it is no longer idle. A session loses its `session_dims` row only when every child row counted for it was actually deleted; one whose child row another transaction changed during the statement keeps its `session_dims` row, is logged with the skipped sessions and is finished by a later run. A session with more than 100 000 child rows is deleted after the batches, in parts of up to 100 000 child rows per transaction, its `session_dims` row last, so it exists partly between its parts; if it turns active between parts it keeps what is left, and the rows already deleted are older than the raw retention, so the refresher cannot rebuild them. A statement that fails (a timeout, a lock timeout, a deadlock) ends the run's session purge: the batches and parts before it stay deleted and the next run continues. Batches take sessions in no particular order: an index on the idle time would cost HOT updates of `session_dims` on every rollup update of an active session, and without one an age order needs a full scan per batch.
