# Spec: backend-analytics-read (EPMCDME-16440 child)

Original planning base: child-1 HEAD 19293cd37. Parent ACs: AC3, AC8, AC10. Updated against implemented review fixes at `a03fd3aecac1705e15ab1439cba5a85a68c212ad`. Paths under `src/codemie/`.

## Goal
Expose subscription type and project origin on CLI-analytics reads, filter by them, show a private Personal session only to its owner, and keep Personal-paid cost out of every shared-project aggregate. Billing class (`subscription_type`) and private scope (`project_origin`, see Definitions) are separate: a Personal-paid session routed to a work project (external and service-account users) is project activity, never project spend. Reads stay in the Postgres reader; no new endpoints.

## Definitions
- **Row classes** (per session id): **P** (private to its owner) = a `session_dims` row exists and `lower(coalesce(project_origin,''))='personal'`, or `subscription_type='personal'` with an origin that is not a shared one (`linked_folder`, `profile`, `registered_repository`, `default_project`; NULL/unknown origin stays private, fail closed). A **Personal-paid session on a work project** (external / service-account users: `subscription_type=personal`, shared origin) is **N**: billing class and private scope are separate; **N** = a `session_dims` row exists and is not P; **M** = no `session_dims` row (legacy priced session known only from raw events/`cost_daily`; `get_session_detail_meta` serves these today, see `test_session_detail_without_dims_starts_at_its_earliest_event`). M is never P.
- **Owned**: row class P, owner and viewer emails match after lowercasing and trimming the same ASCII whitespace set (space, tab, LF, CR, form feed, vertical tab) in Python and SQL, both non-empty. P with NULL/empty owner is not owned (fail closed). Claude account data never replaces CodeMie identity.
- **authNP(row)**: the caller may see a non-Personal (N or M) row under today's rules: `unrestricted` (super-admin only; an auditor is not unrestricted here and has no project admin right unless they are a project admin), or the row's `project_name` (M: the existing derived project, unattributed included) is in `admin_projects` per the current detail/list checks (unattributed stays super-admin only). An ordinary non-admin: always false.
- **Unknown / none**: `subscription_type` NULL/empty (legacy, and M) -> `unknown`; origin NULL/empty -> `none`. Filter values: `unknown` matches NULL/empty subscription type; `none` matches NULL/empty origin.
- **Normalised vocabulary** (responses and filters): values child 1 writes, lower-cased; NULL/empty subscription type -> `unknown`, NULL/empty origin -> `none`; any other stored value -> `other`.

## Behaviour
1. **One effective access scope and truth table.** The router builds one `ViewerScope` per request: `viewer_email` (normalised, None if `User.email` empty), `unrestricted`, `admin_projects`, and `mode`. It is carried in `LocalAnalyticsFilter` and passed by the handler to every reader call, list and detail. A row is allowed iff:

   | mode | allowed |
   |---|---|
   | `exclude` | (N and authNP) |
   | `own_only` | (P and Owned) |
   | `detail` | (P and Owned) or ((N or M) and authNP) |

   - Others' Personal and unowned/ownerless P are denied in every mode, for every role including super-admin/auditor; viewer or owner email missing means Personal is denied and the scope never widens.
   - An ordinary non-admin: authNP is false, so `detail` allows only owned Personal; `own_only` is forced for their `/sessions`.
   - **Fail closed:** the scope is a required argument of every reader method (no default). An absent or malformed scope denies everything and is never treated as unrestricted.
   - Lists and aggregates use `exclude` (or `own_only` on `/sessions` only, item 4); they inherit it from one condition built in `PostgresCliAnalyticsReader._sessions_cte` (`repository/cli_analytics/postgres/reader.py` ~251-291) base conditions, so it also holds when `session_ids` / `restricted_to` (!4652) is set. Lists need a `session_dims` row (`sel` is built from it), so M never appears in lists. Binding-only rows (`started_at NULL`) stay unlisted.
   - Detail, the 7 `get_session_detail_*` methods and `get_skill_names_by_session` use `detail` through one shared reader predicate built on a `LEFT JOIN` of `session_dims`. Row class is decided from the join: a missing row is M (legacy, Unknown/none, existing non-Personal permissions); an existing row with a missing owner is P-unowned (denied). A missing row must never be treated as P-unowned, and P must never be treated as M.
2. **Shared spend.** Aggregate routes always run in `exclude`: private Personal is excluded even for its owner. A Personal-paid session on a work project (N) stays in `sel` as project activity (counts, lists, filters, detail, skills) but its cost is left out of every aggregate money value (`total_cost_usd`, daily/model/user/repository/efficiency cost, averages and percentages use `spend_sessions`); the stored cost and the session's own cost stay as they are. Implemented in `reader.py` (`_spend`, `get_session_model_costs(spend_only=True)`) over `scope.sql_personal_billed`. `/overview`, `/cost`, `/users`, `/repositories`, `/efficiency` reach this through `sel` and have no selector that can include Personal spend. `member_spend_service` is unchanged; no new spend endpoint.
3. **Strict owner-only.** Super-admins and auditors get no exception: they never see another user's private Personal session (class P) in lists, aggregates, detail or skills. A Personal-paid session on a work project (class N) is not private and follows that project's permissions.
4. **Owner self-view (D1 = C) and the `personal_only` selector.** `_admin_gate` is relaxed only for `/sessions` and `/sessions/{trace_id}`. Public selector: query parameter `personal_only`, boolean, default `false`, declared only on `/sessions` (not on aggregate routes, not in their `FilterParams.resolve` path, absent from their openapi entries; an extra `personal_only` on an aggregate route is ignored and cannot change the scope).
   - `personal_only=false` (admin default): today's project scope, mode `exclude`.
   - `personal_only=true`: mode `own_only`; the request's `projects`, `users` and `is_project_unattributed` are ignored (user forced to the viewer, no project scope). Other filters (time, repositories, branch, framework, `subscription_type`, `project_origin`, search, paging) may only narrow. This is how an admin or project-admin owner reaches their own Personal list.
   - A non-admin on `/sessions` is always forced to `own_only` regardless of `personal_only`, and no supplied filter can widen it. A non-admin without a viewer email gets an empty list.
5. **Detail: scope checked before payloads.** The router makes one cheap reader authorization read for the id (LEFT JOIN as in item 1, mode `detail`) and returns 404 if denied (no existence leak) before any payload query. This replaces the router's old post-load `admin_projects` check; non-Personal admin access keeps its project restriction inside authNP. Own Personal detail works for ordinary owners and for project-admin owners whose personal project is not in `admin_projects`; legacy M sessions keep today's behaviour for admins and are denied to ordinary users. Defence in depth: the 7 detail methods and skills-by-id also take the scope and apply the same predicate, so none can run by bare `session_id`.
6. **Filters (D2 = A).** New optional query params `subscription_type` and `project_origin` (multi-value, like `users`) in `FilterParams` and fields in `LocalAnalyticsFilter` (copied in `params()`/`window_params`/`restricted_to`), applied in `_sessions_cte` on the projected `x`. They apply to all list/aggregate routes. Detail returns the fields only; there is no detail filter. A filter for Personal returns no private session unless the mode is `own_only` and the caller owns it; it still matches Personal-paid sessions on a work project that the caller may read (`subscription_type=personal` is a billing class).
7. **Response fields.** `sel` projects `session_dims.subscription_type` and `project_origin`.
   - **Session scope:** `LocalAnalyticsSessionRow` (and the detail subclass) gain scalar `subscription_type` and `project_origin` (`unknown` / `none` for legacy and M) and the additive nullable `route_note` (the stored diagnostic note as is; null when missing or blank, never guessed) and `routing_label` (exactly `folder not linked to a project` for a `default_project` session whose note is `folder_not_linked`, `linked_project_unavailable`, `registered_project_inaccessible` or `registration_ambiguous`; null otherwise, including legacy and missing data).
   - **Aggregate scope:** an entity (repository, user, model, day, tool or activity bucket, and the `/overview` KPI summary) can mix sessions, so every aggregate response model grouping by those gains `subscription_types: list[str]` and `project_origins: list[str]`: the sorted distinct normalised values among the entity's selected sessions. `unknown`/`none` is listed when such sessions are present; no class is dropped and no single session's scalar is chosen. The lists are bounded by the closed vocabulary. Private Personal is never listed in shared views; a Personal-paid work-project session is listed as `personal`/its shared origin, and counted as activity but not as spend. Where the grouped rollup (`cost_daily` etc.) lacks dimensions, the lists come from a join to `sel` on `session_id` inside the same grouping. Aggregate cardinality and totals are unchanged (no new grouping dimension). `/frameworks` (static labels, no reader) is excluded.
   - Models are in `rest_api/models/cli_analytics.py`; handler assembly in `cli_analytics_handler.py`. Regenerate `tests/codemie/rest_api/router_guards/baselines/openapi.json`.
8. **Unchanged.** Unknown/Corporate/CodeMie sessions keep today's project attribution. `cost_available` and subagent pricing semantics from !4652 are not touched; cost availability is price-catalog presence, not billing class. A Personal session leaving a shared project view is expected, not "missing collection".

## Integration with EPMCDME-16441 (!4652)
!4652 is merged to main (squash `a80c1922c`) and this branch is rebased onto it. Combined behaviour is verified: every rule lives in `sel`'s base conditions or in the shared scope predicate, and the !4652 shapes (`_facts_from`, `_token_rows`, `_totals_join`, `get_session_page`, `restricted_to`/`session_ids`, the cost-less listing and the widened `get_session_detail_meta`) subselect `sel` or carry `detail_gate`; the detail `_token_rows` caller has the gate in its WHERE. Spend exclusion applies to the subagent totals-only rows because they are priced per session id. The `session_ids` narrowing sits after the scope condition and never replaces it, including for a denied filter. `include_costless` lists a Personal-paid work-project session as activity and never as spend. Compatibility with the paired CLI #707 is not claimed; it is a future CLI integration seam.

## First-upgrade limitation
Owner-only reads and eligible Personal ingest require no separate activation setting. First-upgrade corner case: while old and new backends serve the same installation during an update, an administrator using an old backend may read Personal sessions already saved by the new backend. This window ends when old backends stop serving requests; it does not recur on later upgrades between versions with owner-only reads, but returns on rollback to an unprotected version. This limitation requires explicit security sign-off.

## Acceptance criteria
- AC1 Fields: session rows and detail carry scalar subscription_type and project_origin; every aggregate model (repository, user, model, day, tool/activity, overview KPI) carries sorted distinct `subscription_types` and `project_origins` lists. Mixed-entity fixture: one repository, user, model and day containing Corporate, CodeMie, Unknown (NULL) and two origins returns exactly those classes (`unknown`/`none` included), with row counts and totals equal to the same query without the fields.
- AC1a Routing explanation: list and detail serialize `route_note` as stored and `routing_label` as above; a default-routed session with an inaccessible link carries the label with its diagnostic note; legacy rows without a note, and non-default origins, carry neither guessed.
- AC1b Privilege: list, detail and the aggregate filter share one CLI privilege policy (`viewer_access`): only `user.is_admin` is unrestricted and only the user's own `admin_project_names` widen the scope. The shared `AccessFilter` (which treats an auditor as unrestricted) is not used; an ordinary auditor sees only their own private Personal session, a mixed auditor and project admin keeps exactly their admin projects, and unauthorized and missing detail are the same 404.
- AC2 Filters: `subscription_type` and `project_origin` params filter all `sel`-backed routes; `unknown`/`none` match legacy NULL/empty rows.
- AC3 Legacy rows: sessions with NULL subscription_type/origin return `unknown` and `none`, stay listed and attributed as before, and match the Unknown filters.
- AC4 Owner self-view: an ordinary non-admin owner and a project-admin owner (personal project not in `admin_projects`) each get their own Personal sessions on `/sessions` and `/sessions/{trace_id}`; an ordinary non-admin gets no non-Personal data, other routes still return 403, and supplied projects/users/filters cannot widen the forced own-Personal scope.
- AC4a Selector: `/sessions?personal_only=true` (default false) returns an admin or super-admin's own private Personal sessions only, ignoring projects/users; aggregate routes have no such selector and exclude private Personal even for the owner (Personal-paid work-project sessions are activity there, without spend).
- AC5 Non-owner: a non-owner (including a project admin) gets an empty list and 404 on detail for another user's private Personal session, and gets none of them when filtering for Personal; a Personal-paid work-project session is returned (with its actual cost on the session) to readers of that project.
- AC6 Super-admin negative: a super-admin and an auditor get no other user's private Personal session in lists, aggregates, detail or skills.
- AC7 Email handling: owner match lowercases and trims the shared ASCII whitespace set in both Python and SQL; NULL or empty `owner_email` or `User.email` never matches and never broadens scope.
- AC8 Shared spend: `/overview`, `/cost`, `/users`, `/repositories`, `/efficiency` totals, daily and model breakdowns exclude private Personal sessions (a seeded one changes none of them) and the cost (not the activity) of Personal-paid sessions on a work project; the session list and detail keep that session's actual cost.
- AC9 Cost-less and subagent rows: the exclusion/visibility holds for cost-less sessions, `subagent_usage` token rows, and paged lists, verified on the rebased branch with the landed !4652 shapes (SQL-text and live tests).
- AC10 Detail and skills: the truth table of item 1 holds for lists, aggregates, skills-by-id and all 7 detail methods (modes `exclude`, `own_only`, `detail`), both owner roles, others' Personal, a missing viewer email and an ownerless P row (denied); an absent scope denies, never unrestricted; denial is decided before any payload fetch. Sibling boundary: a legacy priced session with no `session_dims` row (class M) still resolves its detail for a permitted admin (earliest-event start preserved), is `unknown`/`none`, is denied to an ordinary user, and is never mistaken for an unowned Personal row.
- AC11 Unchanged: binding-only rows remain unlisted; M sessions never appear in lists; reads stay compatible with earlier rows; ingest writes changed only as the ingest-routing spec states (a legacy request now enforces the bound project's checks on every signal, and an eligible non-private legacy adoption reads origin `legacy_project`, while an ordinary user's private Personal request on their own personal legacy anchor keeps `personal`); existing `test_session_detail_without_dims_starts_at_its_earliest_event` still passes.
- AC12 Documentation: no separate Personal activation setting; the event contract documents the first-upgrade corner case.
- AC13 openapi baseline regenerated; reader/filter/handler/router tests and live-PG cases (`TEST_LOCAL_PG_URL`, throwaway postgres:17 at 127.0.0.1) added for AC1-AC10, including the mixed-entity fixture, both owner roles and the M-class case.

## Non-goals
- Storage/migration changes; CLI; UI controls. (The ingest/gate adaptation for Personal-paid work-project sessions and the final discard of a confirmed-unavailable bound project is specified in the ingest-routing spec.) Rename continuity and migration of bound sessions are out of scope.
- Re-implementing !4652 subagent pricing or cost semantics; compatibility claims about the paired CLI #707.
- A new project-spend endpoint; changes to `member_spend_service`, budget or LiteLLM spend.
- Legacy Elasticsearch analytics; relaxing `_admin_gate` on routes other than `/sessions` and `/sessions/{trace_id}`.
- Super-admin/auditor access to others' Personal data.
- Backfill or reclassification of legacy rows.
- A new grouping dimension by subscription type or origin in aggregates.

## Risks
- Any future reader query selecting by bare `session_id` bypasses the rule; a guard test greps reader SQL for it.
- The aggregate lists touch several response models; the plan must enumerate them from `rest_api/models/cli_analytics.py`.
- The vocabulary bucket `other` assumes child 1 writes only a small closed set of values.
- The M-class permission for legacy detail reuses the current router project check; the plan must read that code (router ~670-707) to keep it exact.

## Open decisions outside the read implementation
- Explicit human security approval remains required; passing tests or core code review alone do not provide it.
