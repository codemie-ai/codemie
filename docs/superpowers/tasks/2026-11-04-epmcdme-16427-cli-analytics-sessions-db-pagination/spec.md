# EPMCDME-16427 — CLI Analytics Sessions list: DB-level pagination

## Why

`GET /v1/analytics/cli-analytics/sessions` takes 8.6-12.9 s over a 30-day window and reads 366,724 rows to render 20 sessions. The target is 825 ms. Three things make it slow:

- Sorting by `cost_usd` and filtering by `framework` page in Python over the whole window (`service/analytics/handlers/cli_analytics_handler.py:900-902`).
- The default `start_time` sort probes `log_events`/`spans` for every session in the window (`repository/cli_analytics/postgres/reader.py:325-351,900-903`).
- One request holds up to 5 of the 8 pool connections at once (`cli_analytics_handler.py:911-917`), which can push ingest past its 1000 ms acquire timeout (503).

## What

**S2: page first, then details.** For every sort and filter, the database chooses which session ids go on the page. The detail queries (cost facts, turns, tool success, lines, model costs, skill names) then run only for those ids, through `f.restricted_to(page_ids)` (`repository/cli_analytics/filters.py:63`). The page query extends `get_session_page` (`reader.py:870-933`). The framework path gets a sibling method built on the same order builder. The Python paging branch (`in_sql`, the search in `_filter_sessions`, `named_first_prompt`, the sort map in `_page_sessions`) is retired, and `SESSION_PAGE_SORTS` lists all three sorts. A test ties the router's `sort_by` Literal (`rest_api/routers/cli_analytics.py:694`) to `SESSION_PAGE_SORTS`, so a fourth sort cannot reach the router without a database order.

- `start_time` orders by `session_dims.started_at` DESC, then `session_id COLLATE "C"`.
- `cost_usd` orders by the catalog cost DESC, then `session_id COLLATE "C"`, computed in SQL:
  - First, one statement reads the distinct raw `model_name` values in the filtered window.
  - The handler resolves their rates through the same `lookup_cost_config` / `CatalogPricer` (`handlers/coding_agent_pricing.py:51-145`).
  - The rates go to the reader as a typed DTO declared in `ports.py`, so the repository never imports the service.
  - The SQL cost key is the declared SQL twin of `CatalogPricer.price`: same token-kind-to-rate table, cache-split clamp, `tokens <= 0` skip, and missing rate counting as 0, bound as float8.
  - The key, the model list and `get_session_model_costs` (`reader.py:538`) read one shared token grouping per (session, raw model): `cost_daily` plus the subagent totals in `session_usage`.
- `ctx_per_call` keeps its current SQL key. Its tie-break, and every other `session_id` tie-break, is `session_id COLLATE "C"`, so SQL tie order matches Python codepoint order.
- **Search** is a case-insensitive substring match against the stored `first_prompt`, `session_title`, `repository` and `branch`, for every sort and for the framework path. `%`, `_` and `\` are matched literally, and a NUL returns an empty page.
- **Framework**: SQL returns all ordered window ids with their skill names, built on `_sessions_cte`'s list scope. Python classifies them with `classify_delivery_framework`, keeps the matches in SQL order, counts them for `total`, and slices out the page. Framework combined with search uses the search rule above, so it differs from today.
- `total` stays an exact count over the window.
- **Unpriced-model metadata.** `metadata.unpriced` and `catalog_source` (`rest_api/routers/cli_analytics.py:713`) keep today's scope. For `start_time`, `ctx_per_call` and search-only requests they cover the models of the page's rows (taken from rows already loaded, no extra window query). For the cost sort and the framework filter, which already read the whole window, they cover the whole filtered window. Both follow the same token-aware rule as `CatalogPricer.price` (`coding_agent_pricing.py:117-145`): a model is unpriced when it has no catalog entry and a positive token count in some kind, or has an entry whose rate is missing for a token kind it used. The window-wide flags return one row per raw model, aggregated (`bool_or`) over the shared (session, model) token groups that the cost key reads, so the cache split is clamped on a group's sums exactly as `CatalogPricer.price` does and the flags cannot disagree with the key. *Amended 2026-11-06 (MR review CR-002, CR-005, user decision): "non-zero" became "positive" for an uncatalogued model, so `price()`, its catalogued branch and the SQL flags (`bool_or(tokens > 0)`) share one rule; the change applies to every `CatalogPricer` caller (Cost and Efficiency views included, AC17); the served `cost_usd`, `cost_available` and `bloat_pct` are unchanged, and `metadata.unpriced` differs from before only for negative-only sums, which ingest does not store.* *Amended 2026-11-05 (code-review r9 CR-001, user decision): the text asked for a model-level aggregation that bypasses the groups; a per-row clamp gave different flags than the key for a split spread over several rows of one group.* *Amended at implementation (user decision, 2026-11-04): the original text required whole-window reporting for every sort, which cost about 11 s on a 1M-session window and widened `main`'s page-scoped behaviour.*

The served `cost_usd`, `cost_available` and `bloat_pct` are still priced in Python by `price_session_models` for the page rows. Nothing else changes: response shape, router parameters, viewer scope (always first in `sel`), and the Cost and Efficiency views. *Amended 2026-11-05 (code-review CR-004, user decision): the router contract gains one answer. A Sessions query that outruns the pool's 30 s statement timeout (`asyncpg.QueryCanceledError`) or the client-side command timeout (`TimeoutError`) is answered with HTTP 504 and a clear message, not a 500; the log line records the sort, the framework (cut to 80 characters), whether a search was given and the error type. Nothing else in the contract changes.*

**S1: index.** A new CLI analytics Alembic revision after head `a1c1a0000007` runs `SET LOCAL lock_timeout = '5s'` and then `CREATE INDEX IF NOT EXISTS` on `session_dims (started_at)` (and on the two shared-list indexes of AC8, so three in all, under that one lock) inside the normal transactional migration, so a blocked build fails fast and the next job retries. The setting lasts for the rest of the migration transaction, so this revision stays last in the chain or resets the timeout after the statement. The storage guide gains a runbook step for large installs:

1. Pre-build the same index with `CREATE INDEX CONCURRENTLY` under the same name.
2. Check `pg_index.indisvalid`. If the index is invalid, `DROP INDEX CONCURRENTLY` it and rebuild.
3. Upgrade. The migration then does nothing.

The runbook also states the row count above which the pre-build is required, derived from the measured lock wait and build time (AC18).

**S5: connection use.** A Sessions request holds one pool connection while its window statements run (one after another) and at most two while its detail statements run (bounded concurrency of 2), through port methods `bounded()` (the first connection, waited for like any other) and `widened()` (a second one around the details, waited for only 0.5 s; a request that finds none free runs the details on the one it has, so requests holding one connection each cannot deadlock a nearly exhausted pool). Both are released before pricing and row building. *Amended 2026-11-06 (MR review, Aliaksei Piatrovich): the first version acquired both up front and held the second idle through the window phase, which is the long one (8 to 28 s on the slow paths); four such requests would have held a pool of 8 and starved ingest.* *Decided by the requester (2026-11-04) after AC16 left both candidates short of the ingest bar at K = 7: bounded-2 shipped, the pinned candidate and its port method were deleted; no switch, no setting.* Measured (stand-ins, noisy dev DB, no `main` baseline): bounded-2 at K = 4 had ingest acquire p99 33 ms and 0 ingest 503s; at K = 7 both candidates failed because a pool of 8 is exceeded by the pool hog, the refresher and seven slow requests.

## Accepted trade-offs

- **Search, from AR-2.** On cost-sorted and framework-filtered lists, search now matches text inside pasted prompt content, as the default sort already does. Those two paths stop matching the cleaned prompt, which is a deliberate departure from "filters unchanged". Going back to cleaned-prompt search later needs a stored column and a backfill.
- **Start order, from AR-5.** The list is ordered by the hook start (`started_at`), while each row shows the activity start: the earliest of the hook, activity and OTel times (`reader.py:855`). Rows that began seconds apart can look out of order. Paging stays stable.
- **Unpriced models on default and ctx sorts.** Unchanged from today: page-scoped. A model that only sessions on other pages use is not reported on those sorts (the cost sort and framework filter do report it).
- **Framework name sets and page/total snapshots (accepted 2026-11-05, code-review r9 CR-002 and CR-003, user decision).** (1) The framework filter loads the distinct classifier name sets of the window into Python and sends them back as one JSON parameter; the sets are per-session combinations, so their number can approach the session count on a very large window, with memory and statement size growing while the request holds its connection. Not reproduced on the dev data; a cap with a typed error, or classifying in batches, is the follow-up if it shows. (2) The `start_time` page and its count are two statements on the request's connections, not one snapshot, so a session bound or deleted between them can make `total` disagree with the page for that request; `main` has the same shape. A repeatable-read read-only transaction around both is the follow-up if it shows.
- **Index build without the pre-build.** A plain build needs a SHARE lock on `session_dims`, which waits for open writers (ingest's session binding, `session_binding.py:73-79`, and refresher rollup batches) and blocks later writers while it waits and builds. Worst case: the wait for running writers, capped by the 5 s `lock_timeout` (the build then fails and retries), plus the build once the lock is held. Ingest bindings answer 503 while blocked (plugins retry). Startup of the pod running the migration is also delayed. The measured figures (AC18) go into the runbook.
- **Stored activity facts (2026-11-06).** (1) Until a pre-existing session is derived (the maintenance job: 5,000 sessions per transaction, 120 s a run, 600 s while more than 50,000 sessions lack their facts, hourly; nothing is run by hand) lists are exact but pay the old per-session probes for it; `CLI_ANALYTICS_MAINTENANCE_INTERVAL_MINUTES` can be lowered during the rollout, and `VACUUM (ANALYZE) session_dims` helps once the backlog is gone. (2) `has_activity` is kept at refresh time, so a session whose rollup rows all pass retention stays active until the session itself is purged. (3) The columns are indexed, so the refresher's updates to them are not HOT; each pre-existing row is updated once by the backfill and the table needs a vacuum afterwards. (4) `resumed` follows the start day the refresh saw. (5) Production timings are not measured: the dev database is synthetic (few continued sessions, almost no raw records), so the resumed arm is a lower bound and the candidate arm's cost grows with the sessions that started on the window's first day.

## Assumptions and risks

- Assumption: SQL float8 and Python float sums agree on order except at near-ties, which fall back to `session_id COLLATE "C"`.
- The framework path still grows with the window (ids, skill names and model flags, one classifier subquery per session). Only the detail queries shrink.
- Every sort adds one statement that reads the window's token rows (`cost_daily` across all day partitions, plus `session_usage`), and its full time adds to the 825 ms budget and to how long the connection is held.
