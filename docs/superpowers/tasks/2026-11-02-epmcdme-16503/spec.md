# EPMCDME-16503 Save-time Contract Linker: Model, Simulation and Outcomes

Full AC text: the ticket (AC ids below are the ticket's). Parent spec: Workflow Node Contract Validation technical spec v6.1 (16503 corrections, cited as "parent §n"). Research: `technical-analysis.md`. Correction plan and test map: `../2026-11-09-epmcdme-16503-fix-cx/plan.md`.

## Goal

When the linker is switched on, every save or dry-run simulates, across the whole workflow graph, what data each node finds in the shared context and checks it against what nodes declare or derive as needs. A broken hand-off is reported on the responsible node before the workflow runs. Today `WorkflowExecutor.validate_workflow` (`src/codemie/workflows/workflow.py:224`) checks structure, cross-references, resources and graph compile only, and stops at the first failing stage. Runtime behaviour must not change.

## Design

- **Keys.** `WorkflowState` (`core/workflow_models/workflow_models.py:380`) gains `input_schema` and `validation`, declared leniently so that loading and running a stored workflow never fails on them: `validation: Optional[str]`, and `input_schema` keeps its raw value (`Optional[Any]`, documented as JSON text). Allowed values and shape are enforced only in the schema stage (YAML-schema enum for `validation`, `type: string` for `input_schema`, plus `check_input_contract`) and in the linker. Workflow-level `validation` and `require_input_contracts` are not declared fields: the linker reads them from the `WorkflowConfig.yaml_config` text through one function, `read_contract_settings`, which applies the defaults (parent §6.1, §6.2). `parse_execution_config` is left alone for them; no columns, no migration. The mode enum is defined once in `workflows/constants.py` (beside `WorkflowErrorType`), imported by the contracts models, and a test asserts it equals the enum in `execution_config_schema.yaml`. Key names are fixed (D4); each key is added to that schema.
- **Structural check (AC-16, parent §6.4).** `input_schema` must parse as a JSON object with root `type: object` and a `properties` object whose every entry has a `type` from the flat model (string, number, integer, boolean, object, array, or a list of these that may include `null`). `required`, if present, may name only keys of `properties`. Every other keyword is accepted and ignored (AC-8). Accepted: `{"type":"object","properties":{"doc":{"type":"string"}},"required":["doc"]}`. Rejected: `{"doc":"Title"}`, `{"type":"object"}`, arrays, scalars, a non-string value, unparseable text. One function, `check_input_contract(text) -> problems`, lives in a module with no `core.*` import; `validation/schema.py` wraps its problems in a `schema_validation` error with `state_id` and path `input_schema` (as in `schema.py:131-148`). It runs on every state that carries the key, reachable or not, in every mode, including with the linker off (parent §6.5). Text over 64 KiB or nested deeper than 32 levels is rejected before parsing; `ValueError` (parent of `JSONDecodeError`, also raised by over-long integer literals) and `RecursionError` are caught; `$ref` is never resolved.
- **Module.** New package `src/codemie/workflows/contracts/` (sibling of `validation/`, so importing it never runs the validation layer or services), re-exported from `validation/__init__.py`. It holds the models, contract reader, requirement derivation, node-effect functions, availability simulator and mode policy. It imports only leaf modules (`workflows.constants`, marker constants in `workflows.models`, `core.workflow_models`), never `nodes/*`, services or `codemie.agents`, and no module under `core/` imports `workflows.validation`. It mirrors the runtime rules (`base_node.py`, `workflows/models.py`, `workflow.py`, `tool_node.py`, `transform_node.py`, `dynamic_value_utils.py`, `utils.py`) and never edits them. Node effects are one pure function per node kind selected from a table; a kind with no entry is an unknown source, so a new kind is one function and no change to the propagator. Edges come from `WorkflowNextState.leads_to()` (`workflow_models.py:292`). The dormant `config_yaml_validation.py` and `config_resources_validation.py` are not touched.
- **Contract classification.** Schema-form means what the runtime accepts (`AssistantService.load_and_validate_schema` -> `validate_json_schema`, `assistant_service.py:696-704`): a string `type`, a `properties` object, Draft-7-valid. A JSON-array example is a "list contract" whose names come from its dict items; a list contract with no dict items (for example `["List of found features"]`) is an unknown source with a WARNING on the producer. Anything else that parses as an object is example-form, except that an object carrying schema keywords at the root but failing the schema check, such as `{"type":"object"}`, is invalid (parent §3.1), as an input or an output contract (as `input_schema` it is rejected by AC-16). Text that does not parse is invalid, read with lenient key recovery (parent §3.1). `contracts/` cannot import `codemie.agents.utils`, so agreement is a parity test, not a call.
- **Derived requirements** (parent §3.2, §3.4). Each is a requirement of kind "derived", always evaluated, also when the node declares an input contract (AC-18). **Coverage rule (parent §4.4, §4.5, AC-21), stated once:** a node is covered only when it has a declared input contract or a derivable one: placeholder names (S1), context `extract` roots (S2), or a tool whose args schema was obtained (S3, AC-13, AC-14). Transition requirements are checked but never make a node covered, and neither do the UNVERIFIED bindings of a tool without a usable schema. An agent or custom node with no declared contract and no placeholders is uncovered.
  - Agent placeholders: when `resolve_dynamic_values_in_prompt` is on, supported free output references form a derived contract (AC-S1). A Jinja parser follows the scope of each occurrence. Only plain names and dotted attributes contribute their root name. Macro parameters, loop and `with` targets, assigned locals, and Jinja globals do not create context requirements. A read before assignment can still be free. Filters (including `default`), calls, subscripts, and expressions inside control tags remain excluded. Comments and raw blocks are literal text. A parse failure creates no derived requirements; the runtime returns the original template on a rendering error.
  - Transform: the root key of each `extract` mapping that reads the context is a required input, with `input_key` as the root when set. `template`, `condition`, `script` and `array_map` mappings and sources other than the context (`messages`, `user_input`, `state_schema`) give none (AC-S2).
  - Tool bindings: non-empty state bindings replace tool bindings entirely; absent and empty state bindings use tool bindings. Agent tasks and template bindings use the same Jinja analyser. Bound names are looked up in the context, or inside `context[input_key]` when the tool sets `input_key`, whose contents are opaque in the flat model, so they are UNVERIFIED. The first node of an iteration also sees the item's fields (parent §2.6, §2.3; AC-13, AC-S3).
  - Platform keys: `file_names` and `propagated_headers` are always optional known sources, seeded at the entry (parent §3.5), so a binding to them is never "not guaranteed" (AC-S4).
  - Transitions: condition/switch identifiers and the iteration key are requirements on the node's own output (AC-37). They do not make the node covered (coverage rule above).
- **Simulation (parent §4.1, §4.2).** One forward pass over the reachable graph, linear in edges, not a replay of paths. Nodes are ordered in graph order with back-edges marked (an edge to a node already on the current path). The abstract context maps each field to a state: status (available / partially available / removed / possibly removed / possibly present), provenance (possible producers; the removing node and mechanism), scope (global or inside an iteration scope), and type (possible top-level types with optionality, and whether certain), plus an "unknown contribution" marker. The transfer rules of parent §4.1 are applied as written: initial-input seeding, output spread by contract form, explicit output key, output writing off, the three resets, accumulation, iteration branch, branch convergence and cycles. One exception, where the runtime differs from the parent table: with output writing off, only a full reset removes anything; keep-current and selective resets are not applied (`base_node.py:685-701`). This divergence is fed back to parent §2.4/§4.1 with the AC-38 correction. Alternatives and parallel branches merge differently: on alternatives a field written on some only is partially available; on parallel branches any guaranteeing branch makes it available, two or more writers give a WARNING, and a removal races a write. Cycle rule: a back-edge keeps fields guaranteed before the cycle and not removed inside it, and fields produced only inside the cycle become unknown (AC-11); there is no visit counting or fixed point. A work cap of 100,000 abstract operations turns the remaining requirements into UNVERIFIED. The linker runs on the caller's thread, as the existing stages do.
- **Entry points and position.** `link_workflow_contracts(config, resolver=None) -> ContractLinkReport` is the public entry. `config` must be a `WorkflowConfig` on which `parse_execution_config()` has run; a state that is not a `WorkflowState` gives one "could not analyse" record. `validate_workflow(..., link_contracts: bool = False)` keeps its return type; a second method, `validate_workflow_with_report(..., link_contracts: bool = False)`, returns the graph and the report, so the API sibling runs the simulation once per request. The linker runs after the structural layers pass, resource check and graph compile included (parent §7.3), and collects every contract error across the graph before raising: one `ValueError` (string or json format) carrying all of them, not the first. With `link_contracts` off, no analysis runs and no findings exist; the AC-16 check and the new keys' schema still apply. The default is off, so after this MR a workflow with none of the new keys sees no change on any save path; the platform flag (AC-39) is the API sibling's, which passes its value at the save and dry-run callers, and this parameter is not that flag. The report is a per-call value, never kept at class, module or ContextVar level.
- **Failure isolation.** An unexpected exception in derivation or simulation is logged and recorded as one UNVERIFIED "could not analyse" record, and goes through the mode policy: in warn it never rejects; under workflow or state strict (AC-19) it becomes an ERROR and the save is rejected with the linker error type, not a bare 400. A failure while looking up one tool degrades only that tool (below). Workflows with none of the new keys cannot reach the rejecting path (AC-22).
- **Error type.** AC-16 rejections use the existing `schema_validation` type. Linker rejections use one new `WorkflowErrorType` member, `contract_validation` (parent OQ-2); the string is fixed here and mirrored by the UI whitelist (UI sibling).
- **Report.** `ContractLinkReport` carries (a) one record per requirement or finding: `kind` is one of declared / derived / coverage / contract-form (the producer notes of AC-17 and the AC-44 conflict) / convergence (AC-6) / analysis-failure; `outcome` is the raw result (OK/ERROR/WARNING/UNVERIFIED) and `reported_as` (blocks / warning / info) is the class after the mode policy, kept separate; plus consumer state id and path, and provenance (producers, sources checked, overwriting or removing node with mechanism); (b) coverage data: validated count, reachable total, uncovered node ids, unreachable node ids, and the effective mode per state; the AC-21 ERROR is a record of kind "coverage" on the uncovered node. The mode policy sets `reported_as` for each record. Shaping into the `coverage` response object and issue fields is the API sibling's job (parent §7.2, §7.4). Messages come from fixed templates; names (state ids, parameter names, field names) are quoted, capped in length, and any character outside a safe set, including `< > &`, is replaced, because the string error format joins messages into `<br>` markup; binding values and example-form text are never echoed.
- **Tool parameter schemas.** Today the save's tool lookup is `ToolsService.find_toolkit_for_tool` plus one MCP `tools/list` call for static MCP servers (`resources.py:376-386`); neither reads parameter schemas. A per-call resolver, created by `validate_workflow`, supplies them and is the only place that touches services; it hands `contracts/` only a set of mandatory parameter names or "unknown".
  - Static MCP tools: the resource stage records the args schema of the tool it already selects (`resources.py:376-384`) in the resolver, keyed by the owning `WorkflowTool.id`. No second MCP call.
  - Built-in tools: `ToolDiscoveryService.find_tool_by_name` (`service/tools/discovery/tool_discovery_service.py:62`) is a new lookup made by the linker (the user's AR-6 answer), not one the save performs today. It checks provider tools first, which builds provider toolkits and reads Postgres, so it is not free. It is memoised per save by tool name, asked only for tools whose requirement needs a schema, and bounded by a separate lookup budget (25, provisional, to be confirmed by measurement) rather than counted toward the work cap.
  - UNVERIFIED, never ERROR, node uncovered unless it declares an input contract, and its UNVERIFIED bindings do not cover it (AC-38): dynamic MCP servers (`resolve_dynamic_values_in_arguments`), plugin tools (`_` prefix), provider tools (empty schema), any empty or missing schema, and any exception from the lookup, which degrades that one tool only.
  - A declared `input_schema` is never a source of mandatory parameters (parent §3.4, DEC-3). The resolver is built only after the resource stage, which has already rejected tools the user cannot use.
  - An unreachable MCP server or an empty tool list is handled by the resource stage as today (it raises, or reports the tool unavailable), so the linker never sees it; this ticket does not change the resource stage's behaviour.
- **Tests.** Table-driven, one case set per AC and per spec-added AC, in `tests/codemie/workflows/validation/`. Also:
  - AC-14 with a built-in tool and a mocked MCP tool (the corpus has 66 tool states, 22 MCP and 44 plugin, and exercises neither); a patched resource stage reports "no schema" explicitly; a lookup that raises degrades one tool; `Provider.get_all` is called once for N states with the same built-in tool.
  - Two concurrent validations get their own reports.
  - A malformed-shape fixture set (null `next`, scalar `output_schema`, transition to a missing state, a non-`WorkflowState` state) gives "could not analyse" or an existing error, never an unhandled exception; every generator-accepted fixture gives no linker ERROR; a parameter named `<img src=x onerror=1>` is sanitised and an AC-15 message omits the binding value.
  - A stored workflow with `validation: foo` and `input_schema: {a: 1}` loads through `get_workflow` and `create_executor` and is rejected only by `validate_workflow`, at the schema stage, with state id and path; a stored workflow with none of the new keys and each built-in template are not newly rejected.
  - Over-long digit literal and deeply nested arrays in `check_input_contract`.
  - Import direction: `import codemie.core.workflow_models` and `import codemie.workflows.validation` each succeed first in a fresh interpreter; `contracts/` imports only the leaf modules.
  - Parity against the real runtime on the same fixtures: each mirrored write rule (store_in_context off plus output_key, append, keep_current, reset keys, delete-wins, `.result` unwrapping); `store_in_context: false` combined with each of the three resets (full, keep-current, selective), through the real reducer path; the reader's classification against `load_and_validate_schema` (including `["List of found features"]`, `[{"document": "Document title"}]`, `type: ["object","null"]`, `{"type":"object"}` as an invalid contract, and a list contract with no dict items as an unknown source with a WARNING on the producer); each transform `on_error` strategy; the resolver's mandatory set against the tool class's own fields for the built-in tools in the corpus; and a test that enumerates `WorkflowState.model_fields` and `WorkflowNextState.model_fields` against a classified list (affects context or not), so a new field fails the build until classified.
  - Timing: linker time on the largest template and on a synthetic 200-state chain with 20 condition diamonds at most 5 times the current `validate_workflow` time (resource stage patched) and under 2 s; with the real resolver on 20 distinct built-in tool states, warm under 1 s and cold recorded. If a limit fails, the work cap is lowered.
  - The OpenAPI baseline is regenerated (`router_guards/regenerate_baselines.py`) because `WorkflowState` gains fields. AC proofs call `validate_workflow(link_contracts=True)` or the report entry directly.

## Acceptance criteria (ticket ids, condensed)

**Source locations (16503-C).** Requirements and report records carry an optional immutable `ContractLocation`. Its section is `states`, `tools`, `custom_nodes`, or `workflow`; the owner ID identifies the configuration item, while `consumer_state_id` still identifies the consumer. Path segments retain strict string keys and integer list indices. Numeric strings, punctuation, Unicode, and long keys remain unchanged. Unknown locations are explicitly `None`. Synthetic output-contract, coverage, transition, convergence, and graph findings carry the known source location. Policy conversion, serialization, and copies preserve it. The API sibling resolves YAML lines; the linker does not import YAML lookup or REST models. Existing diagnostic paths and field meanings stay unchanged.

- **Availability.**
  - AC-1: no contracts anywhere means the save succeeds and requirements are UNVERIFIED. A fully satisfied workflow has no issues and full coverage (coverage data in the report). An uncovered reachable node never blocks.
  - AC-2: a known producer or an entry-node declaration gives OK with the producer named. An intermediate node without an output contract makes the type UNVERIFIED, naming the producer and the possible overwriter.
  - AC-3: no source produces the field and every source is known: ERROR-class "not guaranteed by the contracts", naming the sources checked.
  - AC-4: a field produced and then removed by reset, or never written because output writing is off, with all sources known: ERROR naming the node and the mechanism.
  - AC-5: any unknown source on the path, including an undeclared initial input, gives UNVERIFIED, never ERROR.
  - AC-6: conditional/switch gives WARNING naming the alternatives lacking the field, and OK when all have it. Parallel: any guaranteeing branch is OK; two or more writers is WARNING; removal in one branch with no other writer is ERROR; removal with another writer is WARNING.
  - AC-7: a type mismatch or optional/nullable source is WARNING. An example-form or recovered-key source has presence checked and type/optionality UNVERIFIED.
  - AC-8: nested properties, items, enum, format, bounds and similar keywords yield no finding.
  - AC-9: a first-level iteration sees only the context-filtered fields, and a nested one sees its parent's context unfiltered. A required field excluded by the filter is ERROR if all sources are known, else UNVERIFIED. The item is the first node's task only. Dict item fields become context from the second node. A first-node requirement on an item field is UNVERIFIED, never blocking in warn. Cases: filtered first-level, nested, transform, agent/tool.
  - AC-10: with output writing off and an explicit key, only that key is available (string). With it on, the key plus top-level fields. Accumulating transitions give list-typed keys. A sub-workflow node is a known source only with a declared output contract. A list output contributes the union of its dict items' keys.
  - AC-11: a field produced only inside the consumer's own cycle is UNVERIFIED. Fields available before the cycle and not removed inside it are evaluated normally.
  - AC-12: unreachable nodes are never sources, are excluded from coverage and are not linked (the AC-16 structural check still covers them).
  - AC-37 (D3): identifiers in condition/switch expressions and the iteration key follow the not-guaranteed rule against the node's own output contract. No usable contract gives UNVERIFIED. A key declared non-array gives WARNING. A list-typed output gives no iteration-key finding, including placeholders like `_`, and `test_cases_from_unstructured_data_template` saves with none. A dict contract listing the key gives no finding; one that does not list it gives a finding naming the key.
  - AC-44: a transform is a known source with its mapping output fields even without a schema. Types follow the real mapping and supported schema-coercion paths, with a schema-form state output contract on top. An own-schema declaration that the runtime does not enforce cannot invent a type guarantee. Numeric coercion accounts for Boolean inputs. Default fallback values keep their own types because the runtime does not coerce them through the own schema. A state-level conflict is WARNING. Fields are guaranteed under fail-fast and optional under strategies that can drop them. Fallback output keys are added as optional.
- **Spec-added criteria** (derived from parent v6, not ticket ACs; they exist so coverage and derivation are testable).
  - AC-S1 (parent §3.2, §3.4): with `resolve_dynamic_values_in_prompt` on, each supported free output reference creates a requirement for its root name and the node is covered. With the flag off, or no supported free references, there is none. A missing plain name renders empty; a missing dotted root can cause the renderer to return the original template. The existing diagnostic label is retained for compatibility; it is not a promise of identical runtime behaviour for every Jinja expression.
  - AC-S2 (parent §3.2): each `extract` mapping that reads the context makes its root key a required input, with `input_key` as the root when set. A transform without such a mapping is uncovered unless it declares an input contract; its transition requirements do not cover it.
  - AC-S3 (parent §2.6): non-empty state bindings replace the tool's bindings entirely; absent and empty state bindings use tool bindings. With `input_key`, bound names resolve inside `context[input_key]` and are UNVERIFIED. The selected binding owner supplies the source location; the consumer state ID stays unchanged.
  - AC-S4 (parent §3.5): `file_names` and `propagated_headers` are always optional known sources; a binding to either is never "not guaranteed".
- **Tool bindings.**
  - AC-13: a binding to a context field nobody produces follows the not-guaranteed rule on the binding path.
  - AC-14: (a) non-empty bindings that omit a mandatory parameter of the tool's args schema are ERROR-class from configuration alone. (b) With empty or no bindings, name-matched resolution gives ERROR if removed, the not-guaranteed rule if absent, and OK if available. Mandatory parameters come only from the tool's args schema.
  - AC-15: a literal/template binding plus a same-named context field is WARNING (the context value wins at runtime).
  - AC-38: no usable args schema at save means UNVERIFIED, never ERROR, and the node is uncovered unless it declares an input contract (binding records and transition requirements do not cover it). Cases: dynamic MCP server, plugin or provider tool, schema empty or failing to load, lookup exception. The linker makes no MCP call beyond the resource check. An unreachable MCP server is already reported by the resource stage and never reaches the linker.
- **Contract structure.**
  - AC-16: see Design, Structural check.
  - AC-17: in default mode, schema-form is a full contract and example-form is names-only, never rejected. Invalid with recovered keys is names-only with UNVERIFIED types and an advisory note on the producer. Invalid with none is an unknown source with a WARNING on the producer. Workflow strict requires schema-form output contracts, or the producer gets an ERROR. A transform meets this through its own schema or a state-level schema-form contract. A state-level strict override puts an ERROR on the consuming state naming the producer.
- **Modes.**
  - AC-18: in default mode, an ERROR-class finding on a derived requirement saves and is `reported_as` warning, marked "certain runtime failure" except the not-guaranteed kind, which is marked accordingly, and a missing placeholder name (AC-S1), which is marked "renders empty". An ERROR-class finding on a declared requirement rejects. Derived requirements are always fully evaluated, even when a contract is declared.
  - AC-19: in strict mode, any ERROR-class finding, WARNING or UNVERIFIED in scope rejects.
  - AC-20: a state-level mode governs only that state's own requirements. Upstream findings are raised on it, naming the producer. Other states inherit the workflow value.
  - AC-21: `require_input_contracts: true` means an uncovered reachable node (coverage rule, Design) is an ERROR (a "coverage" record on that node) and rejects in warn and strict. False means it is only listed.
  - AC-22: existing workflows and built-in templates with none of the new keys gain no rejection (records whose `reported_as` is blocks; raw `outcome == ERROR` is not what is counted here, only AC-43 counts raw ERROR) and no runtime change, only additive warnings and coverage (proved with `link_contracts=True`).
  - AC-39 (this ticket's part): linker off means no analysis and no findings, and AC-16 plus the key schema still apply. The platform flag is the API sibling's.
- **AC-40.** The selected base includes the EPMCDME-16499 engine fix. Full reset plus an explicit output key must complete without an exception with output writing on or off. After the real reducer, only the output key remains, with the expected value. The linker must report the same available keys. With output writing off, keep-current and selective resets preserve the previous context; full reset still clears it before the explicit output key is written.
- **AC-43 / D2.** Running the linker over the built-in templates gives no new errors, counted on raw `outcome == ERROR`, and the number of warnings (records `reported_as` warning) is checked against a ceiling recorded per template as well as in total. A small loader reads `config/templates/workflow/*_template.yaml` through `WorkflowConfigTemplate.from_yaml` (`workflow_config.py:377`), calls `parse_execution_config()`, and fails if it finds fewer than 64 templates or any non-`WorkflowState` state (`from_yaml` has a `model_construct` fallback). It calls the linker directly with no tool schemas, so tool bindings are UNVERIFIED and missing schemas are tolerated.
  - The EPMCDME-16499 shared save harness and corpus loader are required. Every template must complete the shared save pipeline without a new blocking finding.
  - The warning ceiling is recalculated from the corrected corpus. A ceiling increase must have a documented cause; it must not hide a regression.

- EPMCDME-16503 was rebased on engine base `fb45cbfa668646b10f299809c3e44a7b2b003ccf`. The correction run records the exact source head and commands.

The author of this MR scans stored `workflows.yaml_config` and the `states` JSON for `input_schema`, state `validation`, and workflow-level `validation` / `require_input_contracts` before release and records the result in the MR text.
- Delivery: the tool-binding half (resolver, resource-stage feed, AC-14, AC-38 and their tests) may land as a separate commit inside this ticket; the linker works without it, with `resolver=None` and tool bindings UNVERIFIED.
