## 1. Original Context

Repository: codemie (backend only). task_context (verbatim ticket EPMCDME-16431, Bug):

Summary: Agent with Confluence integration sends text but cannot upload agent-generated JSON files as attachments

Description: An agent configured with a Confluence integration can send text to Confluence but cannot upload a JSON file generated by the agent as an attachment. A user needs an agent-generated JSON file to be delivered through the Confluence integration as a file attachment, not merely as text. The point at which the file is lost, and whether the integration currently supports this operation, have not yet been established.
Preconditions: agent has working Confluence integration; agent generates a JSON file in its workflow; agent has access to a Confluence destination.
Steps: configure agent with Confluence integration and have it generate a JSON file; ask it to send text (works); ask it to upload its generated JSON file as an attachment; check whether file appears as Confluence attachment.
Expected: agent-generated JSON file is uploaded as an attachment to the intended Confluence destination, subject to permissions.
Actual: text works, generated JSON file not uploaded.
Affected areas: Agent-to-Confluence integration; agent-generated file handoff and Confluence attachment handling.
Acceptance Criteria:
1. An agent with required permissions can upload a JSON file it generated to the intended Confluence destination as an attachment.
2. The resulting Confluence attachment retains the generated file's name and content; sending contents as page text does not count.
3. If upload fails or is unsupported, the agent reports that clearly rather than implying the file was attached.
4. Existing text-sending behavior continues to work.

Jira comment (hypothesis, NOT verified): The Confluence tool already uploads attachments (confluence/tools.py:216-265) but only for files the user uploaded; files an agent generates never reach the list the tool reads. With no file the call falls through to a plain request (tools.py:165-171), a name matching nothing attaches all files, an empty file is dropped silently. Any URL containing /attachment goes to upload path when files exist, with no HTTP method check. File handling is shared with ~25 tool files (Jira, XWiki, Azure DevOps, SharePoint, ...) so it should stay untouched. Decisions: generated file = produced by the agent in current conversation incl. earlier messages; fix Confluence only, strict file-name matching (no all-files fallback), "not found" error lists available file names; upload path only for POST/PUT to .../child/attachment, GET/DELETE unchanged; partial multi-file success lists attached and not-attached separately; empty file gets its own message. How the generated file reaches the tool is to be chosen at plan stage. Open questions: same-name generated vs uploaded file; JSON only vs any type.

## 2. Codebase Findings

### Existing Implementations

**Purpose A: attach a file to a Confluence page from an agent**
- `src/codemie_tools/core/project_management/confluence/tools.py` `GenericConfluenceTool(CodeMieTool, FileToolMixin)` (l.85). Single generic REST tool (method, relative_url, params, is_markdown). `execute` (l.133) and `_execute_for_script` (l.143) both call `_perform` (l.154); both paths share the attachment logic.
- `_perform` l.165-171: if `_is_attachment_operation(url)` -> `_resolve_files()` -> if non-empty -> `_filter_requested_files` -> if non-empty -> `_handle_file_attachments`. Otherwise falls to the normal request at l.173-189 (GET/other, `confluence.request(... data=payload_params)`), so an attachment POST with no files is sent as plain JSON body and returns the HTTP result with no "no file" error.
- `_is_attachment_operation` l.212-214: `"/child/attachment" in url or "/attachment" in url`; no method check (`method` is not passed in). Matches GET/DELETE of `/rest/api/content/{id}/child/attachment/{attId}` too, and `/download/attachments/...`-style paths containing `/attachment`.
- `_handle_file_attachments` l.216-265: per file `confluence.attach_content(content, name=file_name, content_type=mime, page_id, comment=None)` (atlassian lib). Success -> one line per file `Successfully attached file '<title>' (ID ..) to page <id>`; falsy response -> ToolException; any exception is re-wrapped as `Failed to attach files to page {id}: ...` (l.264-265), so a mid-list failure discards the successes already uploaded (no partial report). Returns `str` (not HttpResult).
- `_extract_page_id` l.267-300: regex `/content/(\d+)` from URL, else `page_id`/`pageId` in params, else ToolException.
- Tool description `confluence/tools_vars.py:31,40,51` advertises attaching files via POST `/rest/api/content/{pageId}/child/attachment`; `ConfluenceInput.params` (tools.py:65-66) documents `{"file": "x"}` / `{"files": [...]}`. Nothing tells the model where generated files come from.
- Config `confluence/models.py:27` `ConfluenceConfig(CodeMieToolConfig, FileConfigMixin)`; `FileConfigMixin.input_files` (`codemie_tools/base/models.py:205-208`, `exclude=True`) is the only file source.

**Purpose B: how files reach a tool (uploaded files) - hypothesis claim "only uploaded files" HOLDS**
- `FileToolMixin` `src/codemie_tools/base/file_tool_mixin.py`: `_get_supported_files` (l.84) reads `self.config.input_files`; `_resolve_files` (l.112-141) returns `{name: (bytes, mime)}`, silently excluding files with empty content (l.131-134, only a `logger.warning`) or whose `bytes_content()` raised (l.135-138). `_filter_requested_files` (l.143-184): no `file`/`files` param -> returns ALL files (l.170-172); names given but none match -> `result = filtered_files if filtered_files else all_files` (l.182) -> ALL files; some match -> only those, unmatched names only logged (l.180).
- Injection: `ToolkitService._inject_runtime_dependencies` `src/codemie/service/tools/toolkit_service.py:918-927` sets `stored_config.input_files = file_objects` when config is a `FileConfigMixin` and `file_objects` truthy; called at l.864 inside the per-tool config build. `file_objects` comes from `_get_file_objects_from_request` (l.135-151) -> `build_unique_file_objects_list(request.file_names, conversation_id, history_index)`; `assistant_service.py:642-706, 996-1015` builds the same for agent build.
- `src/codemie/core/utils.py:505-528 _process_file_names_to_objects` loads content via `FileService.get_file_object`; on load failure it adds a content-less FileObject. `_collect_files_from_conversation` (utils.py ~l.575-593) collects ONLY `ChatRole.USER` messages' `file_names` (comment: "an assistant message's `file_names` are files it published, not uploads"); `_should_include_message` skips messages at/after `history_index`. Pinned by `tests/codemie/rest_api/models/test_conversation_generated_files.py` (docstring "Files published during a turn ride on the assistant message's `file_names`, never on the user's"; `test_generated_files_of_earlier_turns_are_not_handed_to_the_model_as_uploads`).

**Purpose C: where agent-generated files live**
- Code executor `src/codemie_tools/data_management/code_executor/code_executor_tool.py` (`export_files` param; `FileExportService` `file_export_service.py:40-125`) and `GenerateImageTool` publish through `ArtifactPublisher` (`codemie_tools/base/artifact_publishing.py:63-82`, Protocol) implemented by `ArtifactPublisherService` `src/codemie/service/artifact_publisher.py`. With a conversation id -> `_publish_to_workspace` (writes `artifacts/<turn_id>/<name>` in the conversation's `AgentWorkspace` via `AgentWorkspaceService.publish_artifact_file`, agent_workspace_service.py:149-154; `_unique_name` adds ` (2)` suffix on collision within the same turn folder); without -> `_publish_per_user` (`file_repository.write_file`, name `<uuid>_<name>`, owner = user). Returned link is `SANDBOX_FILE_PREFIX + encoded token`.
- Per-turn recording: `ConversationService._turn_generated_file_names` (conversation_service.py:525-537) calls `AgentWorkspaceService.turn_artifact_tokens(conversation, user, turn_id)` (agent_workspace_service.py:156-166) -> stored in `ChatTurnData.generated_file_names` (conversation.py:85) -> assistant `GeneratedMessage.file_names` (conversation.py:556). This is written when the turn is saved (`upsert_chat_history`, incl. in-progress turns per its docstring), so files of the CURRENT turn are not in history while the turn runs; only the workspace holds them.
- Workspace read side: `AgentWorkspaceService.get_workspace_input_files` (l.595-603) turns every workspace file (DB rows plus conversation uploads) into `FileObject(name=workspace path, content=...)` via `_collect_input_file` (l.619-645; unreadable blobs skipped with a warning). Used for workspace scripts (l.664-690), not for tool configs. `FileSystemToolkit` passes `input_files` only to `CodeExecutorTool` (file_system/toolkit.py:75,149-155).
- Same-name collision: uploaded files are keyed by encoded token in `build_unique_file_objects`, but `FileToolMixin._resolve_files` keys by `file_obj.name`, so an uploaded and a generated file with the same name would collapse to one dict entry (last wins). Workspace-derived FileObject names are paths (`artifacts/<turn>/x.json`), not bare names.

**Who else uses `FileToolMixin` / `_filter_requested_files` / `_resolve_files`** (searched `src`): 13 tool files besides the mixin: azure_devops/wiki/tools.py (7 hits), azure_devops/work_item/tools.py, confluence/tools.py, jira/tools.py, xwiki/tools.py, sharepoint/tools.py, file_analysis/{csv,docx,email,pdf,pptx,xlsx}/tools.py and file_analysis_tool.py. The hypothesis' "~25 tool files" is contradicted on count (13 tool modules use the mixin; more modules mention `input_files`/`FileObject` for other reasons).

### Decisions Already in the Code
- Convention: tools get request-scoped files only through `config.input_files` injected by `ToolkitService._inject_runtime_dependencies` (toolkit_service.py:918); tool constructors are not given a publisher/workspace (contrast `CodeExecutorTool`, which receives `file_repository`, `artifact_publisher`, `publish_context` explicitly: code_executor_tool.py:217-232, file_system/toolkit.py:146-155). Alternative: pass workspace/publisher as tool deps. Reason: none found.
- Convention: generated files are NOT treated as uploads (utils.py collector, assistant vs user role). Reason recorded in comment and `test_conversation_generated_files.py`.
- Convention: `FileToolMixin._filter_requested_files` falls back to all files (shared l.170-182); behaviour is shared by all 13 consumers.
- Convention: artifact publish "never raises"; refusals come back as `PublishResult.reason` and are shown to the model as text (file_export_service.py:116-121).
- Workflow nodes: `workflows/nodes/tool_node.py:240-244` sets `tool.input_files = file_objects` directly on tools that have an `input_files` attribute (the Confluence tool has it on its config, not the tool, so the check is `hasattr(tool, "input_files")`).

## 6. Risk Indicators

- Shared mixin `FileToolMixin` (13 consumers, no direct tests): any change to its fallback (l.170-182) or empty-file drop (l.131-134) changes Jira/XWiki/Azure DevOps/SharePoint/file-analysis behaviour; keeping it unchanged keeps the all-files fallback in place for those consumers (see Consumers).
- Task decision "fix Confluence only / strict matching" keeps `_filter_requested_files` all-files fallback in place for the other 12 modules (Task Statements section).
- Task decision "generated file includes earlier messages" keeps the USER-only collector (`core/utils.py`) in place, which is pinned by a test; current-turn generated files exist only in the workspace until the turn is saved (conversation_service.py:525).
- Speculative: Confluence tool has no access to workspace/publisher today; handoff will need a new injection path (config `input_files`, tool deps like `CodeExecutorTool`, or workspace lookup) - choice is plan stage.
- Speculative: workspace `FileObject.name` is a path (`artifacts/<turn>/x.json`), while the model supplies a bare name; name matching and `attach_content(name=...)` (Confluence attachment name) may need basename handling.
- Speculative: same-name uploaded vs generated file collapse in `_resolve_files` dict (key = name).
- `_handle_file_attachments` wraps all errors and loses earlier successes; no partial-result reporting today.
- Script path (`_execute_for_script`) shares `_perform`; changes affect workspace scripts too.
- Guides do not document the file handoff; no existing test of the attachment path (regression risk for AC4 is on the text path, which is covered by POST tests).

## 7. Summary for Complexity Assessment

Primary change surface is the Confluence tool (`confluence/tools.py`, `tools_vars.py`) plus a handoff path that brings agent-generated files (stored in the conversation workspace under `artifacts/<turn_id>/` via `ArtifactPublisherService`) to the tool, which today only sees user-uploaded files through `config.input_files` injected in `ToolkitService`. The hypothesis checks out against the code in all claims except the "~25 tool files" count (13 tool modules use `FileToolMixin`). The shared mixin and the USER-only conversation collector are stable, tested-by-neighbours or untested contracts used widely.

Novelty is moderate: no existing non-sandbox tool receives generated files; the closest pattern is `CodeExecutorTool` taking `file_repository`/`artifact_publisher`/`publish_context`. Current-turn files are only in the workspace (not yet in conversation history), which affects how "generated in this conversation" can be resolved.

Test posture: Confluence tool tests exist but none cover attachments; the mixin has no tests; generated-file history has focused tests. Layers: tool, service (toolkit/workspace), core utils.
