**Deliberate deviation from task.md.** task.md and the story require a large result to be "limited the same way as for the model" (30,000 tokens). By explicit user decision (gate round 3) the script path has no token limit: the result goes into a script, not the model context. ## Goal

A workspace script calls platform tools through the existing SDK and gets real, complete results as proper JSON. Calls are authorized by where the script runs, use the settings the model would use, and are approved exactly as running the script is today. The echo stand-in goes away.

## Design

1. **Run context.** Frozen dataclass `ScriptRunContext` (user id, scope `assistant|workflow|none`, project, tool registry) in a new `codemie`-side module beside `service/workspace_script_bridge.py`. It flows `AgentWorkspaceToolkit` -> `ExecuteWorkspaceScriptTool` -> `AgentWorkspaceService.execute_workspace_script` -> `WorkspaceScriptRunner` -> `JobBridgeOptions` -> `JobToolCallBridge` -> `ToolCallChannel(handlers=...)`. The handler is a closure over the context. The request thread's contextvars are copied at bridge start and each call runs in a copy (LLM and logging context for tools on the channel thread).
2. **Run's tools (assistant scope).** A registry object is created where the script tool is built (`toolkit_settings_service.py:234`) and filled at the end of `ToolkitService.get_tools` (`toolkit_service.py:466`), after de-dup and the `_append_*` steps, with the final list minus the script tool, MCP tools and stream-dependent tools (`RequestUserInputTool`, tools holding a `thread_generator`); one explicit exclusion list in one module. Unfilled registry means refuse. Attached skills are covered because `_merge_skill_toolkits` feeds the same list.
3. **Workflow scope is server-derived, never from the request.** `AssistantChatRequest.workflow_execution_id` (`core/models.py:675`) is a client-supplied REST field; trusting it would let a chat user claim "any tool I am authorized for". Workflow scope comes only from a `VirtualAssistant` with `execution_id` (bare tool step; its `project` is the workflow's) or a new explicit `get_tools` keyword passed by `build_agent_for_workflow` (`assistant_service.py:772`) for stored assistants. Workflow scope wins over assistant scope for a step.
4. **Authorizer** (pure function, first match wins): script tool -> `tool_blocked`; scope `none` -> `no_context`; `assistant` -> name in registry else `tool_unavailable`; `workflow` -> resolve by name for the user in the workflow's project via `ToolsService.find_tool_by_invoke_request` (`tool_service.py:119`) else `tool_unavailable`.
5. **Handler.** Op `tool.call`, payload `{name, args}`; replaces `echo` (`DEFAULT_HANDLERS` becomes empty). Args are validated against `args_schema`; errors name fields and kinds, never values. The handler calls a new `CodeMieTool.run_for_script(**args)`, not `_run` and not `invoke`. `_run` is not modified.
6. **Structure, not strings: `HttpResult`.** The HTTP-style tools flatten status, reason and body into one string at one f-string site each: Jira (`jira/tools.py:214`), Confluence (`confluence/tools.py:163`), GitLab (`gitlab/tools.py:191`), xWiki (`_format_result`, `xwiki/tools.py:131`, serving about 22 tool methods unchanged). A new `HttpResult(str)` in `codemie_tools/base` is built from `method, url, status, reason, body` and a layout tag. Its string value is rendered from those fields at construction with the exact legacy layout; three layouts exist because the tools differ (`spaced`: Jira, GitLab; `compact`, no separators: Confluence; `body_on_new_line`: xWiki). It keeps the fields as attributes, so the script path reads them and never parses the `HTTP: ...` text. `with_suffix(text)` appends to the rendered string only, so Jira's `+=` notes (`jira/tools.py:230,232`) keep today's text and leave the structure alone.
   **Why a `str` subclass and not a plain object:** `execute()` output is consumed directly by `ToolNode` and `ToolExecutionService.execute_tool`, not only by `_run`, and several tools override `_limit_output_content` and `_post_process_output_content` (Jira, hedge, KB search, MCP). A non-`str` return would be JSON-dumped by `_post_process_output_content` (`codemie_tool.py:213-216`) and change model and workflow output. A `str` subclass passes `isinstance(str)` unchanged everywhere, so model-path output is byte-identical with no edit to `_run`.
7. **Base-class `execute_structured` (no per-tool overrides).** `CodeMieTool.execute_structured(*args, **kwargs) -> ScriptResult` has a working default: call `execute`, convert by type. `HttpResult` -> parsed body plus `http_status`/`http_reason`; pydantic model -> `model_dump(mode="json")` (covers ADO Git's `AzureDevOpsGitOutput`); dict/list/None/bool/number -> as is; `str` starting with `{` or `[` that parses -> parsed value, other strings stay strings; anything else -> `str()`. Only the HTTP body is parsed, and only as object or array. Wrapper outputs that are not plain data implement a small `ScriptValueSource` protocol (`to_script_value()`): `HttpResult` does, and so does `JiraMultimodalResponse` (`jira/tools.py:51`; it carries the `HttpResult` in a new excluded field set at line 237 and drops images). This is the one justified exception, on an output type, not an override of a tool method. No tool overrides `execute_structured` in this task.
8. **`run_for_script`.** Validate config, `execute_structured`, done. No `_limit_output_content`, no token limit, no truncation. Errors are raised, not turned into strings, and logged as tool name, code and exception type only.
9. **Envelope.** The channel's `ok/error` already separates success from failure, so no `ok` key. The `tool.call` result is always an object `{"result": <JSON>, "http": {"status": int, "reason": str|null}}`; `http` is present only for `HttpResult`. A non-2xx status is data, not an error (the model sees it too). Failures are errors with a code: `no_context`, `tool_blocked`, `tool_unavailable`, `bad_arguments`, `tool_failed` (sanitized, truncated root cause), via `ToolCallRefused(code, message)` mapped in `ToolCallChannel._answer` (`tool_call_channel.py:393`); `internal_error` stays for bugs.
10. **Transport bound for large results.** Without a token limit the only bound is the channel cap (`MAX_PAYLOAD_BYTES`, 256 KiB, measured on the JSON-encoded response). `_answer` already returns the existing code `payload_too_large` when the encoded result exceeds it (`tool_call_channel.py:412-413`); the response is written like any other, so the script gets an error at once, not a hang. We reuse that code rather than add a new one (the SDK contract already knows it) and extend its message to state the encoded size and the limit in bytes, never content. The channel encodes with `ensure_ascii`, so non-ASCII text inflates up to about 6x; the plan must check whether the pod-side write and the SDK's read accept UTF-8 so the encoding can change to `ensure_ascii=False`, otherwise the effective cap stays lower for such text and is documented.
11. **No content in logs.** Several tools log full responses at DEBUG inside `execute` (`jira/tools.py:215`, `confluence/tools.py:164`, `gitlab/tools.py:192`, ADO Git `tools.py:245,266`). A log filter added to the handlers in `configs/logger.py` drops records emitted while a "script call active" contextvar is set; the handler sets it around the tool run only. Channel and bridge logs stay content-free, including the oversize path (size only).
12. **Direct REST run** builds a `none` context; the bridge still starts, so the script gets `no_context` at once. **Confirmation unchanged**: the script tool keeps default `is_safe=False`.
13. **Docs and rollout.** Rewrite the "Workspace Script Bridge" section of `code_executor/README.md` (usage, envelope, codes, no token limit, the 256 KiB transport cap, one call at a time). Rollout checklist beside the switch (README and a comment on `features:workspaceScriptBridge` in `config/customer/customer-config.yaml`): network policy, `CODE_EXECUTOR_RUNTIME_CLASS_NAME` (default `gvisor`), stream and gateway idle timeouts above `timeoutSeconds` (API ingress 600 s; others unverified).

Sizing of the `HttpResult` change: 4 formatting sites in 4 files (Jira, Confluence, GitLab, xWiki `_format_result`), plus 2 Jira suffix lines and 1 Jira multimodal construction line.

## Acceptance criteria

- `tool.call` returns the tool's real result, usable in the same run; sequential calls each get their own result.
- Assistant run: only tools in the run's list (incl. attached skills), with the assistant's settings and credentials; the script tool, MCP and stream-dependent tools are refused.
- Workflow run (bare step, stored assistant in a workflow): any user-authorized tool, with the user's integrations in the workflow's project. A chat request sending `workflow_execution_id` gains nothing.
- Running the script is confirmed under `ask_for_approval` and `approve_for_me`, not under `auto_approve`; its calls are never confirmed individually (real `ExecuteWorkspaceScriptTool`).
- Unavailable, blocked, no-context, bad-argument and failing calls give a coded error, never a hang or silent success. A direct workspace run gets `no_context`.
- Jira, Confluence, GitLab and xWiki calls give `result` as the parsed JSON body and `http.status` as an integer, without the script path parsing the `HTTP: ...` text; a non-JSON body stays a string; a 404 is a normal result with `http.status` 404.
- A tool returning a pydantic model, dict, list or JSON-looking string gives `result` as JSON with no per-tool code.
- For the four HTTP tools the string returned by `execute()`, `_run` and the workflow node is byte-identical to before, including Jira's suffix notes.
- Replaces the task.md "limited like for the model" criterion: the script receives the full result with no token limit, up to the transport cap. Above it the script gets error `payload_too_large` stating size and limit, promptly, with no result content in the message or in logs.
- An assistant without the script tool runs no script.
- At DEBUG on all handlers, no call request or result content appears in logs, success or failure, including for tools that log inside `execute` and on the oversize path.

## Non-goals

- Changes to the SDK, channel protocol, switch, time limit, size cap or cleanup, beyond the handler registry, `ToolCallRefused` and the `payload_too_large` message text. No SDK wrapper (`call_tool`), no pooled-mode support.
- Any token limit, truncation or `truncated` flag on the script path; raising the 256 KiB transport cap; chunked or streamed large results.
- Skills, assistants or workflows carrying scripts; workflow script step; named tools; trace and analytics; MCP tools.
- Per-call execution deadline, parallel calls.
- Changing `_run`, `_post_process_output_content` or any model-path output (the model path keeps its 30,000-token limit); harmonizing the four tools' legacy text layouts.
- Any per-tool override of `execute_structured`; `HttpResult` for tools other than the four (SharePoint, OpenAPI, ADO Git use the default conversion, no `http` block).
- Images, binary data or Jira's attachment-transfer notes to scripts; parsing free-form strings beyond object/array JSON.
- Real-cluster verification of network policy and gateway timeouts (written down only).
