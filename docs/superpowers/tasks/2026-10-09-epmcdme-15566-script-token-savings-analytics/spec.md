# EPMCDME-15566 Spec: Script runs and their tool calls in analytics (+ estimated context savings)

Ticket decisions 1-6 (`ticket.md`) are settled except for the amendments declared below. Research: `technical-analysis.md`. Architecture review input: `local/architecture-review/2026-10-09-epmcdme-15566-spec/report.md`.

## Goal
Show tool calls made by scripts through `codemie_runtime_sdk` in the existing tools-usage analytics, count refused calls, attribute direct and script-made calls to the same assistant and workflow, count how often sandbox runs wait for or are refused executor capacity, and emit *estimated* token series showing how much less the LLM had to write and read because a script did the work (a reduction per direction: tokens written and tokens read are never added), separating plain scripts from runs that called tools.

## Declared amendments to settled text
- Ticket decision 3 ("no tokens metric for script calls"): amended. `codemie_tools_usage_tokens` still receives nothing for script calls; a separate, labelled estimate metric `codemie_script_tokens_estimated` is added at the user's request (section 4).
- Ticket acceptance criterion 5 ("script with no calls: nothing changes"): amended. A plain assistant-scope run adds two estimate records (`bridge_calls=none`).
- Ticket decision 6 and acceptance criterion 4 (a separate `codemie_skill_script_run` metric for skill scripts): moved out of this story by the ticket owner (2026-10-12) into a separate story about the origin of a script (skill, assistant files, workflow files, upload). A script run is the existing `execute_workspace_script` tool call, already counted. This story tracks no origin of scripts: no `source_kind`, skill id, skill name or script path is written anywhere; `codemie_skill_tool_invoked` is unchanged.
- Dimensions of all records: usage, errors, refused and both estimate series are written under one shared set (user id and name, project, assistant name and id, workflow id, model), built by one function. The assistant id is `virtual` for a virtual assistant (its own id is new on every run); the workflow id is read from the context variable the workflow executor binds for its own thread (`get_current_workflow_id()`), so no request can set it. Direct tool calls carry the same `assistant_id` and `workflow_id` (section 5).
- Ticket "out of scope: changing existing numbers": one reader filter is added (leaderboard tool cardinality, section 2), and the attribution fix of section 5 fills `assistant_name`, `llm_model`, `user_name` and the real `tool_type` of direct calls in the LangGraph path, which were empty or `internal` before. Existing dashboards grouping on them change for data after the release.
- Built after the approval of 2026-10-09 (the spec's non-goals said otherwise): a number of calls made at once (`CallOutcome.concurrency`, `peak_parallel`, gate waits), sandbox run and capacity metrics (section 7), tool run latency measured in `CodeMieTool` (section 8) and a Kibana dashboard that shows all of it. They are part of this story and need their own approval.
- The call source `{script, test_run}` on the observer is removed: nothing read it. The story EPMCDME-15564 adds it back when it has a reader. `request_bytes` of `CallOutcome` has no metric reader either; it stays for the trace and audit of EPMCDME-15561.
- Local sandbox (built after the approval, with the k3s compose): isolation rests on a deny-all NetworkPolicy in `docker/k3s/manifests/code-executor.yaml`. Its effect on a given machine is checked by hand, which is an accepted risk: a one-off probe (a pod in the sandbox namespace against a control pod in another namespace, both to postgres and to the k3s API) showed it enforced on the development machine, with a window of well under a second after a pod starts. The k3s healthcheck only proves the policy object exists. A check script was written and dropped as not worth maintaining for a local stack.
- Architecture spec D23: superseded in part. D23's per-call context object is realised as the per-call detail record in section 1; the code's `CallOutcome` / `on_settled(outcome)` is the base. D23 and `code_executor/README.md` ("nothing listens yet") must be updated in this story.

## Behavior

### 1. Call event, per-run observer, listener seam (sub-task 1)
- `CallOutcome` (`tool_call_protocol.py`) is settled via `on_settled` on the channel's polling thread (pool workers never settle). Nothing in `src/codemie` listens today.
- Outcome gains two fields. No platform fields are added to this generic `codemie_tools` type.
  - `seq`: sequence number assigned by `RequestDispatcher.handle`, backend-owned. The script-chosen `call_id` can repeat and is never a key.
  - `request_bytes`: exactly the UTF-8 byte length of the tool name plus the serialized call arguments (the payload's arguments field), not the whole request or envelope. It is 0 when no payload was parsed (oversize, bad encoding, unparseable) and 0 for calls settled unfinished at run end. It is a protocol fact; the estimate of section 4 does not use it (it uses tokens counted by the handler).
- How the handler receives `seq` (edit to existing code). `ToolCallHandler = Callable[[Mapping[str, object]], object]` (`tool_call_protocol.py:49`) takes only the request body, and the handler signature is not changed. The dispatcher already passes per-call state to handlers through context variables (`_current_deadline`, `_current_cancel`, set around `handler(payload)` in `_answer`, lines 260-275). Add the same kind: `_current_call_seq` with a public `current_call_seq()`, set and reset in the same try/finally. Handlers run in the dispatching thread, so the variable is visible to them. Edits: `tool_call_protocol.py` (seq counter, new contextvar, the two outcome fields, `request_bytes` computed after `parse_request`); `tool_call_channel.py` (the abandoned outcome built in `_settle_unfinished` must carry the seq of the in-flight call, so the channel tracks seq per in-flight `call_id` instead of a bare id set); tests that build `CallOutcome` positionally (`test_tool_call_protocol.py`, `test_tool_call_channel.py`, `test_job_bridge.py`) get the new fields. Handlers and their tests (`script_tool_calls/handler.py`, `test_handler.py`, `test_end_to_end.py`) keep their signatures.
- Handler to listener: `build_tool_call_handlers` takes the run observer. After authorization it records the per-call detail (resolved tool name, tool type) on the observer under `current_call_seq()`. Tool name in any label is the resolved name or `unknown`. A refused call whose name resolves to an existing tool (blocked or excluded) is recorded under that tool; a name that does not resolve, or no detail found (abandoned calls included), is `unknown`. The raw name sent by a script is never a label.
- One per-run observer object (`service/script_tool_calls/`) owns: the detail table, per-outcome-group counts, per-call token counts recorded by the handler and per-tool token sums, the attribution, the source kind of the entry script, and a closed flag.
- Who creates the observer: `AgentWorkspaceService.execute_workspace_script` takes an optional observer. `ExecuteWorkspaceScriptTool` creates one and passes it so it can read the run facts for its own records (section 4). When none is passed in (the REST route calls the service directly), the service creates the observer itself; this is what gives REST runs their usage and refused records. The service wires the observer into `new_job_bridge_options(on_settled=...)` and `build_tool_call_handlers` either way.
- Fan-out: a platform-layer helper calls listeners in order, the observer's counter first, each listener isolated (one failing never hides the others). Listeners must not block (they run on the thread that also does exec I/O). The folder-to-owner lookup runs once before the run.
- `ScriptRunContext` gains `assistant_name`, `llm_model`, `project`, `user_id`, `assistant_id`, `workflow_id` and `is_tool_step` (ticket decision 2). `assistant_id` is the stored assistant's id or `virtual`; `workflow_id` comes from the context variable when the toolkit is built. They are captured in the request thread when the context is built (project incl. the billing fallback), because the polling thread has no request contextvars (`send_count_metric` would otherwise record user `-`). Model and assistant come from the script tool's metadata (`assistant_agent._configure_tools`, `langgraph_agent`); verify in the plan, including whether a bare tool step has a model.
- Run end: emission happens in a `finally`. The observer is read once, closed under its lock, after `execute_script` returns (or raises). A late settle after close still gets its per-call usage record but is not added to the aggregates (a `stop()` join timeout is logged).

### 2. Usage metrics for script-made calls (sub-task 2)
- New emission method (not `send_tool_metrics`, which always emits tokens and lacks `error_code`). Attributes are the full direct-call set from explicit values: `tool_name`, `base_tool_name` (= resolved name; written today only by `monitoring_callback.py`, and the tools-usage view, `assistant_handler` and `stale_datasource_service` group on it), assistant, `user_name`, `user_id`, project, model, tool type, plus `invoked_by="script"`; `error_code` on errors. No script path label.
- Outcome map (one `classify()` with named code groups, a contract test asserts every protocol/SDK code is classified):

| Ending | Metric | Notes |
|---|---|---|
| success, delivered | usage total, status success | counts toward tokens estimate |
| `tool_failed`, `bad_arguments`, `payload_too_large`, `internal_error`, `timeout`, `unavailable`, `error` | errors, with `error_code` | name resolved or `unknown` |
| `unknown_op`, `bad_request` (protocol faults) | errors, tool `unknown` | counted although the request has an operation other than `tool.call` (or none) |
| `tool_blocked`, `tool_unavailable`, `no_context`, `deadline_exceeded` | `codemie_script_tool_calls_refused_total` only (decision 4 attributes) | |
| withdrawn, abandoned at run end (incl. not started) | usage total, `status=abandoned` | no tokens |

  Every settled ending counts toward `bridge_calls`, except a well-formed request for some other operation of the bridge (`op` set, not `tool.call`, no protocol-fault code): that is not a tool call. Today the bridge has one operation, so the exception is unreachable; it keeps a second operation from being counted as a tool call (`counts_as_call`).
- Workflow bare tool step: calls counted with no assistant, executing user and workflow project from the project scope. REST direct runs (`no_context`) produce only refused records.
- Readers: `tools_handler`/`assistant_handler` show script calls (accepted). Leaderboard: it takes a per-user cardinality of `tool_name` (`leaderboard/collector.py:901`), so `invoked_by=script` records are excluded from that count only. Engagement, assistant and stale-datasource readers accept them (a script's use of a datasource tool counts as use).
- Register the metric names in `metrics_constants.py` and `MetricName`; add label constants in one place.

### 3. Origin of a script (moved out)
Not part of this story. Where a script came from (a skill, files attached to an assistant or a workflow, an upload, written in the workspace) is a separate story; it needs the seed ledger of EPMCDME-15558 and, for uploads, a decision on how to tell them (see the notes in the task folder). The call records and the estimate series carry no origin until then.

### 4. Estimated savings metric (new)
`codemie_script_tokens_estimated`, never summed into `codemie_tools_usage_tokens`. Labels: `direction` {model_output, model_input} (the model's point of view: **model_output** = the tokens the model has to write, i.e. what a tool receives: call arguments, script code; **model_input** = the tokens it has to read, i.e. what a tool returns: results, the script tool's answer), `side` {inner_calls, script_tool}, `estimator=tiktoken_v1`, `bridge_calls` {none, some} and `bridge_ok` {yes, no} on `script_tool`, plus the shared run dimensions (section 1 and the amendments above). `run_ok` {yes, no}.
- One shared estimator: tiktoken tokens of the text, counted with `codemie_tools.base.utils.get_encoding` for the run's model (`o200k_base` when the model is empty or unknown; special-token text is counted, not rejected), the same encoding that counts the output of a direct tool call, so direct and estimated tokens are on one scale. Same for all four series so the ratios are comparable. Counting happens on the thread that already handles the call (the handler thread for inner calls, the tool's thread for the script tool); calls that did not succeed are not counted. The estimator is versioned by the label: the earlier `bytes4_v1` (`ceil(bytes/4)`) is not mixed with it.
- `side=inner_calls`: aggregated per run and per resolved tool at run end (not per call), `tool_name` label. Both sides of the pair are written by the script tool in its `finally` through one function, `emit_savings`, which applies the rule once (assistant scope, not a workflow tool step); the service writes neither. `model_output` = tokens of the tool name plus arguments, `model_input` = tokens of the answer the script got (the JSON envelope included). The handler counts them after a successful call and records them on the observer under the call's `seq`; only success-delivered calls are summed. Each call's output is capped at what a direct call would have shown the model: the assistant's `tools_tokens_size_limit` in tokens when known, else the bridge payload bound in tokens (`max_payload_bytes // 4`). The cap models the direct call's truncation only; it does not limit the script or its tools.
- `side=script_tool`: owned entirely by `ExecuteWorkspaceScriptTool` (it builds the string the model sees), emitted in its `finally`, for assistant scope only (`scope_kind == ASSISTANT`; never bare workflow tool steps or REST runs). `model_output` = tokens of the tool-call arguments plus tokens of the script file's own code (its text read from the workspace; 0 for a binary or unreadable file). `model_input` = tokens of the string `execute_workspace_script` returned (0 if it raised). The tool reads the run facts (`bridge_calls`, `bridge_ok`) from the observer it passed to the service.
- `run_ok` {yes, no} on every estimate record of both sides: whether the script run ended without an error. A run that failed after some calls succeeded still carries its estimate (decision above), and `run_ok=no` lets a reader keep those runs apart from finished ones, so the ratio is not inflated by failed runs. Series count: x2 per existing combination.
- `bridge_calls=some`: any settled call (user decision). Skew risk, stated: a run whose calls all failed or were refused is `some` and adds script_tool cost with no inner_calls numerator. `none` mixes "bridge off" and "bridge on, script made no call". Mitigation: `bridge_ok=yes` (at least one success-delivered call) is kept so a stricter ratio can be derived without re-emitting; per-call outcomes remain in the usage metrics.
- Derived at read time (no reader here): ratio = sum(inner_calls) / sum(script_tool) per direction, per assistant, over `bridge_calls=some` and `run_ok=yes`. Without `run_ok=yes` the ratio is inflated by failed runs: their `script_tool/model_input` is 0 although the model reads the error text.
- Labelling: these are inflatable upper-bound estimates. Inputs, sizes and call counts are chosen by the script; the counterfactual (the model would have called every tool directly and read full results) is an assumption and ignores truncation. They must not feed rankings, leaderboards or billing. Exact measured savings are outside the design.
- Overlap: `execute_workspace_script`'s output is already counted in `codemie_tools_usage_tokens` with the same encoding; the estimate counts the returned string once more under its own metric. Do not add the two.
- Conservative by construction: `inner_calls` counts a call's name and arguments and the answer only. It leaves out what a real direct call also costs the model: the framing of the call, the extra model turn each call needs, and the earlier conversation re-sent with every turn. The `model_output` side is therefore understated (live runs: 3 calls 63 tokens written directly vs 61 for the script; 8 calls 168 vs 61; 20 calls 420 vs 61, because a script loops and its size does not grow with the calls).
- Accuracy: exact for OpenAI-family models, approximate for others. Measured against the earlier bytes/4 estimator, which was off by 0.4x to 1.5x depending on content (JSON, Cyrillic, base64).
- Volume: usage records stay per call; token series are per run and tool. No new per-run call cap; existing limits (`max_parallel_calls`, 480 s run timeout) bound it. Recorded as a risk.

### 5. Attribution of direct tool calls
- The LangGraph agent does not let LangChain run its tools through the callback manager: `LangGraphCallbackBridge` calls `on_tool_start` itself from stream events and used to pass only the tool name, so `MonitoringCallback` saw empty metadata. As a result direct calls had empty `assistant_name`, `llm_model` and `user_name`, no `assistant_id` or `workflow_id`, and always `tool_type=internal` (on clean main too).
- The bridge now looks the tool up by name among the agent's tools and passes the attribution the agent stamped on it in `_configure_tools`: `agent_name`, `llm_model`, `user_name`, `project`, `assistant_id`, `workflow_id`, `tool_type`. `output_format` and the request/user ids are deliberately not passed, so the rendering of thoughts does not change. A tool the agent does not own (a sub-agent's tool in a supervisor run) still gets empty metadata.
- `run_id_metadata(assistant)` stamps `assistant_id` (stored id, or `virtual`) and `workflow_id` (context variable) on every tool, after and over the request's own metadata, so a request cannot supply them. `send_tool_metrics` writes them only when non-empty.

### 6. `invoked_by` is a label, not a filter
Records of calls made by a script carry `invoked_by=script`; a direct call has none (the tool-run records of section 8 write `direct` explicitly). The label is read in Kibana only. The `tools-usage` analytics endpoint, its service, query builder and pipeline take no `invoked_by` filter, and their numbers are unchanged apart from the script-made calls that now count in them.

### 7. Sandbox runs: outcome, capacity, time, parallelism
Written for every sandbox run of `code_executor` and `execute_workspace_script` (REST direct runs included) by `CodeExecutionMonitoringService.send_run`, in a `finally`, never raising. All carry `tool_name`, `sandbox_mode` (`sandbox-jobs`, `sandbox-shared`) and the shared run dimensions.
- Counters (log and Prometheus): `codemie_code_execution_runs_total{outcome}` (every run), `..._attempts_total` (a run that asked for a Job slot or a pod), `..._capacity_waits_total` (one that had to wait, at most one per run) and `..._capacity_rejections_total` (one turned away for the lack of capacity). Rejections <= waits <= attempts. A run refused before it asked for capacity (security policy) counts in `runs_total` only.
- `outcome`: `ok`, `script_error` (non-zero exit code), `timeout` (pod not running, run not finished, or Job not completed within the budget), `sandbox_error` (Job not created, pod stopped early, exec failed), `capacity_rejected`, `policy_denied`, `error` (anything else). A script that exits non-zero stays `script_error` even though the tool then raises. A run's outcome is named by `SandboxFailure(message, outcome)`, a `ToolException` that keeps the user-visible message.
- Capacity rules. Jobs mode: a wait is no free slot at once, a rejection is no slot within `CODE_EXECUTOR_DEFAULT_TIMEOUT`. Shared mode: a wait is a full pool with no Running pod, a rejection is still none after waiting; reusing a Running pod of a full pool is not a wait. A script that fails after the run got its capacity is not a rejection.
- Run record `codemie_code_execution_run`, log and search index only (a number as a Prometheus label would make a series of every run): the dimensions plus `outcome`, `elapsed_seconds` (the whole call), `acquire_seconds` (waiting for the slot, or getting a pod session), `pod_start_seconds` (Job created to pod running) and `pod_seconds` (slot acquired to Job deleted: the pod's life as the app sees it; Jobs mode only), `capacity_requested`, `capacity_waited`; and, for a run with a bridge, `calls_total`, `calls_success`, `peak_parallel`, `gate_waited_calls`, `gate_wait_seconds`, `gate_wait_max_seconds`, `gate_timeout_calls`.
- Histograms (Prometheus, labels `tool_name`, `sandbox_mode` only, `user_id` pinned): `codemie_code_execution_run_seconds`, `..._acquire_seconds`, `..._pod_start_seconds`, `..._pod_seconds`.
- Parallelism: the channel tells each settled call how many of the run's calls were in flight (running or queued) when it was accepted (`CallOutcome.concurrency`); `peak_parallel` is the maximum (1 = sequential). A batch cannot be told from threads on the backend, so "uses parallel calls" means `peak_parallel >= 2`; the protocol and SDK are not changed.
- Tool-call gate (process-wide limit, `WORKSPACE_SCRIPT_TOOL_CALLS_MAX_CONCURRENT`): `ToolRunGate.hold()` yields a `GateTicket(waited, wait_seconds)` and a call that gives up raises `GateTimeout` (still `deadline_exceeded` for the script); the handler records both on the run observer.
- Infrastructure cost: `pod_seconds` times the pod's CPU and memory limits from configuration, at read time. In shared mode the pods are long-lived: `pod_seconds` is not measured and the pool's cost comes from the cluster, not the app.
- Mechanism: `SandboxRunObserver` (`codemie_tools`, no platform imports) is marked by `BatchJobRunner` and `SandboxSessionManager` and read once by whoever started the run (the tool for `code_executor`, `AgentWorkspaceService` for the workspace script, which also passes the tool-call snapshot).
- `code_executor` makes no tool calls. It is written with the same records because it takes Job slots and pods from the same pool, and it is read only as a consumer of capacity (the capacity panels); adoption, shape, outcome, cost (pod-seconds) and savings are read for `execute_workspace_script` only.
- Dashboard: a Kibana dashboard over `codemie_metrics_logs*` (adoption, shape of runs, problems, capacity, time and cost by tool, estimated savings) is built by a script kept outside the repository tree for now; see the notes of the task.

### 8. Tool run latency
How long a tool's own work takes, for the model's calls and for the calls a workspace script makes, measured once, in the tool base class.
- `CodeMieTool` times its `execute` for a model's call (`_run`, `invoked_by=direct`) and its script twin for a script's call (`run_for_script` and `execute_structured`, `invoked_by=script`). The duration leaves out the configuration check, the limiting of the output by tokens and the conversion of the result; for an HTTP tool it is the request plus what the tool does around it. A call that raises is timed too and the exception passes through unchanged.
- `codemie_tools` knows nothing about metrics: `codemie_tools.base.execution_timing` holds a `ToolExecution` and any number of registered sinks (none by default: reporting does nothing; a sandbox tool reports through `SandboxRunReport` the same way). The platform registers `ToolExecutionMonitoringService.record` at start-up (`rest_api/main.py`, next to the Prometheus set-up). A sink that raises never reaches the tool.
- `codemie_tool_execution`, log and search index: `tool_name`, `invoked_by`, `status` (`success`, `error`), `error_class`, `tool_type`, `duration_seconds` and the run's identity (user, assistant name and id, project, model, workflow id) from the metadata the agent stamped on the tool. That metadata is also there on the thread that serves a script's call, where no request context exists. The existing `codemie_tools_usage_*` records are not changed.
- `codemie_tool_execution_seconds`, Prometheus histogram: `tool_name`, `invoked_by`, `status` only (`user_id` pinned).
- Reach: every `CodeMieTool` (137 classes, MCP and skill tools included). Not covered: tools that do not extend it (LangChain tools used directly, the placeholder for a missing integration, IDE tools). A direct call of `execute_workspace_script` includes its sandbox; the calls a script makes inside it are timed on their own.
- Dashboard: median and p95 by who called, direct against script per tool, a latency table by tool, the slowest tools, failing runs. A data view needs its field list refreshed once the first records with `duration_seconds` exist.

## Acceptance criteria
- Each script-made call is counted under its resolved tool name (or `unknown`) with `invoked_by=script`, `base_tool_name` and the assistant, user, project and model of a direct call; it appears in the tools-usage view.
- Every ending in the outcome map lands in exactly the stated metric; a refusal goes only to the refused counter; a failure is an error with `error_code`.
- A script run counts once as `execute_workspace_script`; each inner call once under its own tool name.
- A withdrawn or abandoned call is a use with `status=abandoned` and a resolved name or `unknown`.
- No record is written to `codemie_tools_usage_tokens` for script calls.
- An assistant-scope run emits the `script_tool` `model_output` and `model_input` records with `bridge_calls` and `bridge_ok`, also when the run raises; a workflow tool step or REST run emits none.
- `side=inner_calls` records are aggregated per run and tool, exclude non-success calls, and share the tiktoken estimator (`estimator=tiktoken_v1`) with `script_tool`; each inner call's output is capped at the direct-call limit in tokens.
- Script-tool input includes the tokens of the script's code.
- Both estimate sides carry `run_ok`; a run that raised writes its pair with `run_ok=no` and `model_input=0`.
- Usage, errors, refused and both estimate series carry the same dimensions (user, project, assistant name and id, workflow id, model); no record carries a script path, a skill id, a skill name or an origin of the script; `codemie_skill_tool_invoked` is unchanged.
- The leaderboard `unique_tools` excludes `invoked_by=script`; other readers include them.
- A listener failure never breaks a run or other listeners.
- Direct tool calls of a LangGraph agent carry `assistant_name`, `llm_model`, `user_name`, `assistant_id`, `workflow_id` (in a workflow) and their real `tool_type`; a request cannot set `assistant_id` or `workflow_id`.
- Every sandbox run counts once by its outcome; a run that asked for capacity also adds one attempt, one that waited one wait, one refused for capacity one rejection; a script failing after it got capacity adds neither a wait nor a rejection for that.
- Every sandbox run writes one run record with its durations and, for a bridge run, its calls, peak parallelism and gate waits; durations also go to histograms with the tool and mode only.
- `CallOutcome` carries `seq` and `request_bytes` (tool name plus arguments in bytes, 0 when unparseable); handlers read `seq` through `current_call_seq()` with unchanged signatures.

## Non-goals
- No cost figures in metrics; no new dashboard, API field, UI change or savings/ratio reader.
- No change to other existing readers' computation.
- No counting of a bare workflow tool step itself or its direct tool calls, and no savings estimate for tool steps.
- No script-path or execution-id labels; no figure for calls made at once; no `bridge_calls` on usage, errors or refused metrics.
- No trace-step or audit listener (EPMCDME-15561), no test-run source wiring (EPMCDME-15564).
- No exact tokenization for non-OpenAI models; no database schema change; no per-run call cap; no round-trip or context re-send figures; no change of the handler signature.

## Testing
Observer (thread-safety, closed flag, service-created vs tool-passed), fan-out isolation, `classify()` contract test over all codes, detail table with unresolved and abandoned calls, protocol tests for `seq`, `current_call_seq()` and `request_bytes`, end-to-end through the real channel, tool `finally` on exception, leaderboard filter, workflow scope, REST direct run, token counting (parity with `calculate_tokens`, unknown model, special-token text), handler token recording (success only), cap in tokens, `workflow_id` from the context variable (and not from a request), the bridge attribution (subset of keys, unowned tool, no `output_format`), the run observer (outcome rules, timings), its marks and typed failures in the Job runner and the shared pool manager, the gate ticket and timeout, the channel's concurrency, the run record, counters and histograms (including a run that never asked for capacity). Verified live on docker compose with k3s: REST run, assistant chat, workflow with a tool step and an assistant node, direct-call attribution, and three concurrent runs against a one-slot pool (3 attempts, 2 waits, 2 rejections).
