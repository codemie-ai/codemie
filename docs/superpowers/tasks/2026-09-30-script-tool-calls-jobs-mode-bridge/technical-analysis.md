## 1. Original Context

EPMCDME-15401 follow-up. The script tool-call bridge built in sub-task 1 (SDK `codemie_runtime_sdk`, side-channel `tool_call_channel.py` with an echo handler, per-run exchange folder, customer-config switch `features:workspaceScriptBridge`) only works in `CODE_EXECUTOR_SANDBOX_MODE=sandbox-shared` (pooled) mode. Discovery: pooled mode is not actually deployed anywhere in practice — only `sandbox-jobs` (the default) is used. Decision (already made by the user, not open for debate): remove the pooled-mode bridge wiring entirely and re-implement the bridge for jobs-mode instead.

Current jobs-mode execution model (`BatchJobRunner.run()` in src/codemie_tools/data_management/code_executor/batch_job_runner.py) is a single synchronous call: create a Kubernetes Job, wait for its pod to reach Running, upload a payload tarball (script.py + input files + .ready sentinel), block until a completion sentinel file appears in the pod, download exports/changed-files, delete the Job. There is currently no hook point for a side-channel thread to poll the same pod concurrently while the script executes — this needs genuine interleaving of "wait for the channel's requests" and "wait for the job to finish", not a config flip.

## 2. Codebase Findings

### Existing Implementations

**`BatchJobRunner` — `src/codemie_tools/data_management/code_executor/batch_job_runner.py`** (654 lines, read in full)

- Process-wide singleton (`__new__` + `_instance_lock`), holds a `threading.BoundedSemaphore(config.max_pod_pool_size)` capping concurrent Jobs, and a `KubernetesClientManager`.
- `run(code, input_files, export_files, workdir, baseline_hashes)` — the single synchronous entry point, exact sequence:
  1. `_acquire_slot()` — blocks on the semaphore (timeout = `config.default_timeout`), raises `ToolException` at capacity.
  2. `job_name = f"{pod_name_prefix}{uuid4().hex[:12]}"`.
  3. `_create_job(job_name, workdir)` — POSTs a `V1Job` built by `_build_manifest`.
  4. `deadline = time.monotonic() + config.execution_timeout + _DEADLINE_BUFFER_SECONDS` (buffer = 60.0s) — one shared budget threaded through every subsequent wait.
  5. `_wait_for_pod_running(job_name, deadline)` — polls (`_POLL_INTERVAL_SECONDS`=0.5s) `_find_job_pod`/`_list_job_pods` (label selector `job-name=<job_name>`) until `pod.status.phase == "Running"`; raises on `Failed`/`Succeeded` or deadline.
  6. `_upload_payload(pod_name, workdir, code, input_files)` — builds one tarball (`script.py` + input files + `.ready` sentinel LAST) and pushes it via `_exec_tar_in` (`tar xf - -C <workdir>` over a k8s exec with stdin).
  7. `_wait_for_sentinel(pod_name, f"{workdir}/.done", deadline)` — polls `test -f <path>` via exec every 0.5s until the wrapper's `.done` sentinel appears (i.e. the script finished).
  8. `_download_exports(pod_name, workdir, export_files)` — per-path `_exec_tar_out` (`tar cf - <path> | base64 -w0`, decoded and un-tarred on the host).
  9. `_download_changed_files(...)` (only if `baseline_hashes is not None`) — `_snapshot_workdir` execs a Python one-liner (`hashlib`/`json`/`os` walk) inside the pod to hash every file, diffs against `baseline_hashes`, then reuses `_download_exports` for the changed set.
  10. `_exec_tar_out(pod_name, workdir, ".stderr")` — pulls captured stderr.
  11. `_signal_cleanup(pod_name, workdir)` — touches `.pulled` so the in-pod wrapper's `until [ -f .pulled ]` loop exits (best-effort; logged, not raised, on failure).
  12. `_wait_for_completion(job_name, deadline)` — polls `read_namespaced_job_status` until `_is_terminal` (succeeded/failed/condition), then `_extract_exit_code` from the pod's terminated container status.
  13. `_read_pod_logs(job_name)` — stdout of the container.
  14. `finally`: `_delete_job(job_name)` (foreground propagation, grace period 0) and `self.semaphore.release()`.
  - Steps 5–12 are **entirely sequential and blocking on the same Python thread that called `run()`**; nothing yields control back to a caller-supplied hook between steps, and there is no thread, event loop, or hook parameter anywhere in the class for a concurrent poller.
- `_build_wrapper_command(workdir)` (full read) — returns an argv array (`env -i <safe env> bash -c <inner>`), no shell parses the outer array (fed straight to execve via K8s). The inner bash script: `mkdir/cd workdir`; `until [ -f .ready ]; do sleep 0.1; done` (waits for upload); `python script.py 2>.stderr`; capture exit code to `.exit_code`; `touch .done`; `until [ -f .pulled ]; do sleep 0.1; done` (waits for host to finish pulling); `exit $_ec`. **The container's single process (`bash`) stays alive for the pod's entire life** — from before upload through the `.pulled` wait after the script exits — so the pod is reachable for concurrent `kubectl exec`-style calls (via `stream(core.connect_get_namespaced_pod_exec, ...)`) for that whole window, including while `python script.py` is running. Nothing in the manifest or wrapper serializes execs against each other; `BatchJobRunner._exec` opens an independent WS connection per call.
- `_build_manifest(job_name, workdir)` (full read) — `V1Job` with `backoffLimit: 0`, `activeDeadlineSeconds = int(execution_timeout) + int(_DEADLINE_BUFFER_SECONDS)`, `ttlSecondsAfterFinished = 60`. Pod spec: `restartPolicy: Never`, optional `runtimeClassName` (default `gvisor`), optional `tolerations`, `automountServiceAccountToken: False`, no host namespaces, pod-level `securityContext` (`runAsNonRoot`, `seccompProfile: RuntimeDefault`, `fsGroup`), single container `executor` with `readOnlyRootFilesystem: True`, `allowPrivilegeEscalation: False`, `capabilities.drop: [ALL]`. Volumes: `workdir` (emptyDir, mounted at the run's `workdir` path) and `tmp` (emptyDir, mounted at `/tmp/runtime`) — the *only* writable paths in the container; any exchange folder the bridge needs must live under one of these two emptyDirs (most naturally under `workdir`, since that's what the script's own working directory and the wrapper's sentinel files use).
- `run_via_jobs(...)` module function — the shared chokepoint both `code_executor_tool.py` and `execute_workspace_script_tool.py`'s pre-bridge JOBS path called through (still used by `code_executor_tool.py`'s plain-code-execution JOBS path; `execute_workspace_script_tool.py`'s `_execute_sandbox_script_jobs` calls `BatchJobRunner(...).run(...)` directly instead, to get `baseline_hashes`/`changed_files`).

**`_execute_sandbox_script_jobs` — `src/codemie_tools/data_management/workspace/execute_workspace_script_tool.py:349-385`**

Formats result, builds `last_execution_files` from `result.changed_files`, stores `result.exported_files` via `_store_exported_bytes`. No channel, no timeout override, no tool-calling limit is used or even resolved on this path other than short-circuiting `_resolve_tool_calling_limit()` to `None` when `sandbox_mode == JOBS` (with a `tool_calling_ignored` warning log).

### Architecture and Layers Affected

- **Kubernetes execution layer**: `batch_job_runner.py` (Job lifecycle, exec-based upload/download) — the layer that must gain a concurrency hook; `session_manager.py`/`session_factory.py`/`pod_discovery.py` (pooled pod layer) — candidates for removal of bridge-specific wiring, though the pool machinery itself is likely still used for the non-bridge SHARED mode (if SHARED mode itself stays supported for plain code execution) — this doc does not decide that; see Risk Indicators.
- **Tool/service layer**: `CodeExecutorTool._execute_sandbox`/`_execute_code_sandbox` (`code_executor_tool.py`) and `WorkspaceScriptRunner._execute_sandbox_script`/`_execute_sandbox_script_jobs` (`execute_workspace_script_tool.py`) — both branch on `SandboxMode`; the jobs branch of each currently has no channel/timeout wiring at all.
- **Side channel layer**: `tool_call_channel.py` — `ToolCallChannel`, `ExecRunner` protocol, `KubernetesExecRunner`, `sweep_stale_exchange_folders` — pod-name/container-name/namespace/workdir parameterized only; see next section.
- **Runtime SDK layer**: `runtime_sdk/codemie_runtime_sdk.py` — executed *inside* the sandboxed script process; file-based exchange-folder protocol.
- **Configuration/admin layer**: `customer_config_declarations.py` (`WORKSPACE_SCRIPT_BRIDGE` `SettingDeclaration`), `config/customer/customer-config.yaml` (`features:workspaceScriptBridge` default block), `agent_workspace_service.py` (`resolve_tool_calling_timeout`/`parse_tool_calling_timeout`, wired into `WorkspaceScriptRunner(tool_calling_timeout=resolve_tool_calling_timeout())` at line 556).
- **Pod-side scripts layer**: `pod_scripts/{poll,write_response,sweep,kill}.py`, loaded via `load_pod_script` and run as `python3 -I -c <script>` inside whatever pod the channel is pointed at.

### Integration Points

- `KubernetesClientManager` — shared by `BatchJobRunner`, `SandboxSessionManager`, and `KubernetesExecRunner` for API client lifecycle/recreation-on-stale-connection.
- `codemie.service.agent_workspace_service.AgentWorkspaceService.execute_workspace_script` (around line 551-556, confirmed by grep) constructs `WorkspaceScriptRunner(..., tool_calling_timeout=resolve_tool_calling_timeout())` — the only caller that wires the customer-config timeout into the runner; unchanged regardless of sandbox mode.
- `customer_config.is_feature_enabled` / `get_feature_setting` (`codemie.configs.customer_config`) — read on every script run (no caching beyond `CUSTOMER_CONFIG_CACHE_TTL_SECONDS`, per README).
- `kubernetes.stream.stream(core.connect_get_namespaced_pod_exec, ...)` — the transport both `BatchJobRunner._exec` and `KubernetesExecRunner.__call__` use; both open independent WebSocket connections per call, so nothing currently prevents two concurrent execs against the same pod (one from `BatchJobRunner`'s own polling, one from a hypothetical channel).

### Patterns and Conventions

- **Process-wide singletons with double-checked locking**: `BatchJobRunner`, `SandboxSessionManager` both use `__new__` + a class-level `threading.Lock`.
- **Shared time budget threaded through sequential waits**: `BatchJobRunner.run` computes one `deadline` and passes it to `_wait_for_pod_running`, `_wait_for_sentinel`, `_wait_for_completion` — explicitly documented (line 412-416) as bounding total Python-side wait to `execution_timeout + _DEADLINE_BUFFER_SECONDS` rather than 3x.
- **Best-effort cleanup**: `_signal_cleanup`, `_delete_job`, `ToolCallChannel.cleanup`/`sweep`/`_mark_unavailable`, `sweep_stale_exchange_folders` all catch and log rather than raise, so housekeeping never masks the run's real result.
- **`ExecRunner` protocol for testability**: `tool_call_channel.py`'s `ExecRunner = Protocol` lets tests (`LocalExecRunner` in `test_tool_call_channel.py`) drive the exact same argv against a local filesystem directory instead of a real pod — the channel's own code never imports/depends on `KubernetesExecRunner` internals; it only calls `self._runner(argv, stdin)`.
- **Daemon polling thread with `threading.Event`-based interruptible backoff**: `ToolCallChannel.start`/`stop`/`_run`, `stop_event.wait(delay)` vs `time.sleep(delay)` distinguishing "interruptible" (normal run) vs "housekeeping after stop" backoff.
- **Retry-with-backoff on `ExecFailed`**: `ToolCallChannel._exec` (`DEFAULT_EXEC_ATTEMPTS=3`, linear backoff `backoff_seconds * attempt`).
- **Stdlib-only, no relative imports, standalone-executable module used both inside the sandbox and by the backend for constants**: `codemie_runtime_sdk.py`'s module docstring states this explicitly; `tool_call_channel.py` imports it directly for the protocol constants (`BRIDGE_DIR_NAME`, `FILE_SUFFIX`, `MAX_PAYLOAD_BYTES`, `PROTOCOL_VERSION`, `REQ_PREFIX`, `RESP_PREFIX`, `UNAVAILABLE_MARKER_NAME`) and `sandbox_guard.py` reads its source text (`_read_sdk_source`, cached) to `exec()` it as a module inside the guarded script.

**Confirmation for research item 3 (channel pod-agnosticism)**: `ToolCallChannel.__init__`, `start`, `stop`, `_run`, `_poll`, `_respond`, `_answer`, `sweep`, `cleanup`, `_exec` reference only `self._runner` (the `ExecRunner` callable), `self.exchange_dir`, and internal state (`_handled`, `_stop_event`, `_thread`) — no pod pool, session, or lock concept appears anywhere in the class. `KubernetesExecRunner.__init__` takes `pod_name`, `container_name`, `namespace`, `workdir`, `kubeconfig_path` as plain strings and its own `KubernetesClientManager` — nothing pool-specific; `pod_name`/`container_name` could equally be a Job's pod and its `executor` container. **The pooled-mode assumption lives entirely in the CALLER** (`execute_workspace_script_tool.py`'s `_build_exec_runner`/`_session_pod_name`/`_session_container_name`, which extract the pod/container name from an `llm_sandbox` `SandboxSession` object that only exists for pooled sessions) — confirming the channel itself needs no changes, only a different way for the caller to obtain `pod_name`/`container_name`/`namespace`/`workdir` for a Job's pod (which `BatchJobRunner._wait_for_pod_running` already resolves and returns, and the container is hardcoded `"executor"` in `batch_job_runner.py`'s exec calls).

**Confirmation for research item 9 (SDK mode-agnosticism)**: `codemie_runtime_sdk.py`'s `_configure`/`call`/`_read_response` operate purely on `exchange_dir` (a workspace-relative path) via `os.path.join`, `open`, `os.replace`, `os.remove`, `time.sleep` — no reference to session, pod pool, or sandbox mode anywhere in the file. It is bootstrapped identically for both modes today via `build_guarded_workspace_script`'s `exchange_dir` parameter (`sandbox_guard.py`); jobs mode simply never passes a non-`None` value for it today (`_build_script_wrapper` call in `_execute_sandbox_script_jobs` omits `exchange_dir`).

**Confirmation for research item 8 (customer-config mode-agnosticism)**: `WORKSPACE_SCRIPT_BRIDGE` (`customer_config_declarations.py:205-228`), the `features:workspaceScriptBridge` YAML block (`customer-config.yaml:315-323`), and `resolve_tool_calling_timeout`/`parse_tool_calling_timeout` (`agent_workspace_service.py:56-92`) reference only `enabled`/`timeoutSeconds` and `customer_config.is_feature_enabled`/`get_feature_setting` — no sandbox-mode branching anywhere in this layer. The `WORKSPACE_SCRIPT_BRIDGE.description` field and the README's "Workspace Script Bridge" section, however, both state in plain text that the bridge currently "works only with the pooled sandbox mode" / "only in pooled mode" — this is documentation, not code logic, but it is a fact this ticket must update once jobs-mode support lands.

### Derived Conventions

- Sandbox-mode branching is always a single `if self.config.sandbox_mode == SandboxMode.JOBS:` early-return, never a shared code path with internal mode checks — both `_execute_sandbox` (`code_executor_tool.py`) and `_execute_sandbox_script` (`execute_workspace_script_tool.py`) follow this shape.
- Anything that must run identically in both modes (security-policy validation, guarded-script building, result formatting, export/changed-file persistence) is factored into shared helper methods (`_validate_code_security_policy` vs `_validate_code_security`, `_format_execution_result`, `_store_exported_bytes`/`FileExportService`) called from both branches, rather than duplicated.
- Kubernetes exec commands are always argv arrays passed to `stream(core.connect_get_namespaced_pod_exec, ...)`, never `kubectl` subprocess calls; binary payloads always travel as base64-wrapped tar streams or length-prefixed stdin (never embedded in argv, which is limited to ~128KiB and sent as query parameters).

## 6. Risk Indicators

- **No hook point exists anywhere in `BatchJobRunner.run()`** for a concurrent poller — steps 5–12 of `run()` are strictly sequential on the calling thread (Section 2). Any jobs-mode bridge design needs genuine concurrency (a second thread execing into the same pod while step 7 (`_wait_for_sentinel`) blocks), which is a materially different concurrency model than the pooled-mode design (`_execute_code_sandbox`'s pod lock + `channel.start()`/`session.run()`/`channel.stop()` around one `session.run` call). This is a novel-pattern risk, not a copy-paste of the pooled wiring.
- **`readOnlyRootFilesystem: True` + two emptyDirs only** (`workdir`, `tmp` at `/tmp/runtime`) constrains where a jobs-mode exchange folder can live — it must be under the `workdir` emptyDir (the only writable, non-ephemeral-per-exec path the script and a side channel could both reach), the same constraint the pooled mode already satisfies via the workspace root. Speculative: this likely means the exchange-folder path convention (`.codemie_bridge/<epoch>-<uuid>/` under the workspace root) transfers unchanged, but this is a design decision for Stage 3, not confirmed here.
- **`activeDeadlineSeconds` is sized off `execution_timeout` only, with no tool-calling awareness today** — `_build_manifest`'s `active_deadline = int(execution_timeout) + int(_DEADLINE_BUFFER_SECONDS)`, and `_wait_for_sentinel`'s `deadline` uses the same budget. The tool-calling limit (customer-config, default 120s) is presently never consulted on the jobs-mode path at all (`_resolve_tool_calling_limit` hardcodes `None` for `SandboxMode.JOBS`, Section 2). Since `execution_timeout` defaults to 30s and the tool-calling default is 120s, a jobs-mode script that runs for up to the tool-calling limit would already exceed `activeDeadlineSeconds` and get killed by Kubernetes before the bridge even runs — this gap must be reconciled by whatever design follows.
- **Duplicate hand-rolled snapshot pattern**: `BatchJobRunner._snapshot_workdir` (`batch_job_runner.py:370-400`) and `WorkspaceScriptRunner._get_sandbox_file_snapshot` (`execute_workspace_script_tool.py:269-299`) both inline an `import hashlib, json, os[, sys]` walk-and-hash Python one-liner executed inside the pod. The task names a "recently found separate security bug" in this pattern (unrelated ticket, explicitly out of scope for a fix here) — flagged only because `_snapshot_workdir` sits squarely on the jobs-mode removal/rewrite path this ticket touches; a fix branch for the other ticket could interact/conflict here if timed closely.
- **Pooled-mode removal touches five call sites plus one class's worth of dead code**: `_sandbox_session`, `_build_channel`/`_build_exec_runner`/`_session_pod_name`/`_session_container_name`, `_build_sweep_hook`, `_execute_code_sandbox`'s pod-lock/channel branch in `_run_locked`, and `SESSION_HEADROOM_SECONDS`/the clamp half of `_resolve_tool_calling_limit` are all pooled-only per Section 2 — but `SandboxSessionManager`/`session_manager.py` and `SandboxMode.SHARED` more broadly are also used by `CodeExecutorTool._execute_sandbox`'s plain (non-bridge) pooled path, so "remove the pooled-mode bridge wiring" is not the same scope as "remove pooled mode." Stage 3/4 will need to scope precisely which of these symbols are bridge-only vs shared-with-plain-pooled-execution; this document does not make that call.
- **No test today models the jobs-mode + channel interleaving scenario** (Section 4) — the entire new concurrency behavior is currently untested by construction, since it doesn't exist; Stage 4 planning should expect net-new test infrastructure (likely a fake/threaded Job-lifecycle double), not incremental extension of existing fixtures.
- **User-facing documentation and admin-settings copy currently assert the pooled-mode-only limitation** in three places (`README.md`'s Workspace Script Bridge section, `WORKSPACE_SCRIPT_BRIDGE.description` in `customer_config_declarations.py`, and implicitly the smoke-check instructions in the README) — all three will need updates once jobs-mode support ships; none of this is code logic, but all three are easy to miss since they're prose, not branches.
- **Sub-task 2's task.md assumes the bridge already works** ("The channel, the SDK, the switch, the tool-calling time limit, the size cap and the cleanup exist after sub-task 1") without mentioning the pooled-mode-only gap — this jobs-mode ticket is a precondition sub-task 2's own scope document doesn't currently account for; a plan for this ticket should flag that dependency explicitly rather than assume sub-task 2's document is current.

## 7. Summary for Complexity Assessment

This task touches three architectural layers in one repository: the Kubernetes execution layer (`batch_job_runner.py`, whose synchronous, fully-sequential `run()` has no concurrency hook of any kind today), the tool/service dispatch layer (`code_executor_tool.py` and `execute_workspace_script_tool.py`, both of which branch on `SandboxMode` with the jobs-mode branch currently bridge-blind), and the pod-side/backend side-channel layer (`tool_call_channel.py`, `codemie_runtime_sdk.py`, `pod_scripts/*.py`), which research confirms is already pod-agnostic and needs no logic changes — only a different way for the caller to obtain a pod/container binding for a Job's pod instead of a pooled `SandboxSession`. The removal side of the task is concrete and enumerable (five call sites plus a `session_timeout`-based clamp that is already dead for jobs mode), but the addition side is genuinely novel: nothing in this codebase today models "poll a side channel while a separate blocking wait proceeds" for a single-shot Job, which is a materially different concurrency shape than the pod-lock-around-one-`session.run()` pattern pooled mode used.

Test coverage is substantial in the surrounding code (604 + 1000 + 631 + 276 lines of tests across the four most relevant files) but has zero coverage of the actual new behavior this ticket enables, since that behavior doesn't exist yet — Stage 4 planning should expect to design new test infrastructure (a fake/threaded Job lifecycle double) rather than extend existing fixtures, several of which (`TestWorkspaceScriptRunnerJobsMode`, `TestExecuteCodeSandboxChannel`) will need to be rewritten rather than deleted outright, since they encode assertions (`sb.assert_not_called()`, pod-lock sequencing) that describe the current no-bridge-in-jobs-mode and pooled-only-bridge states respectively.

Key risk factors: (1) `activeDeadlineSeconds`/`execution_timeout` are not currently reconciled with the tool-calling timeout at all for jobs mode, and the two defaults (30s vs 120s) are already inconsistent in a way that would kill a bridge-enabled Job before its tool-calling budget expired; (2) the read-only-root-filesystem + two-emptyDir constraint bounds where an exchange folder can physically live; (3) pooled-mode removal scope must be disentangled from `SandboxMode.SHARED`'s continued use for plain (non-bridge) pooled code execution, which this research does not resolve; (4) documentation/admin-settings copy in three places currently asserts a limitation this ticket removes. None of these are architecturally exotic (the codebase's existing patterns — shared deadline budgets, best-effort cleanup, `ExecRunner`-protocol testability — are directly reusable), but the concurrency design itself is new ground for this codebase.
