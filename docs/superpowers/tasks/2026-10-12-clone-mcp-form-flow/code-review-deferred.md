# Deferred from code review — 2026-10-12-clone-mcp-form-flow (2026-10-12)

- **No ownership/visibility check on clone source** — `src/codemie/service/mcp_config_service.py` (`clone_from_form`, `suggested_clone_name`) — `MCPConfig.find_by_id(config_id)` is gated only by `admin_access_only`, not by "admin owns this config" or "config is public/system", so any admin can clone (or probe the next name for) a different user's private config, carrying its encrypted `client_secret` into a new record the cloning admin owns. Pre-existing: identical pattern already governs `get_mcp_config`/`get_by_id` (available to *all* authenticated users, no owner check) and the pre-change clone route this story explicitly replaces only the request body of; the story's scope is `is_system`/`is_public`/secret-carry-over/`auth_config.id`/error shapes, not the authorization model.
- **Clone source lookup not filtered by `is_active`** — `src/codemie/service/mcp_config_service.py:352` (`clone_from_form`) and `:427` area (`suggested_clone_name`) — a soft-deleted/inactive source can still be cloned or have its name suggested. Pre-existing: `MCPConfigService.get_by_id` uses the same unfiltered `MCPConfig.find_by_id` lookup project-wide; this change reuses that existing lookup rather than introducing it.
- **Check-then-insert duplicate-name race** — `src/codemie/service/mcp_config_service.py:361-373` (`clone_from_form`) — the pre-check (`MCPConfig.get_by_fields`) followed later by `mcp_config.save()` lets two concurrent requests with the same name both pass the check; only the `auth_config.id` conflict is mapped to a typed exception, so a name race would surface as an opaque error. Pre-existing: `create()` (lines 268-280) has the identical check-then-insert shape, and `clone_from_form` was written to intentionally mirror `create`'s validation/error-shape pipeline per the story.
