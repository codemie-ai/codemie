# Spec: backend classification and destination routing for CLI analytics (EPMCDME-16440, child backend-ingest-routing)

Original planning base: codemie `origin/main` 381dc7fd. Requirements: `story.md` (this dir) and parent story D2, D3-rev, D3-iface, D7, D10, D11. Updated against implemented review fixes at `a03fd3aecac1705e15ab1439cba5a85a68c212ad`. Open decisions are listed below.

## Planning baseline observations
- The 16025 gate is already on main; worktree clean (analysis' "dirty" is stale). Gate: `service/analytics/cli_analytics_project_gate.py:52-81`, called per request from `rest_api/routers/cli_analytics.py:150-152`.
- Project is stored **only** on hook rows (`codemie_project_name`); `usage_requests`, spans and metrics carry no project column. Legacy writes enter independently at `ingestor.py:361-383` (`_attributed_to`/`_hook_in_project`, `ingestor.py:278-342`, keep a row whose own project differs).
- `session_dims` recompute (`rollups.py:1905-1924`): project = earliest non-empty hook value by `ts`, merged so a recompute reaching further back overrides the stored value (`_earliest_merged`); `jwt_email = GREATEST(...)` (max across rows).
- **`session_dims` lifecycle supports a row without hook rows** (`alembic_cli_analytics/.../a1c1a0000001...py:253-266`): only `session_id` is NOT NULL, `updated_at` defaults to `now()`, `started_at` NULL means "no dimension hook event", and the reader lists only `started_at IS NOT NULL` sessions (`reader.py:288`), so a binding-only row appears in no dashboard. The idle purge (`session_purge.py:51-57`) tests `coalesce(greatest(last_event_at, ended_at), updated_at) < cutoff`, so a binding-only row lives as long as its `updated_at` is recent and is removed only by the idle-session purge, outliving raw rows. Hence no new table.

Admin settings: `customer_config.get_feature_setting`, TEXTAREA/SWITCH in `customer_config_declarations.py`. Default resolver: `rest_api/security/user.py:31-46`.
- Registration candidates re-checked: only datasource `git_url`+`project_name` (`rest_api/models/index.py:1476`), user-owned indexing config; a new mapping is specified (section 7).

## Design

### 1. Contract (request level, new optional headers on all four ingest routes)
`X-CodeMie-Session-Id`, `X-CodeMie-Routed-Via-CodeMie`, `X-CodeMie-Organization` or `X-CodeMie-Organization-Encoded` (name only; used to classify, never stored), `X-CodeMie-Project-Source` (`linked_folder|profile`), `X-CodeMie-Subscription-Type`, `X-CodeMie-Policy-Version` (client advisory), optional `X-CodeMie-Repo-Remote`. Any present = **evidence request**; none = **legacy request**: gate, conflict and dedup unchanged, except for the binding guard (6c) which only acts on evidence-bound sessions.

The evidence envelope requires a non-blank session header; otherwise HTTP 400 `session_id_required`, before decoding or storage. Plain organization values are not percent-decoded. Non-Latin-1 names use `X-CodeMie-Organization-Encoded: utf8-b64u.v1:<payload>`: canonical unpadded base64url of the original strict UTF-8 text, without transport normalization. Limits: 1366 payload characters, 1024 decoded bytes, 256 code points; blank text and C0/C1 controls are rejected. Both organization headers give HTTP 400 `organization_conflict`; invalid encoded values give `organization_invalid`. A non-CodeMie-routed request claiming `personal` or `corporate` without a usable organization gives `organization_required`. These errors do not acknowledge the CLI spool range.

### 2. Classification (pure function, D7 order)
CodeMie routing -> `codemie`; org missing/blank or list empty -> `unknown`; org in list (trim, case-insensitive; org names are free-text labels, unlike repository identity) -> `corporate`; else `personal`.

### 3. Policy
Customer config `cliAnalytics`: TEXTAREA `corporateOrganizations` (one per line, no defaults). Version = short SHA-256 of the normalized sorted list. `GET /v1/analytics/cli-analytics/classification-policy` (authenticated, behind `_ensure_enabled`) returns `{organizations, version, organization_encodings: ["utf8-b64u.v1"]}`. Encoding capabilities are not part of the policy version.

### 4. Order of decisions for an evidence request
Validate the request envelope and derive classification before storage. After decoding, check the single-session boundary (6), then stale policy: only when both client classification and policy version are supplied, a different version AND a different classification give HTTP 409 `{reason:"stale_policy", policy_version}`, with nothing stored. Binding lookup/owner checks, resolution and validation of the actual destination, binding upsert and row insertion run in one storage transaction under the session lock. Existing bindings and legacy anchors take precedence over fresh routing candidates; unused candidates are not resolved or provisioned.

### 5. Destination
- Derived `personal`: only the owner's personal project (`project_type=personal`, `created_by` = authenticated user), origin `personal`, regardless of header or client claim. Missing project -> `ensure_personal_project_async`; False/lookup error -> 503 retryable. Never a shared project. Excluded user type (`external`, `service_account`, via `is_personal_project_excluded`; EPMCDME-14413 forbids their personal projects): the session stays Personal-paid (`subscription_type=personal`) but is routed like any other session to an authorized work project (link, registration, default), no personal project is created, and no usable destination is the retryable `default_project_unavailable`.
- Otherwise, first hit wins: (a) header project **only when** `X-CodeMie-Project-Source` is present and the project exists, is not deleted, and passes the existing access and live-membership checks -> origin `linked_folder`/`profile`; (b) registered repository (7); (c) effective default project (9) -> origin `default_project`. A header without a source is ignored for routing.
- `route_note` (stored in the binding; empty for linked/registered/personal): `folder_not_linked`, `linked_project_unavailable`, `registered_project_inaccessible`, `registration_ambiguous`; explicit, logged and counted.
- Enablement follows the **destination's** `project_type`: shared needs `cli_analytics_enabled` (false -> existing final discard `cli_analytics_disabled`); a personal destination owned by the user needs no flag (D11; `PERSONAL_CLI_ANALYTICS` rejection removed) with no separate activation setting.
- Owner = authenticated `User`; Claude account data never read.

### 6. Rebinding and single-session boundary
- Evidence request = one session = one classification and destination. A non-blank `X-CodeMie-Session-Id` is required (missing/blank is HTTP 400 `session_id_required`); every session id decoded from the body (all four routes) must equal it, else the whole request is discarded (HTTP 200, nothing written) with `evidence_session_conflict`. Explicit body project values keep the legacy check against the **header** (`project_context_conflict`).
- Persistence: `_attributed_to` replaces `codemie_project_name` on every hook row of an evidence request with the resolved destination **unconditionally** and stamps `subscription_type`, `project_origin`, `route_note`, `client_subscription_type`, `client_policy_version` (nullable columns, alembic migration). Legacy requests keep `_hook_in_project`. Usage, cost and rollups follow the session through `session_id`; no other table gets a project column.
- Dedup identity is computed from the event as sent; an exact re-send is a duplicate; stored rows are never rewritten. Legacy rows read `unknown` / empty origin.

### 6b. Session binding (durable, created synchronously)
- **Binding** = new nullable `session_dims` columns `owner_email`, `subscription_type`, `project_origin`, `route_note`, plus `project_name` and `jwt_email` set to the destination and the owner. No new table.
- **Creation**: the first accepted evidence request of a session, on any of the four routes **including requests with no hook rows** (metrics, traces, usage-only), upserts the `session_dims` row in the **same storage transaction and under the same per-session lock** as the stored rows: `INSERT ... ON CONFLICT (session_id) DO UPDATE` setting the binding columns and `updated_at = now()` only `WHERE owner_email IS NULL` (an existing row from legacy-first computation is bound in place; a bound row is never changed; later accepted writes only refresh `updated_at` so the idle purge cannot drop an active binding). Every request rejected by a gate or guard (409, 503, any discard, validation error) happens before the transaction body or raises inside it, so **no binding is created or changed**; a failing insert rolls back binding and rows together.
- **Recompute/rollup only reads/preserves**: it never inserts or sets the binding columns; for a row with `owner_email` set it keeps the stored `project_name` and `jwt_email` and ignores `_earliest_merged`/`GREATEST` (the recompute's `ON CONFLICT DO UPDATE` list simply omits the binding columns). Derivation reads project/type/owner from the binding, not from min timestamp or max(jwt_email). Planning must confirm readers tolerate binding-only rows (`started_at` NULL is an existing state).
- **Lookup order** (under the lock): `session_dims.owner_email` set = evidence-bound. No hook-row fallback is needed: evidence hook rows exist only from this feature on, and each is written with a binding. For an **unbound** session, a probe of its legacy project (`session_dims.project_name` if the row exists, else the earliest non-empty `hook_events` project) is used only to apply the rules below to an evidence request; no row at all = new session.
- Evidence request on a bound session (after the stale check; a 409 never touches the binding):
  - different user -> discard whole request, `session_owner_conflict`;
  - bound shared destination, derived Personal -> discard, `session_project_conflict` (never split a session, never expose);
  - bound personal, derived anything -> bind-to-existing: stored under the personal project with the bound type (derived value kept in diagnostic columns); ownership still applies;
  - bound shared, derived non-Personal with different type/destination (policy change, new registration, changed default) -> bind-to-existing under the bound project and type; usual existence/access/membership/enabled checks run on the bound project.
- Evidence request on an unbound session with legacy rows under project P: a known legacy owner must match the authenticated sender; unknown legacy ownership can be adopted. Personal derived and P is not the sender's personal project -> `session_project_conflict`, without provisioning. A non-Personal request adopts P and validates P only; the origin stored is `legacy_project` for every classification (approved AC8; no route is guessed, no backfill of earlier rows); a broken unused default or new candidate does not block that adoption. A Personal request whose legacy anchor is already its owner's personal project follows the Personal destination checks.

### 6c. Guard on every write path
- **Every** ingest, legacy or evidence, on event-hooks, logs, metrics and traces, takes `pg_advisory_xact_lock(hashtext(session_id))` for each distinct session id in the decoded batch (sorted, to avoid deadlock) in the transaction that inserts, and runs the guard before any row is written. A legacy-only (never evidence-bound) session pays the lock and a lookup; its behavior is otherwise unchanged.
- Guard for an **evidence-bound** session (defensive rejections, implementation-level; each with a reason in the response, a log line and a counter):
  - authenticated user differs from the bound owner, or sender email is missing (legacy, evidence, hook or non-hook routes) -> discard whole request, `session_owner_conflict`; evidence adoption also rejects a different known legacy owner;
  - legacy hook row, effective project (after `_hook_in_project` stamping) empty or equal (case-insensitive) to the bound project -> stored with bound project/type/origin stamped; different project -> discard whole request, `session_project_conflict`. An earlier timestamp never changes the binding, which is stored state;
  - non-hook rows carry no project: stored when the owner matches.
- Discards are HTTP 200 with the reason (`{"accepted":0,"dropped":N,"reason":...}` / OTLP `partial_success`), final for that request. Chosen over 409/retry because a retry cannot succeed, and over relabelling a contradicting legacy project to the bound one because that would silently rewrite another claim.
- **Mixed-batch loss is observable**: a request is never split, so its other sessions are dropped with it. The log line and counter carry reason, offending session id (hashed), `dropped` wire count and `other_sessions_dropped` (count of the request's other distinct session ids). Cross-child contract (CLI child, required): on any discard response the CLI must not clear the spool entries of the request's other, unrelated sessions without handling the response; it must retry them separately (grouped per session) and clear only the offending session as dropped. The evidence requests it sends are per session already (6), so this concerns legacy-style multi-session batches only.
- **Concurrency**: the lock serializes first writes. Legacy-first then evidence-first for a new session: the legacy rows exist, the session is unbound, the evidence request binds per 6b (Personal vs legacy shared project -> discard; else bound to P). Evidence-first then legacy: the binding already exists and the guard applies. Two evidence requests: the second resolves against the first's committed binding.
- **Raw expiry**: because the binding is created in the first accepted transaction, it exists even if no hook row ever arrived and raw rows expire before any recompute. A later request finds the binding: same user and destination -> stored; different destination -> 6b outcomes; different user -> `session_owner_conflict`; contradictory legacy ingestion -> `session_project_conflict`. Only when the idle-session purge removes the `session_dims` row (past session retention, with every child row) is the session id new and bindable afresh; no private row remains then.

### 7. Repository registration (in scope)
- Store: new table `repository_project_registrations(normalized_remote UNIQUE, project_name, created_by, created_at)`; one repository maps to at most one project, so ambiguity cannot arise by design.
- Normalization (one function, on write and on lookup of the `repo_remote` carried by hook rows or `X-CodeMie-Repo-Remote`) collapses only proven-equivalent transport spellings: lowercase the **hostname only**; **path case preserved**; strip credentials; drop scheme, trailing `/` and `.git`; scp `git@host:org/repo`, `ssh://git@host/org/repo` and `http(s)://host/org/repo` all become `host/org/repo`. A port equal to the scheme default (ssh 22, https 443, http 80) is dropped; any other port is kept and part of identity. No provider catalogs. Unparseable -> 400 on write, no match on lookup. Credentials never stored or logged.
- REST (no UI): `PUT|DELETE /v1/projects/{project_name}/repositories` with exactly one of `{remote}` (raw URL/scp spelling, normalized once) or `{key}` (the returned canonical identity, used without re-normalization), and `GET` list. `GET` and `PUT` return `{key, project_name}`; a returned item can be sent to `PUT` or `DELETE`. Ambiguous/invalid bodies give 400. Allowed: global admin/maintainer or project admin (`is_application_admin`). Personal projects cannot be registered (400). A remote registered to another project -> 409 on write. Registration, project rename and delete lock the project row in their transaction; a registration authorized before a completed rename/delete returns 404 without writing. Rename moves registrations and delete removes them; this does not migrate analytics session bindings or history.
- Registered project inaccessible or deleted -> not used, `route_note=registered_project_inaccessible`, default. More than one match (constraint bypassed) -> no pick, `route_note=registration_ambiguous`, error log, default.

### 8. First-upgrade limitation
First-upgrade corner case: while old and new backends serve the same installation during an update, an administrator using an old backend may read Personal sessions already saved by the new backend. This window ends when old backends stop serving requests; it does not recur on later upgrades between versions with owner-only reads, but returns on rollback to an unprotected version. This limitation requires explicit security sign-off.

### 9. Default destination (D10)
Default = the existing resolver (`rest_api/security/user.py:31-46`), **reused unchanged**; it may be the user's own personal project, except for an excluded user type (external, service account), whose old personal project is never a destination of a new session of ANY classification (header, registration and default alike; a default naming it is the retryable `default_project_unavailable`, nothing substituted or created). subscription_type and destination `project_type` are independent: a Corporate/CodeMie/Unknown session whose effective default is the owner's personal project is stored there (origin `default_project`, `route_note=folder_not_linked`), owner checks retained, no bypass to another shared project. Failures, no arbitrary fallback:
- No projects at all, for any user type -> retryable 503 `default_project_unavailable`, warning log, counter; the CLI retains unacknowledged data for its finite retention window (default 24h, bounded backoff, expiry discards only the affected range with reason and byte count; paired-client contract of the approved AC9, reviewed but not live end-to-end verified). No arbitrary fallback or automatic project creation.
- Default missing, deleted, not accessible or membership removed -> retryable 503 `default_project_unavailable`, warning log, counter.
- Shared default with `cli_analytics_enabled=false` -> existing `cli_analytics_disabled`. Policy lookup error -> 503.
A bad default never reroutes a non-Personal session elsewhere; Personal-derived never lands in a shared project.

## Acceptance criteria
1. Classification matrix (CodeMie in/out of list, empty list, missing org, match, non-match) stores codemie/unknown/unknown/corporate/personal per D7.
2. Policy endpoint returns list + version to any authenticated user; empty list explicit; version changes only with the list.
3. Header project with source stores origin `linked_folder`/`profile`; header without source is ignored for routing.
4. Registered repository routes to its project when no link exists; link beats registration; registration beats default.
5. Normalization: scp/`ssh://`/https forms of one default-port remote equal; `.git`, trailing `/`, credentials, host case ignored; paths differing only in case distinct; non-default ports distinct from each other and from the default-port form.
6. Registration writes: project admin, admin or maintainer only; personal project and duplicate remote rejected; credentials not stored.
7. Registered project inaccessible/deleted/forced-ambiguous: not used, default with explicit `route_note`.
8. No link and no registration: effective default project, origin `default_project`, `route_note=folder_not_linked`.
9. Personal-derived: only the owner's personal project, with no per-project admin enablement or separate activation setting, even if the header names a shared project; shared `cli_analytics_enabled` policy unchanged.
10. Rebinding: hook rows, session_dims, usage/cost and rollups only under the personal project on all four routes; legacy-only sessions behave exactly as before (regression).
11. Evidence envelope without a non-blank session header: HTTP 400 `session_id_required`; decoded session ids differing from that header: final `evidence_session_conflict`; conflicting explicit body project: `project_context_conflict`. Invalid organization envelopes are HTTP 400 as specified in section 1.
12. Personal project missing: provisioned; failure 503; excluded user type reasoned discard; never shared.
13. Default failure: deleted/inaccessible/missing default or no projects -> retryable 503; a failed default never reroutes a non-Personal session and never affects a Personal one. A valid existing binding or legacy anchor does not resolve an unused default.
14. Default-is-personal fixture: Corporate/CodeMie/Unknown with no link and no stored default is stored in the owner's personal project, origin `default_project`, no separate enablement; another user cannot target it.
15. Eligible Personal destinations accept writes without an activation setting; ownership, excluded-user policy and failure handling remain enforced.
16. Stale version + differing classification: 409 with current version, nothing stored, no binding created; a 409 between batches leaves an existing binding intact.
17. Two sequential non-duplicate evidence batches of one session_id: same destination -> both stored; Corporate then Personal flip -> second discarded `session_project_conflict`; Personal then Corporate flip -> second under the personal project; shared then registration/default changed -> under the bound project; legacy shared rows then Personal evidence -> discarded.
18. Binding atomicity: any rejected request (409, 503, owner/project conflict, disabled project, provisioning failure) leaves no `session_dims` binding and no rows; a failure inside the insert rolls back binding and rows together; the first accepted request on each of event-hooks, logs, metrics and traces (including metrics/traces/usage-only with no hook rows) creates the binding in the same transaction; recompute never creates or overwrites it.
19. Personal evidence session, then a legacy hook with an earlier timestamp and a shared project: discarded `session_project_conflict`, nothing written, `session_dims` project/type/owner unchanged; an earlier-timestamp hook with an empty or the same project is stored with the bound project.
20. Different authenticated user writing a bound session via legacy event-hooks, evidence, logs, metrics and traces: each discarded `session_owner_conflict`, nothing stored; owner and `jwt_email` unchanged.
21. Concurrent writes for one new session_id (legacy-first vs evidence-first, two evidence requests) are serialized by the lock; the outcome equals a sequential order and no session is ever attributed to two projects.
22. Hookless first request then expiry: first evidence request is metrics/traces/usage-only (no hook rows) and creates the binding; raw rows expire before any recompute; then (a) same user and destination is stored, (b) a different destination follows 6b, (c) another user is discarded `session_owner_conflict`, (d) a contradictory legacy hook is discarded `session_project_conflict`; the binding survives and protects the remaining data. After the idle-session purge the session id is new.
23. Recompute never overrides a stored binding (older replayed row, `backfill.reclassify`, changed max(user_email)).
24. Mixed-batch observability: a discard of one session of a multi-session legacy-style request returns the reason and `dropped` count and logs/counts `other_sessions_dropped`; nothing else of the request is stored.
25. Owner is the authenticated user; requests without evidence to never-bound sessions behave as before; legacy rows read unknown / no origin.

## Non-goals
- Analytics read fields, filters, visibility, spend (backend-analytics-read).
- CLI evidence, local classification, policy cache, opt-out, sending the registration key (CLI child, 16396, 16394); the CLI's handling of discard responses is a contract requirement on that child (6c), not delivered here.
- Registration admin UI, bulk import, discovery, per-user registrations, provider remote catalogs.
- Per-person admin enablement of personal projects; changes to shared `cli_analytics_enabled` policy or to the default resolver.
- Rewriting stored history; project columns on non-hook tables; codemie-ui; cost mapping (16390); storing organization names or Claude account data.

## Risks
- Reasons `session_owner_conflict`, `session_project_conflict` are defensive implementation-level rejections; a legacy sender of a bound session whose project differs loses those requests, and a mixed request loses its other sessions (observable via reason, `dropped`, `other_sessions_dropped`).
- Cross-child: CLI must handle discard responses per session and not clear unrelated sessions blindly; adopt one request per session, the session header, 409/503 handling, and `X-CodeMie-Repo-Remote` if hook rows lack `repo_remote`.
- Every ingest takes a per-session advisory lock (legacy included) and evidence ingest adds a `session_dims` upsert; measure in planning.
- Binding-only rows stay unlisted, and recompute/reclassification preserve bindings; covered by `test_live_session_binding.py`.
- Remotes a provider treats as one under different path case or non-default ports stay distinct (safe direction).

## Current limitations and open decisions
- Personal-paid sessions of excluded user types go to a work project (decided; resolves the former AC3/AC9 exception). `personal_destination_unavailable` is a final discard for an old personal-project destination of such a user, whatever the classification (a bound or legacy anchor); ordinary personal-project provisioning failure remains retryable 503 with this reason.
- Bindings store the technical project name. For an ALREADY BOUND session, a confirmed rename, deletion or loss of access/membership is the final discard `session_project_unavailable` (HTTP 200, which the CLI acknowledges), without rerouting, provisioning or history migration; a failed lookup, an unbound legacy project and a new session without a destination stay retryable 503; shared analytics explicitly disabled still yields final `cli_analytics_disabled`. Rename continuity and the end state of pending data are not implemented. Changing only the existing display name does not change the technical binding.
- Explicit human security approval is still required for the attribution and privacy contract.
- Policy change on an anchored session: only a request newly Personal for an ordinary user on a session anchored outside the user's own personal project ends collection (`session_project_conflict`, history and binding kept, never rerouted); every other classification change does not terminate by itself. Corporate-list edits therefore stop live shared-anchored sessions that turn Personal; a new CLI session follows the current rules.
