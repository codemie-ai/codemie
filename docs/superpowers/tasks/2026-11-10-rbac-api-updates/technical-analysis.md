## 1. Original Context

"https://gitbud.epam.com/epm-cdme/codemie-enterprise/-/merge_requests/76 также. То есть наша задача сейчас сделать api, которое потом будет использоваться уже измененной kron job."

Ticket EPMCDME-16895 (Sub-task of EPMCDME-15435), "IdP-Managed Users — Service-account management API and identity guard". Repository: codemie (this repo). Sibling sub-tasks: removal of in-repo sync (independent), customer-side sync job (depends on this one).

Context:
- The platform recognises a non-human caller by identity only in the Teams billing swap: a config parameter names the account, the check compares the caller's id and user_type=service_account, a miss falls back silently. No identity-based request guard exists; all guards are role-based.
- Every operation the API needs has a service-layer counterpart, but none is idempotent: membership assignment answers 409 on existing member and 404 on non-member; one membership service sets up budget but does not create the project, the other creates the project but sets up no budget; user updates reject reactivation and non-local email changes; the current branch adds a blanket 403 inside the user-access service and on platform-admin changes while the "IdP-Managed Users" switch is on.
- Deactivation has last-administrator protection but neither auth-cache invalidation nor a self check. The user list always excludes soft-deleted users.
- New routes change the router-guard OpenAPI and precedence baselines, which are regenerated by hand.

Story: As a platform operator whose identities are federated through Keycloak, I want a management API that only a dedicated service account can call, with idempotent create, assign, unassign and deactivate operations and the reads a sync client needs, so that every write to users and memberships goes through the platform while scheduling stays outside it.

Acceptance criteria (abridged headings; full text in the ticket):
Access: no service-account identity configured -> any call to the management API forbidden; configured service account with valid IdP token accepted whether the switch is on or off; any other caller (incl. platform admin / another service account) refused; the configured service account calling anything outside the management API refused (Teams bot unaffected).
Operations (users by IdP identifier, projects by name; membership ops through the project-membership operations the projects API uses - budget membership set up/cleaned, activity events recorded; user ops through existing user flows; service account recorded as actor): create user (profile + Keycloak admin role; admin = Keycloak admin role OR configured admin user; no personal project); create existing = update differing profile fields/admin status, reject demoting last admin; create deactivated = reactivate, visible in all reads, revoked authorisations not restored; assign with/without project-admin, missing project created as on first login, repeat no-op, differing admin right updated; remove member (budget cleaned), removing non-member succeeds, pre-existing personal project rejected; deactivate = admin deactivation + immediate auth-cache invalidation, last admin and service account itself not deactivatable; unknown user/malformed -> not-found/validation error.
Reads: one user (active, profile, admin status, memberships with project-admin + is-personal); list page by page including deactivated; page of 100 with memberships within 1s at 60,000 users.
Contract/regression: models in router-guard baseline, documented as contract; admin membership ops locked under the switch unchanged; switch on -> in-platform mutations rejected, reads and budget management work, switch visible in public configuration.
Out of scope: removal of in-repo sync; the sync job; budget clean-up beyond admin deactivation; users disappearing from Keycloak; KB access sync, legacy user mode, changing platform-admin derivation, editing Keycloak, admin UI.

### Decisions Already in the Code
- Switch lock is applied at two layers: router dependency `require_no_idp_lock` (`idp_lock.py`) on mutation routes, and inline `HTTPException(403)` inside `UserAccessService.grant_project_access:93`, `revoke_project_access:210`, KB grant/revoke (:287, :335), and `UserManagementService._reject_idp_admin_change:721/730`. `ProjectAssignmentService` has no inline lock (only its routers do). Reason recorded: none beyond docstring in `idp_lock.py`.
- Convention: service methods take `Session` and a `User actor`; routers commit (`session.commit()` in router for project assignment; service commits in `UserAccessService`). Errors via `ExtendedHTTPException(code, message, details, help)`.
- Convention: activity events via `activity_event_repository.insert(ActivityEventCreate(domain=USER_MANAGEMENT, ...), session)`.
- `IDP_MANAGED_ENABLED` forces `ENABLE_USER_MANAGEMENT` on (`config.py:1039-1046`); user routes check `config.ENABLE_USER_MANAGEMENT` and answer 400 otherwise (`user_management_router.py` deactivate).
- Switch is published in public configuration: `rest_api/routers/common.py:38` (`idp_managed_enabled`, model field `core/models.py:891`).
- Personal project is not created under the switch on first login (`authentication_service.py:244`); personal-project exclusion for `external`/`service_account` user types is by user_type, independent of switch.
- Auth-cache is in-process dict `_auth_token_cache` keyed by token; invalidation by user id exists but is called only from update/membership paths, not deactivation.
- Data direction: soft-deleted users are hidden by default in getters/lists (`get_by_id` and `_apply_filters`); the reads this task needs are the opposite direction (include deactivated). `fetch_projects_map` returns `UserProject` rows without an is-personal flag (personal status lives on `Application.project_type`).
- User identity: `UserDB.id` = Keycloak subject id on first login/sync (`coordinator._create_user` uses `profile.id`); lookup by e-mail is secondary. UUID format validation is skipped when `ENV==local`.

## 6. Risk Indicators

- The in-repo sync (`enterprise/sync/coordinator.py`) is a second implementation of user create/reactivate/membership logic with different rules (no budget, no events); kept in place by the out-of-scope statement; consumers: `Dockerfile.sync`, sync tests. See Existing Implementations B.
- Task keeps the switch lock in place (router `require_no_idp_lock` and inline 403s in `UserAccessService`/`UserManagementService`) while the new API must operate under the switch: see Decisions and Statements sections.
- Two membership services with divergent behaviour (budget vs project creation, personal-project check) - see Purpose C.
- Speculative: no existing app-wide route-scoped caller restriction; "service account refused outside the management API" has no existing mechanism to extend (routers registered individually, `authenticate` is per-route).
- Speculative: plain `get_by_id` and list queries hide inactive/soft-deleted users; reads for deactivated users and reactivation touch shared repository getters used by auth and budgets.
- `mr76` token parsing and `coordinator` group prefixes are duplicated across repos; Keycloak admin-role derivation lives outside this repo (unverified here).
- 1s/100-user/60k requirement unverified; list ordering `date.desc()` with offset and the two-query membership fetch are what exist.
- Baselines must be regenerated by hand (`regenerate_baselines`); easy to drift.
- `/tmp/ce-mr76.ufKc` cannot be read with plain `git` in this environment (use `/usr/bin/git`); working tree has no checkout.

## 7. Summary for Complexity Assessment

The task touches the router layer (new management router registered in `rest_api/main.py`), a new identity-based security dependency, the user service (`UserManagementService`, `AuthenticationService` first-login helpers), the project membership service (`ProjectAssignmentService`) and the user repository read paths (include deactivated; memberships with personal flag), plus the router-guard baselines. No new schema is established as required by research; all needed tables (`UserDB`, `UserProject`, `Application`) exist.

Technical novelty: moderate. There is no precedent for a caller-identity guard beyond the Teams resolver, and no existing idempotent counterpart for any operation; the existing services each embody part of the required behaviour (budget sync in `ProjectAssignmentService`, project creation in `UserAccessService`/`_ensure_projects_exist`, reactivation and profile diff in the in-repo sync coordinator) and several are gated by the switch lock. Coverage around existing services is good; the new guard, idempotency, deactivation-cache and deactivated-user reads have no tests.

Key risks: duplicated membership logic, switch-lock paths that must remain unchanged, hidden-by-default soft-deleted users in shared getters, the 60,000-user paging performance target with no baseline, and hand-regenerated contract baselines.
