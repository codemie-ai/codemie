## 1. Original Context

Fix EPMCDME-16496 AC4 failure: "listed and counted for a period only when it has activity in that period" is not met.

Context from Jira ticket comments (2026-11-10):
- Root cause in postgres/reader.py: _active_in_window / _SESSION_ADMITTED_IN_WINDOW (main: ~line 257-268, _admitted_arms) admits a session into a period if it has a daily rollup row on a partial window day AND any record from _RAW_ACTIVITY_SOURCES stamped inside the window. _RAW_ACTIVITY_SOURCES includes every non-OTHER log/span and claude_code.lines_of_code.count metric points, INCLUDING ZERO-VALUE points (rollups.py ~line 1796 treats a zero-lines row as "known, zero included").
- This means exit-time housekeeping records (final metric export at shutdown, exit-time log/span, or in the newest repro a synthetic user_prompt log emitted by Claude Code's /exit command) get misclassified as real in-period activity (a prompt, API call, or tool call), causing sessions with zero real activity in the window to be listed and counted with their whole-session (all-time) numbers for that period.
- Also: for reopened sessions (EPMCDME-16993), a session can be admitted via the "started_at is in window AND _has_any_activity" branch, which has no day bound at all.
- Confirmed NOT a regression of EPMCDME-15337 cross-endpoint consistency: Overview total_sessions, Sessions list total, sum(Users.session_count), sum(Repositories.session_count), Cost total_sessions, and sum(Activity.by_weekday) all agree with each other on every tested filter — the bug is specifically about which sessions get admitted into a period, not mismatched totals across endpoints.
- Required regression tests (per QA's recommendation in the ticket):
  1. Integration (live PostgreSQL): a session active on day D1 whose only records in window W are lifecycle hooks (session.start/env/end, git.snapshot) is not returned by sessions, overview, users, repositories, cost, or activity for W. Cover both: started_at moved into W by reopen (EPMCDME-16993), and not moved.
  2. Integration: a session whose only records in W are records stamped at exit (zero-delta lines_of_code point, non-prompt log/span, or a synthetic user_prompt from /exit) and no real prompt/API request/tool call is not listed or counted for W.
  3. Unit: hour-based presets (last_hour, last_6_hours, last_24_hours) on a window that crosses UTC midnight — a partial UTC day must require an activity record inside the window, not just a daily rollup row.
  4. Contract: for the same filter, overview total_sessions = sessions total = sum(users.session_count) = sum(repositories.session_count) = cost total_sessions = sum(activity.by_weekday).

Goal of the fix: tighten the period-membership check in reader.py so that only genuine activity (a real prompt, an API call, or a tool call) — not lifecycle/housekeeping records, zero-value metric points, or /exit's synthetic user_prompt — can admit a session into a given period window. Fact *values* (turns, cost, tool calls shown per session) should remain all-time sums as before; only *membership* changes. Ticket: EPMCDME-16496.

## 2. Codebase Findings

### Existing Implementations

**Purpose: decide whether a session belongs to the requested date window ("period membership").**
- `_SESSION_ADMITTED_IN_WINDOW` (`src/codemie/repository/cli_analytics/postgres/reader.py:259`): `(( _STARTED_IN_WINDOW AND _has_any_activity('d') ) OR _active_in_window('d'))`. This is the one predicate; it is applied in exactly one place, `_sessions_cte` (`reader.py:690-743`), which builds the CTE `sel`. Every fact query in the reader (cost, users, lines, turns, tool success, invocations, repository sessions, session detail list, etc. — ~30 methods) scopes or joins to `sel` and carries no day/timestamp predicate of its own (confirmed by `test_every_fact_a_windowed_query_reads_is_scoped_to_the_selected_sessions`, `test_no_fact_query_carries_its_own_window_and_all_are_scoped_to_sel`, `reader.py:386,1318`). This is the single chokepoint the task must change; every endpoint (Overview, Sessions, Users, Repositories, Cost, Activity) consumes `sel` and therefore inherits whatever membership rule lives here.
- `_active_in_window` (`reader.py:232-245`): the "activity rescue" arm. For a UTC day wholly inside the window (`_FIRST_WHOLE_DAY_UTC`..`_LAST_WHOLE_DAY_UTC`) a row in any of `_ACTIVITY_TABLES` (`turns_daily, tool_facts_daily, cost_daily, session_usage, lines_daily`, `reader.py:180`) is sufficient with no further check. For a day the window covers only partially (`_START_DAY_UTC`..`_END_DAY_UTC`), the day-row check is additionally ANDed with `_raw_activity_in_window` (`reader.py:221-229`), which is true if *any* row of `_RAW_ACTIVITY_SOURCES` (`reader.py:212-218`: `hook_events` filtered to `_ACTIVITY_HOOKS`, all of `usage_requests` unfiltered, `log_events` filtered only to `event_kind <> OTHER`, `spans` filtered only to `span_kind <> OTHER`, `metric_points` filtered only to `metric_name = ANY(LINES_METRICS)`) is stamped inside the window. None of these five source clauses excludes a zero-value metric point, a non-prompt-but-non-OTHER log/span, or a synthetic `user_prompt` — this is the exact mechanism the task names as the root cause.
- `_has_any_activity` (`reader.py:248-256`): `_activity_exists` with no day bound at all — true if the session has ever produced a row in any of `_ACTIVITY_TABLES`, lifetime. This gates the unconditional `_STARTED_IN_WINDOW` admission arm, i.e. "started in the window and has *ever* had real activity" (not necessarily in the window). Per the storage guide (`cli-analytics-storage.md:53`) this is deliberate for `started_at`-precision reasons, but it is also the mechanism the task flags for reopened sessions (EPMCDME-16993): a reopen that moves `started_at` into the window is admitted here without any day-bound check on the window itself, same gap as `_active_in_window`'s zero-signal problem but via a different arm.
- `_admitted_arms` (`reader.py:270-301`) and `_sel_ctes` (`reader.py:304-322`): the same `_SESSION_ADMITTED_IN_WINDOW` predicate, decomposed into 5 indexable `UNION ALL` arms for performance (stored facts `has_activity`/`last_activity_day`/`resumed` stand in for the unbounded table probes once derived). Documented in the storage guide as "the candidate filter is not a pre-filter on the rule's meaning: the rule is still evaluated, unchanged, on every candidate" (`cli-analytics-storage.md:61`) — i.e. whichever predicate change the fix makes to `_active_in_window`/`_has_any_activity` must be reflected identically in all 5 arms, not just arm 1.
- `session_activity.py` (`derive_session_activity`, lines 56-99): precomputes `has_activity`/`last_activity_day`/`resumed` straight from `_ACTIVITY_TABLES` row *existence*, with no concept of what the row's value is. These stored facts are read-through caches of the same five-table existence check the admission rule does directly when NULL; they do not independently encode "real activity" vs. "housekeeping" — they inherit whatever `_ACTIVITY_TABLES` already contains (turns_daily/tool_facts_daily/cost_daily/session_usage/lines_daily rows, which already only exist for turns, tool calls, cost/usage and lines — see Decisions below). They are not implicated in the zero-value-metric-point or lifecycle-hook misclassification (that is a `_raw_activity_in_window` / `_RAW_ACTIVITY_SOURCES` problem, a different code path), but a change to `_active_in_window`'s whole-day semantics or to `_has_any_activity`'s day-bound could change what "activity" means for these stored facts too — currently they are not consulted by that narrower raw check at all.

**Purpose: zero-value lines metric points counted as "known".**
- `lines_daily` recompute (`rollups.py:1856-1872`, comment at line 1856: "A lines_daily row means the lines are known, zero included"). The `metric_points` branch of `_RAW_ACTIVITY_SOURCES` filters only by `metric_name = ANY(LINES_METRICS)` (`reader.py:217`, `LINES_METRICS` from `vocabulary.py`), with no value filter — so a zero-value `claude_code.lines_of_code.count` point (final metric export at shutdown) passes `_raw_activity_in_window` exactly like a real line-count delta. This is a deliberate choice for `lines_daily`'s own "known vs. unknown" semantics (0 is a real answer, distinct from no row at all — see `cli-analytics-events.md` rule for `agent.tool.end`/lines and `cli-analytics-storage.md` "Known limitations"/lines sections) but it leaks into period membership via the shared `_raw_activity_in_window` helper, which the task calls out as consumer #2 of the bug.

**Purpose: a session's facts (turns, cost, tool calls, lines) shown per session, once admitted.**
- Every per-session fact query (`get_turns_by_session`, `get_tool_success_by_session`, `get_session_cost_facts`, `get_lines_by_session`, etc.) sums over the session's *entire* history once it is a member of `sel`, with no day filter — documented explicitly in the storage guide as a deliberate, out-of-scope limitation: "fact *values* are not period-clipped... once a session is admitted to `sel` for a window, every fact query sums or reads that session's entire lifetime of rows" (`cli-analytics-storage.md:75`). This matches the task's own framing ("Fact values... should remain all-time sums as before; only membership changes") exactly — no code change to any of these query bodies is implied by the fix; they stay correct as soon as the membership predicate they read from `sel` is correct.

**Other touched code**: none beyond what is named above — the admission predicate, its raw-activity helper, and the lines_daily zero-value interaction are confined to `reader.py` and `rollups.py`.

### Decisions Already in the Code

- **The five `_ACTIVITY_TABLES` already encode "real activity" for the whole-day and lifetime arms** (`reader.py:180`): `turns_daily`, `tool_facts_daily`, `cost_daily`, `session_usage`, `lines_daily` are each built only from genuine prompts/tool calls/cost/usage/line-count rows (per `cli-analytics-storage.md`'s "Counter fallback" and rollup-families sections) — never from `hook_events` lifecycle types (`session.start`, `session.env`, `session.end`, `git.snapshot`, summary). This is why the whole-day branch of `_active_in_window` is not implicated by the bug: a day wholly inside the window with only lifecycle hooks produces no row in any of the five tables and is correctly excluded today. The bug is confined to the *partial-day* branch, which additionally trusts `_raw_activity_in_window`'s five raw sources, three of which (`log_events` "not OTHER", `spans` "not OTHER", `metric_points` "named a lines metric") are broader than "a real prompt, API call, or tool call."
- **`_ACTIVITY_HOOK_TYPES`** (`reader.py:200-209`) is already the narrowest of the five raw sources: `agent.prompt.submit`, `agent.tool.start/end/error/denied`, `agent.subagent.start/usage`, and the skill-dispatch event — explicitly excluding the 13 lifecycle/dimension hook types (comment at `reader.py:197-199`: "Lifecycle hooks (session start, env, end, git snapshot, summary) are not among them"). The established convention for "real activity" at the hook level is already this allow-list; the task's fix is naturally framed as tightening the other four raw sources (`usage_requests`, `log_events`, `spans`, `metric_points`) to the same standard, not inventing a new vocabulary.
- **`EventKind`/`SpanKind` vocabulary** (`vocabulary.py`): `EventKind.OTHER = 0`, `EventKind.API_REQUEST = 1`; `SpanKind` has `TOOL`, `TOOL_EXECUTION`, `INTERACTION` kinds used elsewhere in the reader (`_TOOL`, `_EXEC`, `_INTERACTION`, `_API_REQUEST`, `_LLM_REQUEST` constants at `reader.py:111-113`) but *not* currently referenced by `_raw_activity_in_window`'s `spans`/`log_events` clauses, which instead use the much coarser `<> OTHER` test. The fix has a ready-made vocabulary (`_API_REQUEST`, `_TOOL`, `_EXEC`, `_INTERACTION`) to narrow those two clauses to "a real prompt/API-request/tool-call kind" without introducing new constants.
- **The turn rule for `user_prompt` already distinguishes real turns from Claude-Code-injected auto-prompts** (`cli-analytics-storage.md` "Turn rule" section, lines 242-278): a `user_prompt` log row is excluded from `turns_daily` when it is an auto-prompt (`<task-notification>`/`<agent-message` prefix) or an injected message with no hook. This logic lives in the rollup recompute (`rollups.py`), not in the reader's raw-activity check — the task's synthetic `/exit` `user_prompt` is a different case again (a /exit-emitted prompt, not an auto-prompt-prefix one), so no existing predicate already filters it out; the fix needs its own test of what marks a genuine prompt for membership purposes, distinct from the turn-counting rule.
- **No existing code path narrows `_has_any_activity` by day** — it is deliberately unbounded by design (the "started" arm keeps "exact sub-day window-boundary precision... as long as it has produced at least one real signal, ever", `reader.py:248-256`). The EPMCDME-16993 reopen gap the task names is a direct, documented consequence of this choice, not an oversight local to `_active_in_window`; a day-bound fix to `_active_in_window` alone will not close the reopen gap, since reopened sessions whose `started_at` lands in the window take the `_has_any_activity` arm (arm 2 in `_admitted_arms`) or the unconditional arm 1 (`has_activity` true), not the `_active_in_window` arms (3-5).
- **The `_admitted_arms`/`session_activity.py` performance layer is a derived cache, not an independent source of truth**: `has_activity`/`last_activity_day`/`resumed` are written only by the rollup refresher from the same five tables the direct check reads (`session_activity.py:33-39`); any semantic change to what counts as "activity" for membership that is expressed only in `_active_in_window`/`_has_any_activity` (the raw SQL) will automatically apply identically when those stored facts are NULL (arms 2 and 3), but **will not** retroactively change what `has_activity`/`resumed` already encode for already-derived sessions, since those facts are existence checks against `_ACTIVITY_TABLES`, independent of `_raw_activity_in_window`. This matters only if the fix needs the derived facts to reflect a narrower day-bound (e.g., for the reopen gap) — current `resumed`/`last_activity_day` have no narrower view of "real activity" than table-row existence.

### Consumers of Changed Contracts

`_SESSION_ADMITTED_IN_WINDOW` / `sel` is read by every query method of `PostgresCliAnalyticsReader` built on `_sessions_cte` — searched by grepping `_sessions_cte(` and `FROM sel` across `reader.py`: `get_class_lists`, `get_cost_kpis`, `get_model_breakdown`, `get_session_model_costs`, `get_window_model_flags`, `get_session_funding_costs`, `get_cost_by_user`, `get_users`, `get_users_daily_activity`, `get_users_last_active`, `get_lines_totals`, `get_lines_daily`, `get_lines_by_user`, `get_lines_by_session`, `get_turns_by_session`, `get_file_facts_by_session`, `get_tool_success_by_session`, `get_tool_usage`, `get_invocations`, `get_session_durations`, `get_active_ms_by_session`, `get_session_cost_facts`, `get_session_page` (and its sort helpers), `get_cost_models`, `get_cost_page`, `get_framework_page`, `get_session_start_times`, `get_repository_sessions`. All of them get a narrower `sel` automatically once the one predicate changes — no per-method edit needed, confirmed by the existing tests `test_every_fact_a_windowed_query_reads_is_scoped_to_the_selected_sessions` / `test_no_fact_query_carries_its_own_window_and_all_are_scoped_to_sel` which assert this scoping property generically over a parametrized method list.

`_admitted_arms`/`_active_in_window`/`_has_any_activity` are also exercised directly, as literal SQL-fragment assertions, by `test_sessions_cte_decides_the_window_by_session_start` and `test_sessions_cte_times_a_partial_window_day_by_its_raw_records` (`tests/codemie/repository/cli_analytics/postgres/test_reader.py:453-471`), which reconstruct the five arms' SQL text (`_ARM_STARTED`, `_ARM_UNDERIVED`, `_ARM_OUTSIDE_UNDERIVED`, `_ARM_RESUMED`, `_ARM_ONE_DAY`) and the raw-table EXISTS clause as local string literals in the test file (`test_reader.py:422-446`, `_RAW_TABLES` parametrize). Any change to the predicate's SQL shape (not just its semantics) will need these test-side literals updated in lockstep, or the tests will fail on a string mismatch rather than a semantic one — grepped, no other test or source file in the repo references `_active_in_window`, `_SESSION_ADMITTED_IN_WINDOW`, `_RAW_ACTIVITY_SOURCES`, `_raw_activity_in_window`, `_admitted_arms`, or `_has_any_activity` by name.

`session_activity.py`'s `derive_session_activity`/`ACTIVITY_TABLES` constant is a literal duplicate of `reader.py`'s `_ACTIVITY_TABLES` (comment at `session_activity.py:56`: "The five tables of reader._ACTIVITY_TABLES (the reader and this module cannot import each other)") — if the fix changes which tables or rows count as "activity" for the five-arm rule in a way that also needs reflecting in the stored `has_activity`/`resumed` facts (e.g., to close the EPMCDME-16993 reopen gap at the derived-fact layer, not just the live-SQL layer), this duplicated constant and `session_activity.py:93-119`'s batch-derive logic are both consumers that would need the same change, plus `test_session_activity.py` which "guards the binding" per its own module docstring.

### Architecture and Layers Affected

- **Repository/adapter layer**: `src/codemie/repository/cli_analytics/postgres/reader.py` (the SQL-building admission predicate) and, if the fix touches zero-value/lines semantics, `src/codemie/repository/cli_analytics/postgres/rollups.py` (the `lines_daily` recompute). No router, service, or port-interface change is implied — the port `CliAnalyticsReader` (`ports.py`) is unchanged; this is a same-contract, internal-query fix.
- **Performance/cache layer**: `src/codemie/repository/cli_analytics/postgres/session_activity.py`, only if the derived facts need to reflect the narrower rule (see Consumers above).

### Integration Points

None external — this is a pure read-path SQL fix inside the PostgreSQL adapter. The only "integration" is the shared vocabulary (`vocabulary.py`'s `EventKind`/`SpanKind`/`LINES_METRICS`/`DIMENSION_HOOK_TYPES`) the admission predicate already imports and could narrow its use of.

### Patterns and Conventions

- SQL is built as Python string-constant fragments (`_ACTIVITY_HOOK_TYPES`, `_RAW_ACTIVITY_SOURCES`, etc.), composed by small functions (`_activity_exists`, `_raw_activity_in_window`, `_active_in_window`) rather than an ORM — the convention for any new membership condition is a module-level tuple/constant plus a small builder function, following the existing `_RAW_ACTIVITY_SOURCES`/`_ACTIVITY_HOOK_TYPES` shape.
- Every predicate change of this kind is paired with a doc update in `cli-analytics-storage.md`'s "Window Semantics" section (the guide already documents the current rule in exhaustive, versioned prose, including a dated "accepted divergence" callout) — the existing convention is to keep that section as the authoritative semantic description alongside the code's own docstrings.
- Performance-sensitive changes to this predicate are measured and the numbers recorded in the guide (see "Scan cost of the admission rule" / "Final code, measured 2026-11-06" in `cli-analytics-storage.md`) — any narrowing that adds more EXISTS probes to the partial-day arm is a candidate for the same kind of measurement given the documented history of this exact code path timing out at 1.9M sessions.

## 6. Risk Indicators

- The fix point is a single, well-isolated predicate (`_SESSION_ADMITTED_IN_WINDOW`/`_active_in_window`/`_raw_activity_in_window`) read by one CTE (`sel`) that every endpoint shares — low architectural risk, but it must be edited correctly in **all 5 arms** of `_admitted_arms`, not just the whole-day/partial-day pair, or the EPMCDME-16993 reopen arm (arm 2, via `_has_any_activity`) stays broken while the partial-day arms (3-5) are fixed. See Decisions Already in the Code.
- `_has_any_activity` is unbounded by day **by design**, documented as intentional for `started_at`-precision reasons (`cli-analytics-storage.md:53-55`); narrowing it risks regressing that documented sub-day precision guarantee for genuinely-started, genuinely-active sessions — the fix needs to distinguish "narrow what counts as activity" from "add a day bound", since the task asks only for the former while EPMCDME-16993 specifically needs the latter handled too for the reopen case.
- This exact code path has a documented history of catastrophic scan-cost regressions at scale (1.9M sessions, 30 s statement timeout hit before the `EPMCDME-16427` stored-facts optimization) — any widening of per-row EXISTS probes in the fenced per-candidate arms (3-5) should be sized against the same measurement discipline the guide already applies (`cli-analytics-storage.md:73`).
- Section 2's "Task Statements Checked Against the Code" flags the fact-values-stay-all-time-sums statement as **keeping an existing, explicitly out-of-scope mechanism in place** (`cli-analytics-storage.md:75`'s "fact values are not period-clipped") — this is low risk precisely because it is a documented non-goal with no code dependent on changing it, but a spec/plan that inadvertently widens scope to "also clip facts to the window" would be touching a separately-scoped, previously-deferred limitation, not this bug.
- Zero semantic test coverage exists today for the membership predicate (only SQL-string-shape assertions) — the four new/extended tests the ticket's QA comments require (live integration x2, unit x1, cross-endpoint contract x1) are entirely new test infrastructure, not incremental extensions, raising implementation effort for the testing side of this task even though the query-logic change itself is narrow.
- The "/exit synthetic user_prompt" claim is unverified against this repository (no CLI/plugin source here); the backend-side mechanism that would admit it (`log_events`'s coarse `event_kind <> OTHER` filter) is confirmed, but exact reproduction depends on a fixture or external CLI behavior not visible from this codebase.

## 7. Summary for Complexity Assessment

The fix is confined to the repository/adapter layer of CLI analytics: one PostgreSQL-reader predicate (`_SESSION_ADMITTED_IN_WINDOW`, built from `_active_in_window`/`_has_any_activity`/`_raw_activity_in_window`/`_RAW_ACTIVITY_SOURCES` in `src/codemie/repository/cli_analytics/postgres/reader.py`), expressed in exactly one CTE (`sel`) that every dashboard endpoint (Overview, Sessions, Users, Repositories, Cost, Activity) already shares by construction — so the change surface for production code is small and structurally guarantees the cross-endpoint consistency the task requires as a non-regression. A secondary, optional touch point is the `lines_daily` zero-value-row semantics in `rollups.py` (unchanged in itself, but its "zero included" row is what currently leaks into `_raw_activity_in_window`'s `metric_points` clause). The predicate must be edited in all 5 arms of `_admitted_arms`, not just the raw-activity arms, to also close the EPMCDME-16993 reopened-session gap that goes through the separate, currently-unbounded `_has_any_activity` arm.

Technical novelty is low — the fix tightens an existing, already-documented rule using vocabulary the reader already imports (`EventKind.API_REQUEST`, `SpanKind.TOOL`/`TOOL_EXECUTION`/`INTERACTION`, `LINES_METRICS`) rather than introducing new concepts, and the existing `_ACTIVITY_HOOK_TYPES` allow-list is already the right shape for the convention to extend to the other four raw sources. The main complexity driver is testing: this exact predicate has zero semantic (row-admits-or-excludes-this-session) test coverage today, only SQL-string-shape assertions, so all four kinds of regression test the ticket's QA comments require (two live-Postgres integration tests with newly-built fixtures, one unit test for UTC-midnight-crossing hour presets, and one cross-endpoint-total contract test) are new test infrastructure. The code path also carries a documented, measured history of severe scan-cost regressions at ~10^6-session scale, which bounds how the fix can be implemented (narrowing existing EXISTS clauses, not adding new unbounded ones) without re-measurement.
