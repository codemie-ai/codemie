# Spec: Public export REST endpoint (EPMCDME-15313)

Source: story.md in this directory. Size L (24/36), single repo (`codemie` backend), not split.

## Goal

`GET /v1/export/{kind}/{id}` returns one entity as a complete, re-applicable, byte-stable document with no credential value, no platform id and no server-managed field. `kind` is one of: assistant, workflow, datasource, integration, skill, category.

## Approach

One new `export` package behind a single router (registered next to the other `/v1` routers in `main.py`, same `APIRouter(prefix="/v1", dependencies=[Depends(authenticate)])` pattern). Chosen over adding an export route to each entity router: one contract, one place to enforce determinism and secret-freedom. Each kind has an exporter that reuses the entity's existing read path and access check, so 404/403 behaviour is inherited. **Exception (review decision):** exporting an assistant or a workflow needs WRITE (owner, project admin or admin), not READ, because the document carries the whole definition in a form meant for version control; referenced entities still only need READ. Workflow was raised from READ to WRITE on review for consistency with assistant, even though `GET /workflows/id/{id}` is itself a READ-gated read path. Three shared parts:

- serialiser core: builds `{meta, spec}` and emits it canonically
- reference resolver: id to name rewriting plus the ambiguity check
- credential reference derivation

Datasources use one exporter per type behind a common protocol, mirroring the type-specific router package `rest_api/routers/index/`. Types: code (git, svn), confluence, jira, xray, azure_devops_wiki, azure_devops_work_item, git_faq, google, sharepoint, xwiki, provider. `knowledge_base_file` and any other type fail with an error naming the type.

## Document contract

- **The document is the IaC document envelope (EPMCDME-15309), as is.** Response is `version` (`v1`), `meta` (kind, name) and `spec`, and it parses in `codemie_iac.envelope.Document` (every spec there is `extra="forbid"`): field names, nesting and reference conventions are the envelope's, not the update requests'. `meta.name` is: the assistant name (the slug stays in `spec.slug`), the integration alias, the entity name otherwise. Revised after measuring against the real envelope (see `envelope-gap.local.md`): the first implementation emitted update-request-shaped specs and 18 of 19 documents failed to parse.
- Spec shapes: assistant = `AssistantSpec` (toolkit/tool/MCP `settings` = integration alias, `assistant_ids` and `categories` = names, MCP config nested in `config`); skill = `SkillSpec`; integration = `IntegrationSpec` (`credential_values` is a list of `{key, ref}`, `setting_type`); category = `CategorySpec`; workflow = `WorkflowSpec` (`workflow` = typed `WorkflowDefinition` with `assistants` keyed by id, catalog assistants named in `assistant_id`; `credential_values` lists the assistant MCP auth-token references); datasource = the `type`-discriminated specs (`code`, `svn`, `knowledge_base_*`, `llm_routing_google`, `provider`), with `project_name`, `shared_with_project` and the integration alias in `setting_id`.
- Excluded: ids, timestamps, state flags (`error`, `completed`, counters, `current_state`), `created_by`, abilities, likes, mask strings.
- Determinism: key order is field-declaration order by alias; fixed list order (sorted by a stable natural key where storage order is not guaranteed); nulls omitted; no run-specific values.
- Completeness: every field the kind's update endpoint accepts is exported or listed under "Deliberately non-exportable". This matters most for the destructive full-replace PUTs (svn, sharepoint, provider).
- Cross-entity references are names: workflow `assistant_id` to assistant name, workflow assistants' `skill_ids` and `datasource_ids` to skill and datasource names (**the engine resolves these names only after EPMCDME-16198**; until then applying such a document writes the names as ids), datasource `setting_id` to integration alias, integration aliases in assistant tool, toolkit and MCP settings. A reference whose target name is shared with any other entity of the same kind in scope (the exported entity's project; categories are global), referenced or not, fails the export, naming the clash. Every referenced target (sub-assistants, integrations) must also be readable by the requesting user through that entity's own read rules; otherwise the export is rejected with 403 naming the reference id (never its name), not silently filtered. Categories have no per-user access control and are not checked. Stored data the document cannot represent (invalid or missing fields) is a 422 naming the entity kind and id, without echoing values.
- **A workflow's literal `integration_alias` (an MCP server, a tool, or a `tool_access` entry configured by alias directly, with no settings-id snapshot) is checked for the same ambiguity as every id-resolved name (review finding, CR 0bcb7377).** `extract_integration_ids` only resolves the snapshot ids of servers that carry no `integration_alias`, so a literal alias used to reach `NameResolver` only by accident, through whatever other ids the same workflow happened to reference; a workflow with only literal aliases exported an ambiguous one with 200. `NameResolver.ensure_alias_unique` runs the same scoped peer lookup `resolve_many`'s `_ensure_unique` uses, against every literal alias collected by `extract_integration_aliases`, before the document is emitted.
- **A referenced id resolved from outside the target project is refused, naming it (review decision, CR 26bf9077).** `db_ids_lookup` resolves a reference to its name wherever the entity lives, but the engine's own `plan_apply/lookup.py` searches only the target project on apply; a cross-project reference (a global integration or a sub-assistant from another project) used to export with 200 and then fail as unresolved there. Categories have no project and are exempt. The peer set used for the sibling-clash check above is also now readability-filtered for assistant and datasource (`_assistant_scope` / `_datasource_scope`, approximating `is_shared_with` / `is_owned_by`), matching the fix already shipped for integrations (OC-3, `_integration_scope`): before this, a 422 "name not unique" could tell the caller that an assistant or datasource they cannot read exists.
- Credentials: `env:{ALIAS_OR_NAME}_{KEY}` (`CredentialRef` format `env:[A-Za-z0-9_]+`). Derivation is identical to the envelope's `CredentialRef.from_entity` (decision after review): identifier and key are normalised separately by replacing each run of non-ASCII-alphanumerics with `_` and upper-casing; leading/trailing `_` are kept; an identifier or key with no ASCII alphanumeric fails the export (422) instead of falling back to `UNNAMED`. Golden vectors updated to the envelope's outputs. Derived from keys and identifying fields only; the value is never read. This covers integration credential values, datasource inline credentials, tool, toolkit and MCP settings, `mcp_connect_auth_token` and sensitive prompt variables. Golden vectors are shared with the document envelope story.
- **No inline exception any more.** The envelope's integration `credential_values` entries are all `CredentialRef`s, so an integration's `openapi_spec` is exported as a reference like every other key (the operator supplies the document through the environment on apply). The earlier "inline literal" exception cannot be expressed in the envelope.
- Where the envelope's credential resolver looks: integration `credential_values[].ref`, MCP server `config` / `mcp_connect_url` / `arguments` / `command` of assistants and workflow assistants, provider datasource `settings`. Exported secrets sit exactly there.
- **Detection inside those resolver slots is positional, not by name or shape (review decision, CR dfcf1994).** Every literal value under MCP `command` / `arguments` / `mcp_connect_url` / `config` (its nested `command`, `url`, `args`, `headers`, `env`) becomes a reference; only a pure `{{...}}` / `${...}` template is left literal. Name/shape heuristics (`is_secret_name`, token-prefix matching) missed realistic secrets there (`DB_PASS`, `glpat-...`, `-u user:pass`, `?k=...`) while also false-positiving on harmless values (`{"key":"PROJ-123"}`, `--max-tokens`), so inside these slots — which the engine resolves on apply regardless of content — guessing is replaced with "every value is a reference." Outside these slots (free text such as `jql`, `cql`, prompt content, and any field the resolver does not walk), only strong, name-independent signals are refused (`has_literal_credential`: token-prefix shapes and URL userinfo) — the full `to_canonical_bytes` leak check already worked this way. This is an intentional cost: an operator now sets a few more environment variables than before (e.g. a plain MCP `command` like `npx`), matching how an unknown provider parameter is already treated (`provider.py` `_exported_params`).
- **Sensitive prompt variables are exported with an empty default, not an `env:` reference (Jira decision, amended, superseding the earlier review decision below).** The envelope never resolves a reference inside a prompt variable (no sensitive flag, no credential slot there), so an `env:{IDENT}_{KEY}` reference there was always literal, unresolvable text — worse than an empty default, since it reads as if it were a resolved value. This backend's own update path still has no mask for the field, so an unedited document applied today still overwrites the stored secret, now with an empty string rather than reference text (pinned by `test_assistant_round_trip_with_sensitive_prompt_variable`, xfail).
- Workflow: the stored flattened `yaml_config` is converted to the envelope's typed definition (lists to a mapping keyed by id, catalog assistants by name, only the fields the envelope's workflow models declare). Re-rendering reproduces the stored text for the modelled subset.
- Skill: the envelope's skill fields only. The document cannot state that companion files are excluded (no field), so that statement is dropped; applying it leaves companion files intact (AC11 keeps its behavioural half).

## Deliberately non-exportable

Everything below has no field in the envelope's specs (all `extra="forbid"`), or would be a platform id the envelope does not resolve, so it is absent from the document. Each is pinned by an exporter test; round-trip consequences are pinned by strict `xfail` tests where the update would otherwise change the stored entity.

Server-managed (all kinds): ids, timestamps, state flags (`error`, `completed`, counters, `current_state`), `created_by`, abilities, likes, mask strings.

- **Skill**: companion files, `toolkits` (and their integration settings), `mcp_servers` (and the MCP catalog id), the in-document `companion_files: excluded` marker.
- **Assistant**: `plan_prompt`, `agent_mode`, `image_generation_model`, `smart_tool_selection_enabled`, `custom_metadata`, `hide_tool_outputs` (EPMCDME-15555, no envelope field), `guardrail_assignments`, `bedrock`, `agentcore`, `agent_card`, per-tool/per-toolkit/per-MCP `credentials` maps (credentials live on the integration document), prompt variable `is_sensitive` (the sensitive default itself is exported as an env: reference, see the Credentials bullet above), MCP `mcp_config_id` (a platform id; the envelope keeps it verbatim, so exporting it would break the no-id rule), MCP config `allow_issuer_prefix_match`, MCP server `allow_user_context` (per-server override of whether MCP requests receive user context, EPMCDME-14984; review finding, auto_epmd-edp_vcs — real field, no envelope field, so classified here rather than adding one to the envelope, which is outside this story's scope, same as the others on this list). Exported since the envelope gained the fields (EPMCDME-16198 and the IaC branch): `skill_ids` (as skill names), `hedging_config`, `interactive_enabled`, `enable_image_generation`, `file_attachment_enabled`, toolkit/tool `auto_credentials_lookup`, MCP config `audience` and `auth_config` (an `auth_config` that holds a credential fails the export).
- **Workflow**: `supervisor_prompt`, `meta_config`, `project` (apply supplies it), `keep_history` / `override_task` on `next`, MCP server `mcp_config_id`, `settings` snapshots and `mcp_connect_auth_token` (only the integration alias survives, in `integration_alias`), MCP server `allow_user_context` (not in `ENVELOPE_FIELDS["mcp_server"]`, same reason and finding as the assistant bullet above), `categories`. A workflow whose export would be invalid in the envelope fails with an error naming the cause instead: a state that runs a sub-workflow (`workflow_id`), an enabled MCP server that is only a catalog link, an assistant without prompt, name or catalog assistant. The same applies to a credential found in tool `tool_args`, state `tool_args`, custom-node `config`, or a **tool-level `mcp_server`** (review decision, CR 2aca0289: unlike an assistant's `mcp_servers`, which `_iter_servers` walks, the engine never resolves a reference on a tool-level MCP server): the envelope has no credential slot there and apply never resolves `env:` references in them, so the export is refused (422, naming the tool, state or node) instead of emitting a reference that apply would write over the value. **A tool-level MCP server's `config.env` / `config.headers` are checked for a credential by position, not by name or shape (review finding, auto_epmd-edp_vcs).** The refusal check for the rest of a tool-level server (`_refuse_if_secret`) is a name/shape scan, same as `tool_args`/custom-node `config`; it missed an unrecognized variable or header name whose value also carried no known shape (`env: {DB_PASS: hunter2}`), the exact failure mode the assistant-level MCP config's positional treatment (CR dfcf1994) exists to avoid. Scoped to just these two maps, not `command` / `url` / `auth_token`: the latter three are legitimately literal on almost every tool-level server (`command: npx`) and refusing by position there would block the overwhelming majority of credential-free servers instead of the rare credential-bearing one; `auth_token` is already caught unconditionally (its name always matches). **`config.args` gets its own, narrower check: `redact_arg_list` (review finding, auto_epmd-edp_vcs).** A flag and its value are separate list elements (`["--password", "hunter2"]`); `_refuse_if_secret`'s scan judges each element alone with no memory of the flag before it, so it never connected the two (a single `command` string with the same words space-separated has no such gap: `_SECRET_ARG` already matches a name and its value within one string). `redact_arg_list` is not positional like `env`/`headers`: it keeps ordinary flags and values (`--max-tokens 4096`) while still catching a secret-named flag's value, the same balance already pinned for the assistant-level case. Exported since the envelope gained the fields: `start_hint`, the yaml engine switches the envelope models (`enable_summarization_node`, `max_iteration_key_output_limit`, `messages_limit_before_summarization`, `tokens_limit_before_summarization`), tool `tool_access`, MCP `audience` / `auth_config`.
- **Datasource**: provider `cron_expression` / `timezone` (the SDK provider request has no such fields; every other type still exports them), `guardrail_assignments`, SharePoint `access_token` (transient), `new_project_name`, Azure DevOps `organization`/`project` (not stored on the index). `project_name` IS exported (the envelope requires it; apply rejects a document whose project is not the target). `knowledge_base_file` and any unknown type still fail naming the type. A datasource missing a field the envelope requires (xray `jql`, svn `link`, SharePoint `site_url`) fails the export naming it. A git/svn `link` that holds a credential is refused rather than redacted (review decision, CR 2aca0289): the envelope's credential resolver does not walk a datasource `link`, so a reference there is never substituted on apply.
- **Integration**: nothing is omitted, but `project_name` is required (an integration without one fails the export), and `openapi_spec` is a reference.
- **Assistant** also fails the export when it has no `llm_model_type` (required by the envelope).
- Known limited round trips (strict `xfail`): inline MCP secrets (assistant and workflow; the backend update has no mask path for `env:` references, but the real engine preserves the secret when the operator's environment variable holds the same value, and an unset variable fails preflight with no write) and toolkit settings-snapshot credentials (update has no mask path) and the MCP catalog link. Workflow `supervisor_prompt` and `meta_config` are kept by the real engine's update body and are pinned by passing tests.

## Open questions for the envelope owners (EPMCDME-15309)

- Skill `categories` are `SkillCategory` enum values on the platform, but apply resolves them as category documents.
- Workflow state `workflow_id` and MCP `mcp_config_id` are passed through verbatim by apply (ids), and the envelope has no fields for assistant `skills`. (Tool-level MCP servers not being walked by the credential collector is no longer open: this exporter now refuses one that holds a credential — see "Deliberately non-exportable" above — rather than leave a reference apply would never resolve.)
- MCP server `allow_user_context` (review finding, auto_epmd-edp_vcs): a real, accepted per-server override with no envelope field; classified as deliberately non-exportable for now (see above), same disposition as `allow_issuer_prefix_match`.

## Acceptance criteria

1. Any in-scope entity exports as a document sufficient to re-create it through apply.
2. No credential value on any credential-bearing surface; a resolvable `env:` reference appears in its place.
3. Applying the exported document to a clean project yields an equivalent entity, aside from platform-assigned ids.
4. An unknown or inaccessible id fails with an error naming the problem; never a partial or empty document.
5. Two consecutive exports of an unchanged entity are byte-identical.
6. No platform id, server-managed field or mask string appears in any document.
7. Every cross-entity reference is a name, not an id.
8. Every field the update endpoint accepts is exported or listed as non-exportable.
9. Converting the document to the kind's update request (credentials as the mask) and submitting it leaves the stored entity unchanged, aside from timestamps and the datasource `error` flag.
10. Workflow document has a structured definition with assistant names; re-render equals stored text for the modelled subset.
11. Skill export then update leaves companion files unchanged (the envelope has no field to state the exclusion in the document).
12. (negative) `knowledge_base_file` or any unsupported datasource type fails naming the type.
13. (negative) An ambiguous referenced name fails naming the clashing name.

## Testing

Golden fixture per kind; per-type datasource round trip (11 types); credential-leak parametrised across all surfaces; `env:` golden vectors; determinism; references and ambiguity; workflow re-render; skill companion files; not-found and forbidden. Tests live under `tests/codemie/rest_api/routers/` using the FastAPI `TestClient`. Every exporter output is also validated against `tests/codemie/service/iac_export/envelope/envelope_schema.json`, a JSON Schema generated from the envelope's pydantic specs and committed (regenerated by a script that is never imported by the tests), so parseability is guarded without importing the other repo. Cyclomatic complexity per function stays at or below 15 (Sonar gate), so per-type and per-kind logic is split into small exporters, not one branching function.

Redaction regexes are timing-tested, not just correctness-tested (`test_secret_detection_is_not_quadratic`, CR 1f3a8151): every regex that scans unbounded free-form text (MCP args, system prompts, skill content) must stay linear on an adversarial ~50 KB input (`"apikey" * 8000` was ~20s before the possessive-quantifier fix). `redaction.py` caps the length `url_has_credentials` / `text_has_credentials` will scan (`_MAX_SCAN_LENGTH`, fail-closed above it) as a backstop for those two and any pattern added to them later — both only ever run on bounded fields (a link, a command/arg string, a URL). **`has_literal_credential` has no such cap (review finding, auto_epmd-edp_vcs: the first version applied the same cap to this function too, so an entity with a credential-free system prompt or skill body over 50 KB exported a 422 claiming it looked like a credential — contradicting "large content is inline in the one response").** It backs the whole-document leak check in `to_canonical_bytes`, which deliberately runs over prose fields with no realistic size bound; its two patterns (`_TOKEN_LITERAL`, `_URL_USERINFO`) are both linear already, so the cap was never needed there.

## Non-goals

- SDK `export` method and CLI `export` command.
- `plan`, `apply`, and name resolution on apply.
- Guardrails (follow-up story: needs an envelope kind).
- Skill companion files in the document.
- `knowledge_base_file` datasources.
- Unifying this serialiser with the diff/apply engine's internal one.
- Changing the existing `/skills/{id}/export` and `/index/{id}/export` endpoints.
- Bulk or project-wide export.
- Any change to the credential masking on the read path.

## Open risks

- Datasource type set confirmed against the envelope (`code`, `svn`, 8 `knowledge_base_*`/`llm_routing_google`, `provider`; `knowledge_base_file` rejected).
- Two serialisers (this one and the diff/apply engine's) may diverge and need a later unification pass; unverified against the shipped engine.
- About seven datasource exporters (xray, azure_devops_wiki, azure_devops_work_item, git_faq, sharepoint, xwiki, provider) have no converter precedent.
- Skill update may not preserve companion files today; if the test fails, raise before shipping.
- The `env:` derivation is re-implemented across repos and relies on shared golden vectors.
- **Known divergences from `codemie-sdk`'s own `Spec.from_entity` mapping (review decision: not this exporter's problem to fix).** `codemie-sdk` ships a second entity-to-envelope mapping (26 `from_entity` methods, its own `_looks_secret`). This exporter reads an entity and maps it to the envelope's shape as completely and correctly as the entity's own data allows; it does not know about, and is not responsible for reconciling with, any other tool's mapping, SDK, IaC or the plan/apply engine — what consumes the document, or how, is outside this endpoint's business. Recorded here only so a reader comparing the two outputs is not surprised, not as backend work to pick up: `skill_ids` (exported once the envelope carries the field, EPMCDME-16198 — see "Open questions" above), `auth_config` (this exporter refuses it when it holds a credential; `from_entity` turns it into a reference), the `env:` identifier (this exporter derives it from the entity's slug-or-name; `from_entity` uses the name). `regenerate_envelope_schema.py`'s `_generated_from` field records the envelope commit a schema snapshot came from, so a future comparison has a fixed point to diff against.

> Correction (envelope e2e check): `meta.name` for an assistant is the assistant **name**, not the slug. The real engine links
> documents of a bundle by `meta.name` and every exported reference to an assistant (workflow `assistant_id`, `assistant_ids`)
> is the name, so a slug made those references unresolvable inside a bundle. Slug stays in `spec.slug`.
