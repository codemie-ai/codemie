## 1. Original Context

Story: Enterprise Feature Gating by Package Presence (EPMCDME-14536)

As a platform engineer setting up a non-enterprise CodeMie deployment, I want Cost Centers, Budget
Management, and Chargeback to stay unavailable regardless of their customer-config flags, unless the
codemie-enterprise package is installed, so that a customer config can't accidentally expose
enterprise-only functionality.

Context:
- Cost Centers, Budget Management, and Chargeback are controlled solely by boolean flags in
  customer-config.yaml (costCenters, budgetManagement, projectChargeback), with no check for whether
  the codemie-enterprise package is installed.
- The enterpriseEdition flag already follows the target pattern: computed at runtime from package
  presence (importlib.metadata.version("codemie-enterprise")), and YAML cannot override it. This is
  the precedent to mirror.
- Server-side enforcement is inconsistent. Cost Centers and Chargeback have service-level flag checks,
  but no backend reference to budgetManagement was found outside the YAML file.
- UI enforcement is also inconsistent. The Budget Management nav tab combines its flag with the
  enterprise-edition check, but the Cost Centers nav tab does not.
- The unrelated codemie-chargeback service (a standalone BigQuery aggregator) is out of scope. This
  story covers only the features:projectChargeback flag in codemie and codemie-ui.

Acceptance Criteria:
1. Without codemie-enterprise, when features:costCenters is true, Cost Centers stays unavailable in
   both API and UI, as if the flag were disabled.
2. Without codemie-enterprise, when features:budgetManagement is true, Budget Management stays
   unavailable in both API and UI, including where it isn't currently enforced server-side.
3. Without codemie-enterprise, when features:projectChargeback is true, Chargeback stays unavailable
   in both API and UI, as if the flag were disabled.
4. With codemie-enterprise installed and all three flags true, all three features behave as they do
   today (no regression).
5. Without codemie-enterprise, direct API calls to Cost Centers, Budget Management, or Chargeback
   endpoints are rejected the same way as when the flag is explicitly disabled.
6. Without codemie-enterprise, if one of the three flags is omitted from the YAML, the feature
   defaults to unavailable rather than enabled.
7. With codemie-enterprise installed but a flag set to false, the feature stays disabled. Package
   presence raises the ceiling but does not override an explicit false.

Out of Scope:
- Changes to the standalone codemie-chargeback BigQuery aggregator.
- Changing default enablement when the enterprise package is installed.
- New UI for explaining why a feature is hidden.
- The known gap where Chargeback's cost_center attribution depends on Cost Centers at the functional
  level but not at the flag level (tracked separately).

Open Questions carried into research:
- Should the UI indicate a feature is hidden because the enterprise package is missing, vs. looking
  identical to "disabled by flag"?
- Is Budget Management truly unenforced server-side, or guarded somewhere this story's prep missed?

### Decisions Already in the Code

- **Convention for "never YAML-overridable" flags**: add the id to `CONFIG_IDS` (`customer_config.py:30-54`) and append a `Component` built from a function call inside `_get_runtime_config()` (`customer_config.py:154-360`). Every existing runtime flag (`enterpriseEdition`, `userManagement`, OAuth providers, etc.) follows exactly this shape; there is no second mechanism for "YAML can lower but not raise" in the current codebase — `enterpriseEdition` is wholly computed, not YAML-plus-ceiling.
- **Convention for "two switches ANDed, with one as a hard ceiling"**: `is_approval_gate_armed()` (`marketplace_management.py:325-338`) is the one existing example of a function (not a `CONFIG_IDS` entry) that combines an env/package-level switch with a YAML/DB-backed one via `and`, deliberately ordered cheapest-first. This is a plain Python function callable from backend code directly; it also happens to be the literal value the UI's corresponding flag exposes, but via the function's result being surfaced as a component, not by the UI combining two flags itself.
- **Established convention: UI never ANDs enterprise-edition with another flag itself for route/API gating** — every UI flag read found (`isCostCentersEnabled`, `isBudgetManagementEnabled`, `isProjectChargebackEnabled`) is a single `config.id === x` lookup against `appInfoStore.configs` (`isConfigItemEnabled`/`isFeatureEnabled` in `src/utils/settings.ts` and `src/utils/featureFlags.ts:44-51`). The one UI-side combination with `isEnterpriseEdition()` that exists (Budget Management's Admin nav entry, `tabs.tsx:119-121`) is local to that one call site, not a shared utility — there is no `isEnterpriseGatedFeatureEnabled()` helper to extend for the other two flags.
- **`is_feature_enabled` defaults a missing component to disabled, already**: `is_component_enabled()` (`customer_config.py:455-461`) returns `False` when `resolve_component` returns `None` ("If the component is not in the configuration, it defaults to False"). This already satisfies AC6's "omitted from YAML ⇒ unavailable" *for the YAML-omission case*; it does not by itself address "flag present and true but package absent" (AC1-3), which is the actual gap.
- **No cached invalidation hazard found for `has_enterprise()`**: `@lru_cache(maxsize=1)` on `has_enterprise()` (`loader.py:232`) is safe for what it checks — installed-package presence does not change within a process lifetime — and `_get_runtime_config()` re-reads it on every call (not itself cached beyond that), matching the existing pattern other runtime flags already rely on.

### Architecture and Layers Affected

- **Backend, `codemie` repo**: configuration/flag-resolution layer (`src/codemie/configs/customer_config.py`, `src/codemie/configs/component_resolution.py`, `src/codemie/enterprise/loader.py`) — the layer that would gain the enterprise-package ceiling logic. Service layer (`src/codemie/service/cost_center_service.py`, `src/codemie/service/project/project_service.py`, budget service modules) — consumers of `is_feature_enabled`, not expected to change if the ceiling is applied centrally in the configs layer. API layer (`src/codemie/rest_api/routers/cost_centers.py`, `project_budget_router.py`, project router) — enforcement point for AC5 (reject direct API calls), contingent on whether the per-id checks already cover every route (Cost Centers' coverage is unverified beyond `create`).
- **Frontend, `codemie-ui` repo**: a single config-read layer (`src/utils/featureFlags.ts`, `src/hooks/useFeatureFlags.ts`, `src/utils/settings.ts`, `src/store/appInfo.ts`) that all nav (`tabs.tsx`), route guards (`router.tsx` + `FeatureGuard.tsx`), and in-page conditionals (`ChargebackSettings.tsx`, `ProjectDetailsPage.tsx`, etc.) sit on top of. Because every UI read is a lookup against the `/v1/config` payload, the UI layer has no independent "is enterprise installed" concept of its own beyond `isEnterpriseEdition()` reading `features:enterpriseEdition` the same way.

### Integration Points

- Backend configuration layer → `importlib.metadata.version("codemie-enterprise")` (external package presence check, no network/IO beyond local package metadata).
- Backend service layer → backend configuration layer via `customer_config.is_feature_enabled(...)` (module-level singleton `customer_config`, not shown in this pass's source but referenced throughout as `from codemie.configs.customer_config import customer_config` or similar import alias based on call sites).
- `codemie-ui` → `codemie` backend via `GET /v1/config` (the only integration point the UI has with the flag system) and via each gated feature's own REST endpoints (`/v1/admin/cost-centers/*`, project update endpoint for chargeback, budget endpoints) which independently need their own 403/404 enforcement per AC5 — the UI being correct does not substitute for API-level enforcement.

### Patterns and Conventions

- **Runtime-computed flag pattern** (to mirror per the task's own framing): add entry to `CONFIG_IDS`, compute a boolean in `_get_runtime_config()`, append a `Component(id=..., settings=ComponentSetting(enabled=...))`. This is the dominant, repeated pattern (18 runtime components already follow it).
- **Shared-function-as-ceiling pattern**: `is_approval_gate_armed()` style — a plain function ANDing two switches, with the YAML/DB-backed one as the "fine-grained" switch and the other (env var there, package presence here) as the hard ceiling, cheap check ordered first.
- **Service-level `ensure_feature_enabled()` classmethod pattern**: `CostCenterService.ensure_feature_enabled()` — a small guard classmethod raising `ExtendedHTTPException(403, ...)`, called at the top of mutating operations. Not yet applied uniformly (budgetManagement has none at all; Chargeback's is inline rather than a named guard).
- **UI `FeatureGuard` component pattern**: wraps a route element, throws a React-Router-recognized 404-shaped error when the flag is false (`src/components/FeatureGuard.tsx`). Only Cost Centers' routes use this; Chargeback has no dedicated route to guard (it's a form section), and Budget Management's route-level guarding was not located in this pass (only the nav-tab gating was).

## 5. Configuration and Environment

### Environment Variables
No dedicated env var exists for these three flags; they are pure YAML booleans. `has_enterprise()` reads installed-package metadata, not an env var — there is no `codemie-enterprise`-specific env toggle in the codebase (distinguishing it from, e.g., `MARKETPLACE_MANAGEMENT_ENABLED`, which is an env-backed kill switch).

### Configuration Files
`config/customer/customer-config.yaml` — lines 177-180 (`features:costCenters`, `enabled: true`), 237-241 (`features:budgetManagement`, `enabled: true`, with name/description), 300-304 (`features:projectChargeback`, `enabled: false`, with name/description). These three entries are the full extent of today's control surface for the three features.

### Feature Flags and Deployment Concerns
The `codemie-enterprise` package's presence is a packaging/deployment-time decision (installed or not in the image), not a runtime toggle — `has_enterprise()` is cached per-process (`lru_cache`), so a package change requires a process restart to take effect, matching every other runtime-computed flag's behavior already.

## 6. Risk Indicators

- Two competing precedents exist for "flag gated by more than YAML" (`CONFIG_IDS` runtime-component vs. a standalone AND-function like `is_approval_gate_armed`); picking between them is a design decision with no documented preference, and inconsistent choice per flag would leave a third divergent pattern in the codebase.
- Budget Management has **zero** backend enforcement today (AC2's hardest requirement: gate "including where it isn't currently enforced server-side") — this is new backend plumbing, not a tweak to an existing guard, and touches whichever budget routers/services the spec decides need the check.
- Cost Centers' service-level guard (`ensure_feature_enabled`) was confirmed wired into `create()` only in this pass; whether `list_paginated`, `get_or_404`/detail, `update`, `delete`, and the budget-rollup read path also enforce it needs verification before scoping AC5 (direct API rejection) for Cost Centers — risk of assuming full coverage that doesn't exist.
- Chargeback's only backend check is inline inside `ProjectService.update_project()` and only fires on write of `chargeback_enabled`/`chargeback_attribution` — reading chargeback fields on an already-configured project is not gated, which may or may not matter depending on what AC3's "unavailable in... API" is read to require.
- UI nav-tab enterprise-combination is role-scoped today (Admin yes, Auditor no, for Budget Management) and absent entirely for Cost Centers and Chargeback — the task statement "Budget Management nav tab combines its flag with the enterprise-edition check" is a partial truth worth flagging precisely because downstream stages may otherwise assume uniform behavior across roles (see Task Statements Checked Against the Code).
- `docs/budgeting-cost-centers-backend.md` / `-frontend.md` exist but were not read this pass; they may contain additional relevant context on Cost Centers/Budget behavior that the spec stage should check before finalizing scope.

## 7. Summary for Complexity Assessment

The change touches the backend configuration/flag-resolution layer (`codemie/src/codemie/configs/customer_config.py`, `component_resolution.py`, `enterprise/loader.py`) as its locus, with two viable existing shapes to extend from: the `CONFIG_IDS`-plus-`_get_runtime_config()` pattern that `features:enterpriseEdition` itself already uses, or a standalone AND-function in the style of `is_approval_gate_armed()`. Downstream, it touches the backend service/API layer unevenly per feature — Cost Centers and Chargeback already have *some* flag enforcement to extend (service classmethod for Cost Centers, inline check for Chargeback), while Budget Management needs enforcement added from nothing, which is new plumbing rather than a tweak. On the frontend (`codemie-ui`), every flag read already funnels through one config-store layer fed by a single `/v1/config` endpoint, so a backend-only fix to flag resolution (making the three ids runtime-computed with a ceiling) would propagate to the UI's nav, route guards, and in-page conditionals without UI code changes — contingent on that being the chosen design.

Technical novelty is low: the enterprise-presence check (`has_enterprise()`) and the "ceiling" composition idea both already exist in the codebase in two different shapes; this task is substantially about choosing and applying one consistently to three flags that currently lack it, not inventing new machinery. Test coverage posture is mixed: the flag-resolution layer has strong existing test scaffolding directly reusable for the new cases (`test_customer_config.py`'s enterprise-installed/not-installed tests, `test_loader.py`'s `has_enterprise` tests, and the UI's per-flag mock-based tab tests), but there is zero existing coverage of "flag true + enterprise missing" for any of the three target flags, and Budget Management has no backend tests to extend at all because it has no backend check at all.

Key risk factors are the uncertain completeness of Cost Centers' existing API-layer coverage (confirmed only for creation in this pass), the undocumented choice between the two competing "more than YAML" patterns, and the role-scoped (not uniform) nature of the UI's one existing enterprise-combination example, which could mislead a spec into assuming more consistency already exists than this research found.
