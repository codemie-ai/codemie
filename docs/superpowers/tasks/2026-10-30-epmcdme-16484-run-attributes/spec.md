# Spec: Run attributes for analytics (EPMCDME-16484, backend)

This spec is the single source of truth for the scope, behavior, API contract, limitations and acceptance of the backend change. Size: L (complexity 23), single repo, no split.

## Goal

A caller attaches up to 4 immutable string key/value attributes to one agent conversation or one workflow execution at start. Authorized analytics users filter and group chat and workflow usage by them.

## Behavior

**Input and validation.** Optional `attributes: dict[str, str]` on `AssistantChatRequest` (`src/codemie/core/models.py:653`) and `CreateWorkflowExecutionRequest` (`src/codemie/core/workflow_models/workflow_execution.py:326`). One shared module holds validation (max keys from a new `config.py` setting, default 4; key regex `^[a-z0-9][a-z0-9._-]{0,62}[a-z0-9]$`, 2-64 chars; `codemie.` and `otel.` prefixes reserved; value 1-128 chars, no control characters or unpaired surrogates) and the builder of record fields. Request-shape validation runs in the request model (Pydantic validator, like `FileNamesCountValidatorMixin`), so a failure returns 422 before any handler code, history write, usage record or summary exists. Absent attributes change nothing.

**Access.** Any caller who may run the assistant or workflow may set attributes on that run; no extra permission exists. They are fixed at start and cannot be edited. Reads follow the existing rules: the conversation and execution read endpoints return them to whoever may read the run, and analytics shows them within the existing analytics access filter. Values are written to logs and usage records, so they must not carry secrets.

**Value limit (128, not 256).** `run_attribute_pairs` stores `key=value`. The metrics index uses default dynamic mapping, where a string's `.keyword` subfield is not indexed once the string is longer than 256 chars (`ignore_above`). A pair over 256 chars would be silently missing from `.keyword`, so the attributes filter and `attributes-usage` would skip that run with no error. Invariant: key max (64) + `=` (1) + value max (128) = 193, which must stay under 256. The shared module must keep this true (for example by deriving or asserting the bound from the two limit constants), and any future change to either limit must preserve it.

**Persistence.** Nullable JSONB `attributes` on `Conversation` and `WorkflowExecution` (precedent: `file_names`), no index, additive Alembic migration chained to the single current head (resolve at write time; several merge files exist). `attributes` is added explicitly to `ConversationResponse` and `WorkflowExecutionResponse` and is returned by `GET /v1/conversations/{id}` (also when history is paged with `page`, `per_page` or `sort_order`, whose column list in `get_conversation_history_slice` includes `attributes`) and `GET /v1/workflows/{id}/executions/{execution_id}`.

**Chat.** Both the id and slug routes, which share `_ask_assistant` in `routers/assistant/_ask.py`. The "attributes changed -> 422" check is a pre-flight check, `validate_run_attributes_and_raise` in `rest_api/routers/utils.py`, shared by the chat and IDE routes. `_ask_assistant` calls it right after the existing `_validate_*_and_raise` helpers (`_ask.py:297-301`): after `check_user_can_access_assistant`, before the guardrail step and before the `try` that starts at `_ask.py:325`. Revised 2026-11-02 (architecture review): a request without attributes skips the check and loads nothing, so chat messages without attributes add no conversation read. A request with attributes loads the conversation row via `request.conversation_id`. With no row, the request keeps its attributes (a new conversation). When the caller may not READ the row (`Ability(user).can(Action.READ, conversation)`), the check drops the request's attributes and returns before it looks at history or stored attributes. A caller who cannot read a conversation therefore learns nothing about it from a 422 (whether it exists, has history or carries attributes), and cannot leave their attributes on it or on its usage records, even through the error turn a refused request writes. The existing conversation access handling then decides the request as it does without attributes. Otherwise a row without history keeps the request's attributes, and a row with history accepts identical attributes and raises `ExtendedHTTPException(code=422)` when they differ. The check never copies stored attributes onto the request: later turns keep the stored attributes because `conversation_service` writes attributes only to a new or history-less row, and the usage metric reads them from the row. The check must not live inside the `try`, the request handler or `conversation_service`: an `ExtendedHTTPException` raised inside the `try` is caught at `_ask.py:365-366` and passed to `_save_error`, which writes an error turn into the user's chat history, and `record_usage` and `create_request_summary` have already run at `_ask.py:326-332`. The request's attributes are carried down to `conversation_service` only to be stored on a new or history-less row; the service does no conflict check. The usage metric reads attributes from the conversation row when the caller may read it, and otherwise uses the request's attributes, which the check has already dropped. Tool-call resume and `in_progress` upserts are therefore labelled. The virtual-assistant path (`_ask_virtual_assistant`) writes no usage record and is not extended. Revised 2026-11-02: the IDE virtual route `POST /v1/ide/inference/virtual` (`routers/ide.py`) is a different path. It saves history and writes usage records through the standard handler, so it runs the same pre-flight check as its first step, before the `try` that turns every exception into 500 and before `record_usage` and `create_request_summary`. The route is async and the conversation read blocks, so it runs the check in a worker thread (`asyncio.to_thread`). A conversation the caller cannot read is then denied by the handler exactly as without attributes. `POST /v1/ide/inference/{assistant_id}` already reaches the check through `_ask_assistant`. `save_history=false` chats store no conversation and write no usage record, so their attributes are validated and then ignored; the request field description says so.

**Workflow.** `WorkflowService.create_workflow_execution` stores attributes (new optional parameter; existing callers unchanged). `sub_workflow_node._create_child` passes the parent's attributes; resume reuses the stored row. `WorkflowExecutionService` passes attributes to every `send_workflow_execution_metric` call and keeps a cached copy for use after the row is deleted mid-run.

**Metrics.** `send_count_metric` gains an optional log-only extra-fields parameter, written in the log record and never added to the dict handed to the OTel counter. `send_conversation_metric` and `send_workflow_execution_metric` add `run_attribute_keys` (sorted keys) and `run_attribute_pairs` (sorted `key=value`) through it only when attributes exist. Records of runs without attributes are byte-identical to today's. No ES mapping change. Revised 2026-11-02 (architecture review): the record field names, the `key=value` separator and the Elasticsearch field paths are defined only in `core/run_attributes.py` (`KEYS_RECORD_FIELD`, `PAIRS_RECORD_FIELD`, `KEYS_FIELD`, `PAIRS_FIELD`, `encode_pair`, `pair_prefix`, `attributes_from_pairs`, `attributes_from_record`). The record writer, the filter, the group-by handler and the per-request and per-execution rows all use them, so a change to the encoding is made in that one module.

**Analytics filter.** New `attributes` query parameter (JSON object string; every pair must match) on `/assistants-chats`, `/assistants-requests`, `/workflows`, `/workflows-executions` and `/attributes-usage`. It becomes a field on `AnalyticsQueryFilters` and one `SecureQueryBuilder` method emitting `term` filters on `attributes.run_attribute_pairs.keyword`, modelled on `add_client_source_filter`. `/summaries` does not take it (revised 2026-11-02, see Non-goals). Not a JSON object, non-string values, invalid keys, values over 128 chars, or input nested too deeply to parse: 422 (same key and value rules as run input). The filter applies to the time-ranged query of each listed endpoint; the all-time query used for engagement metrics (`_build_query_without_time_filter`) does not take it. The validated filter is echoed as `attributes` in `metadata.filters_applied` of every response built by the pipeline (`_build_filters_applied`), next to `client_source` and `assistant_id`.

**Analytics error mapping.** `handle_analytics_errors` (`routers/analytics/_common.py:55`) re-raises `ExtendedHTTPException` unchanged but converts any `ValueError` into HTTP 400, and anything else into 500. `ExtendedHTTPException` is a plain `Exception`, not a `ValueError`. Therefore every analytics-side validation failure (bad `attributes` filter, bad `attribute_key`) must explicitly raise `ExtendedHTTPException(code=422, ...)`. A bare `ValueError` or a Pydantic `ValidationError` (a `ValueError` subclass) escaping into the decorator would return 400 and violate AC 6 and AC 7. The shared validation module therefore raises its own neutral error; the request-model validators map it to `ValueError` (FastAPI 422) and the analytics layer maps it to `ExtendedHTTPException(422)`.

**Group-by endpoint.** New handler under `service/analytics/handlers/`, wired through `AnalyticsService` and `routers/analytics/usage.py`, returning `TabularResponse` within the existing access filter and error decorator:
- `GET /v1/analytics/attributes-usage?attribute_key=`: columns `value, conversations, workflow_executions, total_tokens, total_cost, unique_users, last_used`. `terms` aggregation on the pairs field restricted to the validated key's prefix with regex-special characters escaped, plus a `term` filter on the keys field. The route validates the key against the key regex once, before use (injection surface); invalid or missing key: `ExtendedHTTPException(422)`. The handler uses the validated key and does not check it again.

**Per-request analytics (EPMCDME-16481, merged into this branch).** `GET /v1/analytics/assistants-requests` (MR !4690) lists one row per `conversation_assistant_usage` document, the same records that carry `run_attribute_pairs`. Each row gets an `attributes` column (`type: json`): the pairs turned back into a `{key: value}` object by `run_attributes.attributes_from_pairs` (split on the first `=`; keys cannot contain one), or `null` when the record has no pairs. The endpoint also takes the `attributes` filter, which lists every request of the chats that carry the given attributes. The endpoint description states both.

**Per-execution workflow analytics (revised 2026-11-02).** `GET /v1/analytics/workflows-executions` is the workflow counterpart of `assistants-requests`: one row per workflow execution, so one labelled workflow run and its cost can be found in analytics, as a chat request can in `assistants-requests`. The workflow execution read endpoints are not enough: they list one workflow at a time from PostgreSQL, take no date or `attributes` filter, use the workflow access rules instead of the analytics access filter, and lose executions removed by `delete_on_completion`. One execution writes several `workflow_execution_total` documents (one per LLM call, or one aggregated document, and more after a resume), so the endpoint cannot list raw documents like `assistants-requests`. It is a `WorkflowHandler` method on `execute_exact_tabular_query`: two sequential searches share one short-lived Elasticsearch point-in-time (PIT). The first selects execution IDs using a `terms` aggregation on `attributes.execution_id.keyword` ordered by `max(@timestamp)` descending; it calculates the global token sums and approximate distinct execution count. Only the requested page of IDs is then reaggregated by the second search, which reapplies the identical access/date/attribute query plus a `terms` filter for those IDs. The second aggregation orders by `_key`, with size equal to the number of selected IDs, so every selected execution contributes all matching documents from every shard and rotated index. Rows are restored to the first search's newest-first order. An empty page skips the second search. The first search contains no per-execution sums or top hits. Per execution, tokens are summed, `usage_records` counts the documents, `execution_time` is the largest reported, and `workflow_name`, `status`, user, `project` and the attribute pairs come from the newest document (`top_hits`, size 1, reading `_source`, so the column does not depend on the `.keyword` mapping). Columns: `execution_id, last_activity, workflow_name, status, user_id, user_name, user_email, project, usage_records, input_tokens, output_tokens, total_tokens, money_spent, execution_time, attributes` (`type: json`, `attributes_from_pairs`, `null` without pairs). Token totals come from global sums in the first search over the full filtered range, independent of page size. Both searches use the same PIT and resolved date boundaries; the latest PIT ID is reused and closed on success or failure. Unconfigured/unavailable Elasticsearch, expired snapshots, timed-out searches, failed shards, or missing detail buckets return 503 rather than partial or empty success. The generic analytics fail-open behavior for other endpoints is unchanged. It takes the shared filters, `client_source` and `attributes`, under `@handle_analytics_errors`; paging follows the fetch-and-slice rules of the other grouped endpoints (approximate `total_count` above 3,000 executions, at most 10,000 executions per filtered range). It needs no migration, index or mapping change: every Elasticsearch field it reads is already read by `/workflows` or the `attributes` filter.

**Docs.** No Markdown page is added to this repository. The run attributes contract is documented in OpenAPI: the `attributes` request fields (`RUN_ATTRIBUTES_REQUEST_DESC` for chat and `WORKFLOW_RUN_ATTRIBUTES_REQUEST_DESC` for workflow executions, which states that attributes are fixed per execution and are not inherited or checked across executions of one `conversation_id`: types, limits, immutability, inheritance, visibility, no-secrets warning, difference from `metadata`, `prompt_variables`/`user_input` and workflow `tags`), the `attributes` response fields, the `attributes` filter parameter, and the `attributes-usage` and `workflows-executions` endpoint descriptions (columns, access scoping, what is not covered). Revised 2026-11-02 (architecture review): the chat request description also says that attributes are ignored when `save_history` is false. The conversation response descriptions (`CONVERSATION_RUN_ATTRIBUTES_RESPONSE_DESC`) say that workflow conversations always return null, because workflow attributes are stored on each execution. The request, filter and `attributes-usage` descriptions say that values are declared by callers and not verified. The `attributes-usage` description says that keys are not listed and an unknown key returns an empty table.


**Cost (revised 2026-11-11, after rebasing onto EPMCDME-13429's single spend ledger).** Elasticsearch `attributes.money_spent` is a settled remainder, so every money figure this story adds comes from the LiteLLM spend ledger, priced per run: a request id for chat requests, the execution id for workflow executions (workflow LLM calls carry it as `request_id`). `request_spend.collect_request_usage` lists the runs behind a table with a composite aggregation over (group, run id) under the table's own secured query, with each run's first `@timestamp` and coverage-qualified Elasticsearch money; `price_requests` prices runs first seen at or after the ledger's coverage floor with `spend_service.costs_for_requests` and keeps the Elasticsearch figure below it or without an activated ledger. `costs_for_requests` reads each ledger in batches of `SPEND_LEDGER_REQUEST_COST_BATCH_SIZE` (default 1,000) ids; a failed batch leaves only its own ids unavailable. A pending cost is `null` with `spend_unavailable: true`. `workflows-executions` rows carry the whole execution's cost and `totals.money_spent` sums every execution in the filtered range, listed in the same snapshot. `attributes-usage` `total_cost` sums the runs carrying each value. Under an `attributes` filter, `/workflows` and `/assistants-chats` price their rows from the filtered runs instead of the ledger's workflow and assistant dimensions, which cannot be narrowed by attributes; without the filter they are unchanged. Unfiltered `/workflows` still prices only a name that belongs to exactly one existing workflow, so executions of deleted, duplicate-named or renamed workflows have a cost in `workflows-executions` and none there, and under the filter `/workflows` prices them too.
## Acceptance criteria

1. Valid attributes on a chat or workflow request are stored on the run and returned by the two read endpoints.
2. Invalid count, key, reserved prefix or value (empty, over 128 chars, control characters, unpaired surrogates) returns 422 and nothing runs, with no history write, usage record or request summary. A 129-char value is rejected; a 64-char key with a 128-char value is accepted and its `key=value` pair is 193 chars.
3. Chat: a pre-created empty conversation takes the request attributes; a conversation with history keeps its stored attributes when later turns omit them or send identical ones. On different attributes the request returns 422 from a pre-flight check outside the `try`, and writes no error turn into the conversation history, no assistant usage record and no request summary; the conversation row is unchanged. A request without attributes does not load the conversation. A caller who cannot read the conversation gets neither the 422 nor its stored attributes, and the attributes they send are dropped, so they are never stored on that conversation (empty or not) or written to its usage records (revised 2026-11-02).
4. Every `conversation_assistant_usage` and `workflow_execution_total` record of a run with attributes carries both keyword arrays, including tool-resume turns, resumed executions, sub-workflows (parent's attributes) and metrics flushed after `delete_on_completion`.
5. Attributes never reach the OTel counter; records for runs without attributes are unchanged.
6. The `attributes` filter narrows `/assistants-chats`, `/assistants-requests`, `/workflows`, `/workflows-executions` and `/attributes-usage` to runs matching all pairs; an invalid filter (including a value over 128 chars or input nested too deeply to parse) returns 422, not 400, via an explicit `ExtendedHTTPException(code=422)`.
7. `attributes-usage` returns the documented columns, scoped by the existing access filter; a key with `.` or `-` does not match sibling keys sharing a prefix; a missing or invalid `attribute_key` returns 422, not 400.
8. Migration applies and downgrades cleanly on a single head; existing rows keep `attributes` null.
9. Revised 2026-11-02: no docs page in this repository; the OpenAPI descriptions listed under Docs cover the topics listed under Docs and state the 128-char value limit.
10. Every `assistants-requests` row has an `attributes` column: the record's pairs as a `{key: value}` object (a value containing `=` survives intact), or `null` without pairs.
11. `metadata.filters_applied` echoes the `attributes` filter (null when absent).
12. `workflows-executions` returns one row per `execution_id` of the `workflow_execution_total` documents in range, newest activity first, with summed tokens, the execution's cost (see Cost), the newest document's workflow name, status, user and project, and an `attributes` column (`{key: value}` or `null`); totals cover the complete filtered range from the same snapshot and are independent of pagination. Per-execution usage includes every matching document across shards/indexes. Incomplete searches return 503; the PIT is closed on success and failure.

## Non-goals

- Editing, adding or removing attributes after start.
- Key registry, allowlist or per-key value rules.
- Any UI or SDK change.
- Forwarding to LiteLLM spend logs or Langfuse; reuse of chat `metadata` or workflow `tags`.
- Attributes on webhook, scheduler or A2A runs, or on tool, CLI or datasource metrics.
- Backfill of existing runs; new ES index or mapping change (including raising `ignore_above`); index on the JSONB columns.
- Usage records for `save_history=false` chats or virtual assistants.
- Changing `handle_analytics_errors` or its ValueError-to-400 behavior for other endpoints.
- Revised 2026-11-02, removed as redundant: a `GET /v1/analytics/attribute-keys` endpoint listing the keys in use, and the `attributes` filter on `/summaries` (including DAU, MAU and the CLI cost adjustment). Neither was asked for by the ticket, and `/summaries` mixes usage types that carry no attributes.
