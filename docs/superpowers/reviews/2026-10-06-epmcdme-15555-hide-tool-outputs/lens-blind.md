- `strip_response` fails open for any response type without `model_fields` (not a `StreamingResponse` and not a pydantic model): it only logs an error and returns the original, unstripped response — src/codemie/service/assistant/tool_output_visibility.py lines 439-449. This directly contradicts the "fail closed" principle stated elsewhere in the same diff (`_effective_hide_tool_outputs` docstring, `_hidden_ids` comment) — an unrecognized response type silently leaks tool outputs instead of being blocked or raising.

- `strip_chunk`/`_strip_line` assumes each chunk handed to it from `body_iterator` contains only complete NDJSON lines terminated by `\n`; if a network/streaming boundary ever splits one JSON record across two chunks, the trailing partial fragment is unparseable JSON and gets silently dropped (`except ValueError: return None` path in `_strip_line`, src/codemie/service/assistant/tool_output_visibility.py lines 373-378) — unfiltered streams tolerate this by buffering elsewhere, but the new filter has no buffering and would corrupt/truncate the stream rather than reassembling the split line.

- The thought-only drop check `if thought and not any(data.get(k) for k in _PAYLOAD_KEYS): return None` (tool_output_visibility.py line 382) uses a truthiness test, not key-presence. A chunk carrying a legitimate falsy payload value alongside a thought — e.g. `tool_call_pending: False` (signalling "no longer pending") or `generated: ""` — is indistinguishable from a pure-thought chunk and gets dropped entirely, losing that state transition for the client.

- `tool_errors` is only nulled when `data.get("last")` is true (tool_output_visibility.py line 391-392); the code assumes `tool_errors` can only ever appear on the final chunk. If a handler ever emits `tool_errors` on a non-final chunk, it passes through completely unfiltered even though `hide_tool_outputs` is on.

- `_ask_assistant_resume` strips using only `apply_to_response(assistant, ...)` (src/codemie/rest_api/routers/assistant.py line 66), i.e. `is_hidden(assistant)` alone, whereas the sibling `ask_assistant_by_id`/`ask_assistant_by_slug` paths combine `is_hidden(master) or is_hidden(execution_assistant)` via `_effective_hide_tool_outputs` to fail closed against version-pinned requests (lines 57, 74, 82-84). If tool-call resume can also be invoked against a version-pinned conversation/assistant, this path has no equivalent master+pinned-version fail-closed check, unlike every other entry point in this diff.

- The security-error promotion in `_strip_line` only fires `if ... and not data.get("generated") and thought.get("message")` (tool_output_visibility.py line 386). If a final chunk already carries any truthy `generated` text alongside an error thought, the error message is silently discarded rather than appended/surfaced, with no fallback or logging — a legitimate security-error message could be lost to the end user.

- `strip_chunk` decodes bytes with the platform default (`chunk.decode()`, tool_output_visibility.py line 399) without specifying `utf-8` explicitly or handling decode errors; a non-UTF8 byte chunk (unlikely but unchecked) would raise an uncaught `UnicodeDecodeError` inside the stripping wrapper instead of failing gracefully.
